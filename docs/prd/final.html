1. 개요

1.1 무엇을 만들었나

브라우저나 curl이 보낸 HTTP 요청을 받아 세 가지 방법 중 하나로 응답하는 서버입니다.

                                   ┌─ 정적 파일   폴더에서 파일을 읽어 응답
클라이언트 ── HTTP 요청 ──▶ 서버 ──┼─ CGI         프로그램을 실행하고 그 출력을 응답
                                   └─ 중계        백엔드 서버에 대신 요청하고 받은 응답을 전달

어느 방법으로 처리할지는 요청 경로가 정합니다. 실행할 때 준 라우팅 규칙에 맞는 경로는 백엔드로 중계하고, 나머지는 서버가 직접 정적 파일이나 CGI로 처리합니다.

1.2 해결하려는 문제

시작점은 CS:APP 교재의 예제 서버 Tiny입니다. Tiny는 요청을 받아 파일과 CGI 결과를 돌려주지만, 실제 서버로 쓰기에는 다음 문제가 있습니다.

Tiny의 문제이 서버의 해결자세한 내용
한 번에 한 연결만 처리합니다. 한 클라이언트가 멈추면 모두 기다립니다.스레드 풀로 여러 연결을 동시에 처리하고, 멈춘 연결은 제한 시간 뒤에 닫습니다.5.1, 5.2
헤더와 본문을 버립니다. POST를 처리하지 못하고 응답마다 연결을 닫습니다.헤더와 본문을 해석해 POST를 처리하고 연결을 재사용합니다.5.2, 5.6
클라이언트 하나의 오류로 서버 전체가 종료될 수 있습니다.문제가 생긴 요청만 정리하고 서버는 계속 동작합니다.7장 1번
CGI가 실패해도 200 OK가 나갑니다.출력을 모두 받아 확인한 뒤 응답합니다. 실패는 500, 시간 초과는 504입니다.5.4
다른 서버로 요청을 나누지 못합니다.Reverse Proxy와 Round-Robin 로드 밸런싱을 제공합니다.5.5
종료하면 처리 중이던 응답이 잘립니다.종료 시그널을 받으면 하던 요청을 마치고 자원을 정리합니다.5.7

3.3 범위에서 제외한 것

항목이유
Forward Proxy, 캐싱Reverse Proxy 하나로 필수 요구사항을 충족합니다. Forward Proxy는 HTTPS용 CONNECT와 내부망 접근 차단까지 필요합니다.
이벤트 루프연결마다 읽기·쓰기 진행 상태를 저장하도록 코드 전체를 다시 짜야 합니다.
chunked 요청 본문과제는 Content-Length 기반 처리를 요구합니다. 501로 거절합니다.
Host 기준 라우팅, 라우팅 설정 파일경로 기준 라우팅과 실행 인자로 요구사항을 충족합니다.
백엔드 연결 재사용, 백엔드 상태 확인, Least Connections연결 풀, 확인 스레드, 연결 수 집계가 각각 필요합니다.
작업 큐가 가득 찼을 때 503기다리면 처리할 수 있는 연결까지 거절하게 됩니다.
부하가 높을 때 연결 유지 중단M8에서 측정할 연결 재사용률에 직접 영향을 줍니다.

3.4 과제 요구 외에 추가한 기능

기능선택한 이유
정적 파일과 중계의 HEAD본문 없이 응답 헤더를 확인할 수 있고, GET의 처리에서 본문만 빼면 됩니다.
Expect: 100-continue큰 본문을 받기 전에 거절할 수 있고, curl이 응답을 기다리며 약 1초 늦어지는 것을 막습니다.
연결당 요청 수 상한요청을 계속 보내는 연결 하나가 작업 스레드를 오래 차지하지 않게 합니다.
요청 수신 마감타임아웃만으로는 막지 못하는, 조금씩 계속 보내는 연결(Slowloris)을 정해진 시간에 닫습니다.
CGI 프로세스 그룹 분리터미널의 Ctrl+C에 CGI가 함께 종료되어 처리 중인 요청이 실패하는 것을 막습니다.

5. 기능 설계

5.1 연결과 동시성 (M1, M4)

서버는 socket → SO_REUSEADDR → bind → listen 순서로 포트를 엽니다. SO_REUSEADDR은 서버를 껐다가 바로 켤 때 이전 연결이 남아 있어도 같은 포트를 쓸 수 있게 합니다.

main 스레드는 새 연결을 받아 작업 큐에 넣고, 작업 스레드가 꺼내 처리합니다.

  • 작업 큐는 고정 크기 원형 배열이며 mutex 1개와 조건 변수 2개(비어 있지 않음, 가득 차지 않음)로 보호합니다.
  • 락은 작업 큐를 만지는 동안에만 잡습니다. 요청 처리는 락 밖에서 하므로 작업 스레드들이 동시에 일합니다.
  • 작업 큐가 가득 차면 main 스레드가 빈자리를 기다립니다. 그동안 새 연결은 운영체제의 연결 대기열에 머뭅니다.
  • fd가 모자라 accept가 실패하면 10ms 쉬고 다시 시도합니다.

CGI 프로세스가 다른 클라이언트의 소켓을 물려받으면 서버가 연결을 닫아도 상대에게 FIN이 가지 않습니다. 이를 두 겹으로 막습니다. 소켓에 FD_CLOEXEC를 설정하고, CGI 자식 프로세스는 실행 직전에 3번 이상의 fd를 모두 닫습니다. Linux에서는 accept4와 close_range를 쓰고, 그 밖의 환경에서는 fcntl과 반복 close를 씁니다.

5.2 요청 읽기와 검사 (M2, M5, M7)

읽기와 마감

연결마다 8 KiB 읽기 버퍼를 하나 두고 연결이 끝날 때까지 씁니다. 클라이언트가 다음 요청을 미리 보내면(파이프라이닝) 그 데이터가 이미 버퍼에 있을 수 있어서, 요청마다 새로 만들면 데이터를 잃습니다.

5.5 Reverse Proxy (M6)

라우팅

규칙은 접두사=백엔드,백엔드 형식입니다. ? 앞의 경로가 접두사로 시작하고 그다음 글자가 /이거나 경로의 끝이면 맞는 것으로 봅니다. 여러 규칙에 맞으면 가장 긴 접두사를 씁니다. 경로와 쿼리는 바꾸지 않고 백엔드에 그대로 보냅니다.

규칙맞는 경로맞지 않는 경로
/api 또는 /api//api, /api/users, /api?x=1/apiary, /a?/api
/api, /api/admin/api/admin/x는 /api/admin 규칙 사용
/모든 경로. 더 긴 규칙이 있으면 그쪽이 우선

접두사 끝의 /는 떼고 저장합니다. 그래서 /api/로 설정해도 /api 요청이 맞고, /api와 /api/를 함께 등록하면 중복으로 거절합니다.

규칙은 시작할 때 검사합니다. 형식 오류, 잘못된 포트, 중복된 접두사, 개수 초과, 주소를 찾을 수 없는 이름, 자기 자신을 가리키는 백엔드가 있으면 이유를 출력하고 시작하지 않습니다.

5.6 응답과 연결 유지 (M5, M7)

정적 파일, CGI, 오류 응답은 HTTP/1.1 상태 줄과 Content-Length, Connection을 포함합니다. 중계한 응답에는 백엔드가 길이를 준 경우에만 Content-Length를 넣으며, 세부 규칙은 5.5의 표를 따릅니다.

연결은 요청을 끝까지 읽었고 응답 길이를 알면 유지하고, 아니면 닫습니다. 길이를 정할 필요가 없는 본문 없는 응답은 길이를 아는 것으로 봅니다.

HTTP/1.0이고 Connection: keep-alive가 있음유지

길이를 모르는 중계 응답닫음
연결의 요청 수가 --keepalive-max에 도달닫음
종료가 시작됨닫음
응답을 보내다 실패닫음

닫기로 정한 응답에는 Connection: close를 넣습니다.

응답한 뒤 바로 닫으면, 서버가 읽지 않은 데이터가 남아 있을 때 FIN 대신 RST가 나가 클라이언트가 응답을 받지 못할 수 있습니다. 그래서 먼저 쓰기 방향만 닫아 응답이 끝났음을 알리고, 클라이언트가 닫을 때까지 최대 1초, 1 MiB까지 남은 데이터를 읽어 버린 뒤 닫습니다. 응답 없이 끝내는 연결은 이 과정을 거치지 않습니다. 정적 파일, CGI, 오류 응답은 전송에 실패해 닫을 때도 이 과정을 거칠 수 있고, 중계 응답은 전송에 실패하면 바로 닫습니다.

요청마다 메서드, URI, 버전, 상태 코드를 한 줄 로그로 남깁니다. 중계한 요청에는 연결한 백엔드 주소를 붙여 Round-Robin을 확인할 수 있습니다. 응답 없이 끝난 연결 중 요청을 다 읽지 못한 경우에는 로그를 남기지 않습니다.

GET /home.html HTTP/1.1 200
GET /api/users HTTP/1.1 200 -> 127.0.0.1:8001
GET /api/users HTTP/1.1 200 -> 127.0.0.1:8002

5.7 종료 (M7)

SIGINT나 SIGTERM을 받으면 새 연결을 받지 않고, 처리 중인 요청과 작업 큐에 남은 연결의 첫 요청까지 응답한 뒤 종료합니다. 종료 시그널이 다시 오면 즉시 종료합니다.

[시그널 스레드]  sigwait로 첫 번째 시그널 수신
                  → 종료 표시 → 종료 파이프에 1바이트 → 작업 큐 종료
                  → 두 번째 시그널이 오면 _exit(1)

[main 스레드]    종료 파이프를 보고 accept 중단 → 리스닝 소켓 닫기
                  → 작업 스레드가 모두 끝날 때까지 기다림
                  → 시그널 스레드를 깨워 끝냄 → 자원 해제 → 종료 코드 0

[작업 스레드]    처리 중인 요청을 마치고 Connection: close로 응답
                  → 작업 큐에 남은 연결의 첫 요청 처리 → 종료
                  연결 유지로 쉬던 연결은 종료 파이프를 보고 바로 닫음

스레드마다 기다리는 곳이 달라 깨우는 방법도 다릅니다. poll에서 기다리는 스레드는 종료 파이프가, 작업 큐에서 기다리는 스레드는 조건 변수가 깨웁니다. 종료 파이프의 1바이트는 아무도 읽지 않으므로 여러 스레드가 같은 알림을 볼 수 있습니다.

종료 알림과 소켓이 동시에 준비되면 스레드에 따라 순서가 다릅니다. main 스레드는 종료 알림을 먼저 보고 새 연결을 받지 않습니다. 작업 스레드는 이미 도착한 요청을 먼저 처리하고, 도착한 데이터가 없는 연결만 바로 닫습니다.

SIGPIPE는 무시합니다. 이미 끊긴 클라이언트에 데이터를 쓰면 기본 동작으로는 서버 전체가 종료되지만, 무시하면 쓰기 실패로 처리해 그 연결만 정리할 수 있습니다.

5. 연결 유지 규칙을 하나로 통일한다

정적 파일 성공만 유지하는 방법과 오류 응답까지 모두 유지하는 방법을 비교했습니다. 요청을 끝까지 읽었고 응답 길이를 아는지만 확인하면 모든 응답에 같은 규칙을 적용할 수 있습니다. 본문 길이가 잘못된 요청 뒤에 연결을 유지해 다음 요청의 시작을 잘못 읽는 일도 막습니다. 근거 기록: m4m5 5.2

6. Reverse Proxy를 서버 안의 라우팅 단계로 둔다

Forward Proxy는 클라이언트를 대신해 바깥 서버에 요청하고, Reverse Proxy는 백엔드를 대신해 클라이언트의 요청을 받습니다. Reverse Proxy를 고른 이유는 백엔드를 직접 띄워 실패 상황까지 확인할 수 있고, 권장 요구사항인 Round-Robin으로 이어지기 때문입니다.

별도 프로그램으로 나누는 대신 기존 서버에 라우팅 단계를 넣어 스레드 풀, 요청 해석, 연결 유지 코드를 그대로 씁니다. 정적 요청이 프록시를 한 번 더 거치지도 않습니다. 근거 기록: m6m7 M6-1, M6-2

7. 백엔드에는 HTTP/1.0으로 요청한다

방법특징
클라이언트의 버전 그대로요청마다 백엔드의 동작이 달라짐
HTTP/1.1 고정백엔드가 chunked로 응답할 수 있어 해석 코드가 필요함

RFC 9112 6.1은 HTTP/1.1보다 낮은 버전의 요청에 Transfer-Encoding으로 응답하지 못하게 합니다. 클라이언트에게는 서버의 버전인 HTTP/1.1로 응답합니다. 근거 기록: m6m7 M6-9, M6-11

8. 중계 응답은 헤더를 확인한 뒤 본문을 바로 전달한다

응답 전체를 모으면 실패할 때 항상 오류 응답을 보낼 수 있지만, 응답 크기만큼 메모리가 필요하고 큰 파일을 전달하지 못합니다. 헤더만 모아 확인하면 백엔드가 꺼졌거나 응답하지 않는 대부분의 실패를 502와 504로 알릴 수 있고 본문의 메모리 사용량은 일정합니다.

본문 도중의 실패는 curl로 확인해 처리 방법을 정했습니다. 길이가 없는 응답이 FIN으로 끊기면 curl이 성공으로 판단하기 때문에 RST로 닫습니다.

본문 도중 끊긴 응답FIN으로 닫음RST로 닫음
길이 있음curl 오류 18curl 오류 56
길이 없음curl 성공 (잘린 것을 모름)curl 오류 56

근거 기록: m6m7 M6-11 ~ M6-13

9. 연결 실패에만 다른 백엔드를 시도한다

재시도하지 않으면 백엔드 2대 중 1대가 꺼졌을 때 요청의 절반이 실패합니다. 반대로 요청을 보낸 뒤에도 재시도하면 같은 POST가 두 번 처리될 수 있습니다. 연결 단계의 실패는 요청을 보내지 않은 상태라 안전하게 재시도할 수 있습니다. 여러 백엔드를 시도해도 전체 시간은 처음 정한 마감을 넘지 않습니다. 근거 기록: m6m7 M6-14, M6-15

10. 요청을 읽는 단계마다 마감을 둔다

타임아웃만 쓰면 조금씩 계속 보내는 연결을 막지 못하고, 헤더에만 마감을 두면 같은 공격을 본문으로 옮길 수 있습니다. 헤더와 본문에 각각 마감을 두고 poll로 기다립니다. poll을 쓰면서 쉬는 연결이 종료 파이프를 함께 볼 수 있게 되어 종료도 빨라졌습니다. 근거 기록: m6m7 M7-4

11. 시그널 전용 스레드로 종료한다

시그널 핸들러는 아무 스레드에서나 실행되고 mutex를 쓸 수 없어 작업 큐를 안전하게 깨우지 못합니다. 종료 시그널을 모든 스레드에서 막고 전용 스레드가 sigwait로 받으면 일반 코드처럼 락을 쓸 수 있습니다. Linux와 macOS에서 같은 방식으로 동작합니다.

두 번째 종료 시그널은 종류와 상관없이 즉시 종료합니다. 정상 종료가 길어질 때 사용할 방법을 하나의 규칙으로 정했습니다. 근거 기록: m6m7 M7-5 ~ M7-8

12. 경로가 잘못되면 고치지 않고 거절한다

10.1 설계에서 선택한 한계

영역한계다시 검토할 조건
동시성연결이 작업 스레드 수보다 많으면 기다립니다. 계속 요청하는 연결은 최대 100건까지 작업 스레드를 차지합니다.부하 측정에서 대기가 길면 이벤트 루프나 부하에 따른 연결 유지 중단을 검토
동시성스레드 하나의 메모리 오류가 서버 전체에 영향을 줍니다.Sanitizer로 예방
과부하작업 큐가 가득 차면 기다리기만 합니다.과부하가 계속되는 환경이면 503 검토
요청HTTP/1.1 수신자는 chunked를 해석해야 하지만(RFC 9112 7.1), 이 구현은 chunked 요청을 501로 거절합니다.chunked로 보내는 클라이언트를 지원해야 할 때
요청절대 URI와 % 인코딩 해석을 지원하지 않습니다.해당 클라이언트를 지원해야 할 때
요청본문을 30초 안에 보내지 못하는 느린 업로드도 끊깁니다.정상 업로드가 끊기면 마감을 조정
응답쓰기 제한은 write 한 번 기준이라 조금씩 계속 받는 클라이언트는 막지 못합니다.느린 수신자가 문제가 되면 쓰기 마감 추가
파일심볼릭 링크가 루트 밖을 가리키는 것은 막지 않습니다.루트에 외부 링크를 두지 않는 것으로 관리
CGI본문과 출력은 1 MiB까지입니다. 클라이언트가 끊겨도 CGI가 끝나거나 10초가 지날 때까지 작업 스레드가 기다립니다.큰 파일 처리가 필요할 때
CGI서버가 강제 종료되면 실행 중인 CGI가 남을 수 있습니다.실제로 문제가 될 때
프록시프록시가 멈추면 모든 백엔드에 접근할 수 없습니다.다중화가 필요할 때
프록시백엔드 상태를 미리 확인하지 않아 꺼진 백엔드에도 연결을 시도합니다.응답 지연이 커지면 상태 확인 추가
프록시요청마다 새 연결을 맺어 TIME_WAIT가 쌓이고, GET·POST·HEAD만 중계합니다.부하 측정 결과에 따라
프록시백엔드의 주소는 다시 시작해야 갱신됩니다. 다른 프록시를 거쳐 돌아오는 요청은 감지하지 못합니다.운영 환경에 맞춰
프록시길이 없는 응답을 보내던 백엔드 프로세스가 죽으면 완료된 응답과 구분할 수 없습니다.백엔드가 길이를 보내도록 구성
종료정상 종료의 전체 시간에는 상한이 없습니다. 첫 요청을 보내지 않은 연결은 타임아웃(5초)까지 기다립니다.두 번째 종료 시그널로 즉시 종료 가능
종료SIGHUP에는 정리 없이 끝납니다. 작업 큐에 넣지 못한 연결은 응답 없이 끊깁니다.운영 환경에 맞춰
