# Reverse Proxy 라우팅 설계 예시

> 개인 PRD 초안 예시입니다. Reverse Proxy를 선택한다고 가정하고 라우팅 방식 하나를 비교합니다.

## 목표와 범위

프록시의 한 주소로 들어온 API 요청과 정적 파일 요청을 각각 담당하는 백엔드에 전달합니다. 클라이언트가 받은 본문과 프록시 로그를 보고 어떤 백엔드가 응답했는지 확인할 수 있으면 목표를 달성한 것으로 봅니다.

이 예시에서는 `/api/`와 `/static/`에 백엔드 하나씩 연결합니다. 여러 백엔드에 요청을 나눠 보내는 로드 밸런싱은 이후로 미룹니다.

## 설계 선택

Reverse Proxy는 요청의 URL 경로와 `Host` 헤더 중 어느 값을 보고 백엔드를 고를까요?

- **경로 기준**은 요청 경로가 `/api/`와 `/static/` 중 어느 쪽으로 시작하는지 비교합니다. 같은 주소에서 경로만 바꿔 어떤 규칙이 적용되는지 재현할 수 있습니다.
- **호스트 기준**은 `Host`에서 호스트 이름을 얻고 그 이름에 연결된 백엔드를 고릅니다. 포트가 포함된 값도 처리해야 하고, 라우팅 문제를 재현할 때는 원래 요청의 `Host` 값도 알아야 합니다.

**추천은 경로 기준입니다.** 한 주소 아래 API와 정적 파일을 나누는 데 필요한 두 규칙을 바로 표현할 수 있고, 테스트할 때도 URL만 바꾸면 됩니다. 백엔드에는 받은 경로를 그대로 전달합니다.

이 방식에서는 서비스별 경로 접두사를 합의해야 합니다. 서로 다른 서비스가 각자 같은 경로를 써야 한다면 호스트 기준을 다시 검토합니다.

## 요청 흐름

```text
curl에서 GET /api/health 요청
  → 프록시가 요청을 읽고 경로를 파싱
  → /api/ 규칙에 따라 API 백엔드 127.0.0.1:8001 선택
  → API 백엔드에 GET /api/health 전달
  → 백엔드의 200 응답과 api-ok 본문을 클라이언트에 반환
```

프록시 로그에는 요청 경로와 적용한 규칙, 백엔드 주소를 남깁니다. 일치하는 규칙이 없으면 프록시에서 `404`를 응답합니다.

## 검증 계획

프록시는 `8080`, API 백엔드는 `8001`, 정적 파일 백엔드는 `8002`에 띄웁니다. API 백엔드의 `/api/health`는 `api-ok`를 반환하고, 정적 파일 백엔드의 `/static/site.css`는 테스트용 CSS를 반환하도록 준비합니다.

| 요청 | 기대 응답 | 프록시 로그에서 볼 것 |
| --- | --- | --- |
| `curl -i http://127.0.0.1:8080/api/health` | `200`과 `api-ok` 본문 | 규칙 `/api/`, 백엔드 `127.0.0.1:8001` |
| `curl -i http://127.0.0.1:8080/static/site.css` | `200`과 테스트용 CSS 본문 | 규칙 `/static/`, 백엔드 `127.0.0.1:8002` |
| `curl -i http://127.0.0.1:8080/apix/health` | `404` | 일치한 규칙과 선택된 백엔드가 없음 |

라우팅 단위 테스트에도 같은 세 경로를 넣습니다. `/apix/health`가 `/api/` 규칙에 잘못 들어가지 않는지 확인할 수 있습니다.
