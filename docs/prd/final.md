## 1. 개요

### 1.1 무엇을 만들었나

브라우저나 curl이 보낸 HTTP 요청을 받아 세 가지 방법 중 하나로 응답하는 서버입니다.

```text
                                   ┌─ 정적 파일   폴더에서 파일을 읽어 응답
클라이언트 ── HTTP 요청 ──▶ 서버 ──┼─ CGI         프로그램을 실행하고 그 출력을 응답
                                   └─ 중계        백엔드 서버에 대신 요청하고 받은 응답을 전달
```

어느 방법으로 처리할지는 요청 경로가 정합니다. 실행할 때 준 라우팅 규칙에 맞는 경로는 백엔드로 중계하고, 나머지는 서버가 직접 정적 파일이나 CGI로 처리합니다.

### 1.2 해결하려는 문제

시작점은 CS:APP 교재의 예제 서버 Tiny입니다. Tiny는 요청을 받아 파일과 CGI 결과를 돌려주지만, 실제 서버로 쓰기에는 다음 문제가 있습니다.

| Tiny의 문제 | 이 서버의 해결 | 자세한 내용 |
| --- | --- | --- |
| 한 번에 한 연결만 처리합니다. 한 클라이언트가 멈추면 모두 기다립니다. | 스레드 풀로 여러 연결을 동시에 처리하고, 멈춘 연결은 제한 시간 뒤에 닫습니다. | [5.1](#51-연결과-동시성-m1-m4), [5.2](#52-요청-읽기와-검사-m2-m5-m7) |
| 헤더와 본문을 버립니다. POST를 처리하지 못하고 응답마다 연결을 닫습니다. | 헤더와 본문을 해석해 POST를 처리하고 연결을 재사용합니다. | [5.2](#52-요청-읽기와-검사-m2-m5-m7), [5.6](#56-응답과-연결-유지-m5-m7) |
| 클라이언트 하나의 오류로 서버 전체가 종료될 수 있습니다. | 문제가 생긴 요청만 정리하고 서버는 계속 동작합니다. | [7장](#7-주요-설계-결정) 1번 |
| CGI가 실패해도 `200 OK`가 나갑니다. | 출력을 모두 받아 확인한 뒤 응답합니다. 실패는 `500`, 시간 초과는 `504`입니다. | [5.4](#54-cgi-m3-m5-m7) |
| 다른 서버로 요청을 나누지 못합니다. | Reverse Proxy와 Round-Robin 로드 밸런싱을 제공합니다. | [5.5](#55-reverse-proxy-m6) |
| 종료하면 처리 중이던 응답이 잘립니다. | 종료 시그널을 받으면 하던 요청을 마치고 자원을 정리합니다. | [5.7](#57-종료-m7) |

### 1.3 진행 방식

| 단계 | 마일스톤 | 한 일 |
| --- | --- | --- |
| Phase 1 교체 | M1 소켓 연결, M2 정적 GET, M3 CGI GET | Tiny의 각 부분을 같은 동작을 하는 팀 코드로 바꿨습니다. |
| Phase 2 확장 | M4 동시성, M5 HTTP 완성 | 동시 처리, POST, 연결 유지, CGI 오류 응답을 더했습니다. |
| | M6 Reverse Proxy, M7 안정성 | 중계, 로드 밸런싱, 요청 검사, 수신 마감, 안전한 종료를 더했습니다. |
| | M8 품질 검증 | 부하 측정과 README를 정리할 예정입니다. |

마일스톤마다 세 사람이 같은 범위를 각자 설계한 뒤, 초안을 비교해 팀 설계를 정하고 코드를 하나로 합쳤습니다.

## 2. 용어

이 문서는 아래 이름으로 통일해서 씁니다.

| 용어 | 뜻 |
| --- | --- |
| 클라이언트 | 서버에 요청을 보내는 쪽. 브라우저, curl 등 |
| 백엔드 | 중계할 때 이 서버가 대신 요청을 보내는 뒤쪽 서버 |
| main 스레드 | 새 연결을 받아 작업 큐에 넣는 스레드 |
| 작업 스레드 | 작업 큐에서 연결을 꺼내 요청을 처리하는 스레드 |
| 시그널 스레드 | 종료 시그널만 기다리는 스레드 |
| 작업 큐 | 작업 스레드를 기다리는 연결이 줄을 서는 고정 크기 큐 |
| 스레드 풀 | 미리 만들어 두고 계속 다시 쓰는 작업 스레드 묶음 |
| 리스닝 소켓 | 새 연결을 기다리는 소켓 |
| 클라이언트 소켓, 백엔드 소켓 | 각각 클라이언트, 백엔드와 데이터를 주고받는 소켓 |
| 연결 유지 (keep-alive) | 응답한 뒤 연결을 닫지 않고 다음 요청을 받는 것 |
| 타임아웃 | 새 데이터가 오지 않을 때 기다리는 최대 시간 |
| 마감 | 데이터가 계속 와도 연장하지 않는 전체 제한 시간 |
| CGI | 서버가 프로그램을 실행하고 그 출력을 응답으로 보내는 방식 |
| 중계 | 요청을 백엔드에 전달하고 응답을 클라이언트에 전달하는 일 |
| 경로 접두사 | 라우팅 규칙이 비교하는 경로의 앞부분. 예: `/api` |
| 홉 단위 헤더 | 이웃한 두 서버 사이의 연결에만 적용되어 다음 구간으로 넘기지 않는 헤더. 예: `Connection` |
| fd | 프로세스가 연 파일이나 소켓을 가리키는 번호 (파일 디스크립터) |
| FIN, RST | TCP 연결을 닫는 두 가지 방법. FIN은 정상 종료, RST는 강제 종료 |

### 3.3 범위에서 제외한 것

| 항목 | 이유 |
| --- | --- |
| Forward Proxy, 캐싱 | Reverse Proxy 하나로 필수 요구사항을 충족합니다. Forward Proxy는 HTTPS용 `CONNECT`와 내부망 접근 차단까지 필요합니다. |
| 이벤트 루프 | 연결마다 읽기·쓰기 진행 상태를 저장하도록 코드 전체를 다시 짜야 합니다. |
| chunked 요청 본문 | 과제는 `Content-Length` 기반 처리를 요구합니다. `501`로 거절합니다. |
| Host 기준 라우팅, 라우팅 설정 파일 | 경로 기준 라우팅과 실행 인자로 요구사항을 충족합니다. |
| 백엔드 연결 재사용, 백엔드 상태 확인, Least Connections | 연결 풀, 확인 스레드, 연결 수 집계가 각각 필요합니다. |
| 작업 큐가 가득 찼을 때 `503` | 기다리면 처리할 수 있는 연결까지 거절하게 됩니다. |
| 부하가 높을 때 연결 유지 중단 | M8에서 측정할 연결 재사용률에 직접 영향을 줍니다. |

### 3.4 과제 요구 외에 추가한 기능

| 기능 | 선택한 이유 |
| --- | --- |
| 정적 파일과 중계의 HEAD | 본문 없이 응답 헤더를 확인할 수 있고, GET의 처리에서 본문만 빼면 됩니다. |
| `Expect: 100-continue` | 큰 본문을 받기 전에 거절할 수 있고, curl이 응답을 기다리며 약 1초 늦어지는 것을 막습니다. |
| 연결당 요청 수 상한 | 요청을 계속 보내는 연결 하나가 작업 스레드를 오래 차지하지 않게 합니다. |
| 요청 수신 마감 | 타임아웃만으로는 막지 못하는, 조금씩 계속 보내는 연결(Slowloris)을 정해진 시간에 닫습니다. |
| CGI 프로세스 그룹 분리 | 터미널의 Ctrl+C에 CGI가 함께 종료되어 처리 중인 요청이 실패하는 것을 막습니다. |

### 4.3 요청 하나의 흐름

`./build/tiny 8000 --route /api=127.0.0.1:8001,127.0.0.1:8002`로 실행한 서버에 요청이 온 경우입니다.

```text
[main 스레드]   리스닝 소켓에서 accept → 작업 큐에 넣기
[작업 스레드]   작업 큐에서 연결 꺼내기
                  │
  1. 읽기         요청 줄과 헤더 (마감 10초)
  2. 검사         형식, 버전, 메서드, 헤더           → 400 413 414 417 501 505, 연결 닫기
  3. 본문         필요하면 100 Continue를 보낸 뒤 Content-Length만큼 (마감 30초)
  4. 경로 검사    ".." "." 빈 조각                   → 403
  5. 라우팅       /api 규칙에 맞는가?
                  ├─ 맞음   백엔드 선택 → 연결 → 요청 전달 → 응답 전달    → 502 504
                  └─ 아님   정적 파일 또는 CGI                            → 404 405 403 500 504
  6. 응답         상태 줄, 헤더, 본문 전송과 요청 로그 출력
  7. 연결 판단    유지 조건을 만족하면 1번으로, 아니면 닫고 다음 연결 꺼내기
```

### 4.4 실행 방법

```text
./build/tiny <port> [--root DIR] [--threads N] [--queue N] [--timeout 초] [--keepalive-max N]
                    [--route 접두사=이름:포트[,이름:포트...]]... [--proxy-timeout 초]
```

| 인자 | 기본값 | 설명 |
| --- | --- | --- |
| `<port>` | 필수 | 1~65535. 항상 첫 번째 인자입니다. |
| `--root` | 현재 폴더 | 정적 파일과 CGI를 찾는 폴더 |
| `--threads` | 16 | 작업 스레드 수 |
| `--queue` | 64 | 작업 큐 크기 |
| `--timeout` | 5 | 요청을 읽을 때의 타임아웃(초). 헤더 마감은 2배, 본문 마감은 6배, 클라이언트 쓰기 제한은 2배 |
| `--keepalive-max` | 100 | 연결 하나에서 처리하는 최대 요청 수 |
| `--route` | 없음 | 라우팅 규칙. 여러 번 줄 수 있으며 규칙은 최대 16개, 규칙당 백엔드는 최대 8개 |
| `--proxy-timeout` | 10 | 백엔드 연결부터 최종 응답 헤더까지의 마감, 응답 본문의 타임아웃(초) |

기본값 16과 64는 M8 부하 측정 전의 시작값입니다.

```bash
make
./build/tiny 8000 --root tests/fixtures/www
curl -i localhost:8000/home.html
```

저장소의 테스트 폴더에는 `adder`가 들어 있지 않습니다. CGI를 확인하려면 `build/adder`를 `--root`로 지정한 폴더의 `cgi-bin/`에 복사합니다.

## 5. 기능 설계

### 5.1 연결과 동시성 (M1, M4)

서버는 `socket → SO_REUSEADDR → bind → listen` 순서로 포트를 엽니다. `SO_REUSEADDR`은 서버를 껐다가 바로 켤 때 이전 연결이 남아 있어도 같은 포트를 쓸 수 있게 합니다.

main 스레드는 새 연결을 받아 작업 큐에 넣고, 작업 스레드가 꺼내 처리합니다.

- 작업 큐는 고정 크기 원형 배열이며 mutex 1개와 조건 변수 2개(비어 있지 않음, 가득 차지 않음)로 보호합니다.
- 락은 작업 큐를 만지는 동안에만 잡습니다. 요청 처리는 락 밖에서 하므로 작업 스레드들이 동시에 일합니다.
- 작업 큐가 가득 차면 main 스레드가 빈자리를 기다립니다. 그동안 새 연결은 운영체제의 연결 대기열에 머뭅니다.
- fd가 모자라 `accept`가 실패하면 10ms 쉬고 다시 시도합니다.

CGI 프로세스가 다른 클라이언트의 소켓을 물려받으면 서버가 연결을 닫아도 상대에게 FIN이 가지 않습니다. 이를 두 겹으로 막습니다. 소켓에 `FD_CLOEXEC`를 설정하고, CGI 자식 프로세스는 실행 직전에 3번 이상의 fd를 모두 닫습니다. Linux에서는 `accept4`와 `close_range`를 쓰고, 그 밖의 환경에서는 `fcntl`과 반복 `close`를 씁니다.

### 5.2 요청 읽기와 검사 (M2, M5, M7)

#### 읽기와 마감

연결마다 8 KiB 읽기 버퍼를 하나 두고 연결이 끝날 때까지 씁니다. 클라이언트가 다음 요청을 미리 보내면(파이프라이닝) 그 데이터가 이미 버퍼에 있을 수 있어서, 요청마다 새로 만들면 데이터를 잃습니다.

소켓에서 읽기 전에는 `poll`로 기다립니다. 기다리는 시간은 타임아웃과 마감까지 남은 시간 중 짧은 쪽입니다. 타임아웃만 있으면 4초마다 1바이트씩 보내는 클라이언트(Slowloris 공격)가 작업 스레드를 계속 차지할 수 있습니다. 마감은 새 데이터가 와도 연장되지 않으므로 이런 연결도 정해진 시간에 닫힙니다.

#### 요청 줄과 헤더

| 검사 | 어긋나면 |
| --- | --- |
| 요청 줄이 8,191바이트 안에 끝남 | `414` |
| 메서드, URI, 버전 세 부분으로 나뉨 | `400` |
| 버전이 `HTTP/숫자.숫자` 형식 | `400` |
| 버전이 1.0 또는 1.1 | `505` |
| URI가 `/`로 시작 | `400` |
| 메서드가 HTTP 토큰 글자로만 이루어짐 | `400` |
| 메서드가 GET, POST, HEAD 중 하나 (대소문자 구분 없음) | `501` |
| 요청 줄과 헤더 줄에 탭 외의 ASCII 제어 문자가 없음 | `400` |
| 헤더가 `이름: 값` 형식이고 이름이 HTTP 토큰 | `400` |
| 헤더 한 줄이 8,191바이트 이내, 전체가 8 KiB 이내 | `400` |
| `Host`와 `Content-Type` 값이 각각 255바이트 이내 | `400` |
| HTTP/1.1이면 `Host`가 정확히 하나, HTTP/1.0이면 최대 하나 | `400` |
| `Host` 값이 `이름[:포트]` 또는 `[IPv6][:포트]` 형식 (F10, RFC 9112 3.2) | `400` |
| `Expect` 값이 `100-continue` (HTTP/1.0은 무시) | `417` |

위 오류는 요청의 끝을 확실히 알 수 없거나 그대로 받아들일 수 없는 경우라 응답한 뒤 연결을 닫습니다. 자주 쓰는 필드는 구조체에 저장하고, 원본 헤더도 함께 보존해 중계할 때 사용합니다.

URI가 `/`로 시작하는지 검사하는 것은 보안 규칙이기도 합니다. 파일 경로를 `"." + URI`로 만들기 때문에 `./secret`이라는 URI를 허용하면 루트 밖의 `../secret`을 가리키게 됩니다.

#### 본문

본문의 길이는 `Content-Length`로만 판단합니다.

| 상황 | 처리 |
| --- | --- |
| `Content-Length`가 올바름 | 정확히 그 길이만큼 읽음 |
| `Content-Length`도 `Transfer-Encoding`도 없음 | 본문 0바이트 |
| 숫자가 아님, 음수, 서로 다른 값이 여러 개 | `400` |
| `Content-Length`와 `Transfer-Encoding`이 함께 있음 | `400` |
| `Transfer-Encoding`만 있음 | `501` |
| 1 MiB 초과 | 메모리를 할당하기 전에 `413` |
| 본문을 받다가 끊기거나 시간이 지남 | 응답 없이 닫음 |

`Content-Length`와 `Transfer-Encoding`이 함께 온 요청을 받아들이면 앞뒤 서버가 본문의 끝을 다르게 판단할 수 있고, 이 틈으로 다른 요청을 숨겨 보내는 공격(request smuggling)이 가능해집니다. GET에 붙은 본문도 읽어서 비웁니다. 읽지 않으면 남은 본문이 다음 요청으로 해석됩니다.

HTTP/1.1 요청에 `Expect: 100-continue`와 본문이 있으면, 검사를 통과한 뒤 `100 Continue`를 보내고 본문을 받습니다. curl은 이 응답이 없으면 약 1초를 기다립니다.

### 5.3 경로 판정과 정적 파일 (M2, M6, M7)

라우팅보다 먼저 모든 요청의 경로를 같은 규칙으로 검사합니다. `?` 앞의 경로에 `..` 조각, `.` 조각, 중간의 빈 조각(`//`)이 있으면 `403`입니다. 라우팅과 직접 처리가 같은 경로를 보므로 `/static/../api/admin`처럼 규칙을 우회하는 경로를 막을 수 있습니다.

라우팅 규칙에 맞지 않는 요청은 `?` 앞 경로의 첫 조각이 `cgi-bin`이면 CGI, 아니면 정적 파일로 처리합니다. 정적 파일은 쿼리를 떼고 찾으므로 `/style.css?v=2`는 `style.css`를 돌려줍니다. 경로가 `/`로 끝나면 `home.html`을 찾습니다. (F9: 전에는 URI 어디에든 `cgi-bin`이 있으면 CGI였고 정적 파일 이름에 쿼리가 붙었습니다. `/a/cgi-bin/x`는 이제 정적 파일입니다.)

검사는 파일 없음 `404`, 메서드 `405`, 파일 종류와 권한 `403` 순서입니다.

| 대상 | 허용 메서드 | 허용하지 않는 메서드의 응답 |
| --- | --- | --- |
| 정적 파일 | GET, HEAD | `405`, `Allow: GET, HEAD` |
| CGI | GET, POST | `405`, `Allow: GET, POST` |

정적 파일은 먼저 열고 메모리에 올린 뒤 `200`을 보냅니다. 준비에 실패하면 `500`을 보낼 수 있습니다. 크기가 0인 파일은 메모리에 올리지 않고 길이 0으로 응답하며, HEAD는 본문 없이 같은 헤더를 보냅니다. MIME 타입은 마지막 확장자로 정합니다.

| 확장자 | Content-Type |
| --- | --- |
| `.html` | `text/html` |
| `.css` | `text/css` |
| `.js` | `text/javascript` |
| `.png` | `image/png` |
| `.jpg`, `.jpeg` | `image/jpeg` |
| `.gif` | `image/gif` |
| 그 밖 | `text/plain` |

### 5.4 CGI (M3, M5, M7)

서버는 CGI의 출력을 모두 받아 확인한 뒤 응답합니다.

```text
 작업 스레드 (부모)                              CGI 프로세스 (자식)
 환경 변수, 입력, 출력 파이프 준비
 fork ───────────────────────────────────────▶ 프로세스 그룹 분리
                                                시그널 설정을 기본값으로
                                                표준 입력과 출력을 연결
                                                fd 3번 이상 닫기
                                                execve
 출력을 모음 (1 MiB, 10초)  ◀───────────────── 헤더 + 빈 줄 + 본문
 종료 상태 확인 → 응답
```

- **입력:** POST 본문은 임시 파일에 담아 표준 입력으로 연결합니다. 파일을 만들자마자 이름을 지우므로 서버가 중간에 죽어도 디스크에 남지 않습니다. 그 밖의 메서드는 `/dev/null`을 연결합니다.
- **출력:** 파이프로 받아 메모리에 모읍니다. 서버는 CGI의 파이프에 쓰는 일이 없으므로, 서버와 CGI가 서로의 읽기를 기다리는 교착이 생기지 않습니다.
- **환경 변수:** `REQUEST_METHOD`, `QUERY_STRING`, `SERVER_PROTOCOL`, `GATEWAY_INTERFACE`, `PATH`를 넘깁니다. POST는 `CONTENT_LENGTH`를 더하고, 요청에 `Content-Type`이 있으면 `CONTENT_TYPE`도 더합니다. 자식에서 메모리 할당을 하지 않도록 `fork` 전에 준비합니다.
- **시그널:** CGI를 별도 프로세스 그룹에서 실행해 터미널의 Ctrl+C가 CGI로 전달되지 않게 합니다. 막아 둔 시그널과 무시한 SIGPIPE는 기본값으로 되돌립니다.
- **중단:** 시간이나 크기를 넘으면 CGI의 프로세스 그룹과 CGI 자신에게 SIGKILL을 보내고 회수합니다.

| CGI의 결과 | 응답 |
| --- | --- |
| 정상 종료, 헤더와 빈 줄이 있음 | `Status` 헤더의 값, 없으면 `200` |
| 준비 실패, 실행 실패, 0이 아닌 종료, 시그널로 종료 | `500` |
| 출력이 비었음, 빈 줄이 없음, `:`이 없는 헤더 줄, 잘못된 `Status` 값, 헤더 8 KiB 초과, 출력 1 MiB 초과 | `500` |
| `Status`가 1xx(`101` 포함), `Transfer-Encoding` 헤더, 토큰이 아닌 헤더 이름, 제어 문자가 든 헤더 줄 (F8, 중계 응답과 같은 규칙) | `500` |
| `Status`가 `204` | 본문과 `Content-Length` 없이 헤더에서 끝냄. 204의 `Content-Length`는 RFC가 금지함 (F8, RFC 9110 8.6) |
| `Status`가 `304` | 본문과 `Content-Length` 없이 헤더에서 끝냄 (F8). 서버가 쓰는 길이는 실제 본문 길이(0)인데, 304의 `Content-Length`는 같은 요청에 200을 보냈을 때의 길이여야 하므로 0은 틀린 값임. 그래서 선택이 아니라 필수로 뺌 (RFC 9110 8.6). 중계는 백엔드가 준 값을 그대로 전달하므로 304의 길이를 남김: 304에서만 CGI와 중계 규칙이 다름 |
| 10초 안에 끝나지 않음 | `504` |

`Content-Length`와 `Connection`은 CGI가 준 값을 쓰지 않고 서버가 직접 정합니다. `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Upgrade` 같은 홉 단위 헤더도 뺍니다 (F8). 응답 길이를 서버가 세므로 CGI 응답 뒤에도 연결을 유지할 수 있습니다.

### 5.5 Reverse Proxy (M6)

#### 라우팅

규칙은 `접두사=백엔드,백엔드` 형식입니다. `?` 앞의 경로가 접두사로 시작하고 그다음 글자가 `/`이거나 경로의 끝이면 맞는 것으로 봅니다. 여러 규칙에 맞으면 가장 긴 접두사를 씁니다. 경로와 쿼리는 바꾸지 않고 백엔드에 그대로 보냅니다.

| 규칙 | 맞는 경로 | 맞지 않는 경로 |
| --- | --- | --- |
| `/api` 또는 `/api/` | `/api`, `/api/users`, `/api?x=1` | `/apiary`, `/a?/api` |
| `/api`, `/api/admin` | `/api/admin/x`는 `/api/admin` 규칙 사용 | |
| `/` | 모든 경로. 더 긴 규칙이 있으면 그쪽이 우선 | |

접두사 끝의 `/`는 떼고 저장합니다. 그래서 `/api/`로 설정해도 `/api` 요청이 맞고, `/api`와 `/api/`를 함께 등록하면 중복으로 거절합니다.

규칙은 시작할 때 검사합니다. 형식 오류, 잘못된 포트, 중복된 접두사, 개수 초과, 주소를 찾을 수 없는 이름, 자기 자신을 가리키는 백엔드가 있으면 이유를 출력하고 시작하지 않습니다.

#### 백엔드 선택과 연결

규칙마다 순번을 두고 요청마다 다음 백엔드부터 시도합니다(Round-Robin). 순번은 여러 작업 스레드가 함께 올리므로 C11 atomic을 씁니다.

| 상황 | 처리 |
| --- | --- |
| 연결 거부, 도달 불가, 연결 3초 초과 | 다음 백엔드 시도. 백엔드마다 한 번씩 |
| 모든 백엔드 연결 실패 | 시간 초과가 하나라도 있으면 `504`, 없으면 `502` |
| 연결부터 최종 응답 헤더까지의 마감 초과 | `504` |
| 소켓을 열 수 없음 (fd 부족) | 바로 `502` |
| 요청을 보내다 실패, 응답 전에 끊김, 응답 형식 오류 | `502` |

다음 백엔드로 넘어가는 것은 연결에 실패했을 때뿐입니다. 이때는 요청을 한 바이트도 보내지 않았으므로 POST가 두 번 처리될 위험이 없습니다.

#### 백엔드로 보내는 요청

백엔드에는 HTTP/1.0으로 요청하고 요청마다 새 연결을 맺습니다. HTTP/1.0 요청에는 chunked로 응답할 수 없으므로 백엔드 응답의 chunked 해석이 필요 없습니다.

```text
클라이언트가 보낸 요청                  백엔드로 보내는 요청
GET /api/users?id=1 HTTP/1.1            GET /api/users?id=1 HTTP/1.0
Host: example.com                       X-End: 1
Connection: keep-alive, X-Hop           Host: example.com
X-Hop: 1                                X-Forwarded-For: 203.0.113.7
X-End: 1                                Via: 1.1 tiny
X-Forwarded-For: 1.2.3.4                Connection: close
```

| 처리 | 헤더 |
| --- | --- |
| 뺌 | `Connection`과 그 값에 적힌 헤더, `Keep-Alive`, `Proxy-Connection`, `TE`, `Transfer-Encoding`, `Upgrade`, `Proxy-Authorization`, `Trailer`, `Expect`, 클라이언트가 보낸 `X-Forwarded-For` |
| 다시 씀 | `Host`(클라이언트 값 그대로. HTTP/1.0 요청에 없으면 만들지 않음), `Content-Length`(실제 본문 길이) |
| 더함 | `X-Forwarded-For`(클라이언트 IP), `Via`(클라이언트가 보낸 HTTP 버전과 `tiny`), `Connection: close` |
| 그대로 전달 | 그 밖의 헤더 |

#### 응답 전달

백엔드 응답의 헤더를 8 KiB까지 모아 확인한 뒤, 상태 줄을 `HTTP/1.1`로 바꾸고 홉 단위 헤더를 빼서 보냅니다. 본문은 모으지 않고 받는 대로 전달하므로 큰 응답도 일정한 메모리로 처리합니다.

| 백엔드 응답 | 클라이언트로 보내는 본문 | 클라이언트 연결 |
| --- | --- | --- |
| `Content-Length` 있음 | 그 길이만큼. 더 온 데이터는 버림 | 유지 |
| `Content-Length` 없음 | 백엔드가 닫을 때까지 | 닫음 |
| `204` (HEAD 요청이어도) | 없음. `Content-Length`도 보내지 않음. HEAD 규칙보다 우선 (RFC 9110 8.6) | 유지 |
| HEAD 응답(`204` 제외), `304` | 없음. 백엔드가 준 `Content-Length`가 있으면 전달하고, 없으면 만들지 않음 | 유지 |
| `100`, `103` 등 중간 응답 | 전달하지 않고 다음 응답을 읽음 | |
| `101`, `Transfer-Encoding`, 형식 오류, 서로 다른 길이 | `502`로 바꿈 | 유지 |

`유지`는 [5.6](#56-응답과-연결-유지-m5-m7)의 조건도 만족할 때를 뜻합니다.

본문을 보내는 도중에는 이미 상태 줄이 나가서 `502`로 바꿀 수 없습니다. 이때는 클라이언트가 응답이 잘렸다는 사실을 알 수 있게 닫습니다. 길이를 알린 응답은 그냥 닫아도 부족한 것을 알 수 있고, 길이가 없는 응답은 FIN으로 닫으면 정상 완료로 보이므로 RST로 닫습니다.

### 5.6 응답과 연결 유지 (M5, M7)

정적 파일, CGI, 오류 응답은 `HTTP/1.1` 상태 줄과 `Content-Length`, `Connection`을 포함합니다. 중계한 응답에는 백엔드가 길이를 준 경우에만 `Content-Length`를 넣으며, 세부 규칙은 5.5의 표를 따릅니다.

연결은 요청을 끝까지 읽었고 응답 길이를 알면 유지하고, 아니면 닫습니다. 길이를 정할 필요가 없는 본문 없는 응답은 길이를 아는 것으로 봅니다.

| 조건 | 연결 |
| --- | --- |
| HTTP/1.1이고 `Connection: close`가 없음 | 유지 |
| HTTP/1.0이고 `Connection: keep-alive`가 있음 | 유지 |
| `403`, `404`, `405`, CGI의 `500`·`504`, 중계의 `502`·`504` | 유지 |
| 요청 줄과 헤더 검사의 오류 | 닫음 |
| 길이를 모르는 중계 응답 | 닫음 |
| 연결의 요청 수가 `--keepalive-max`에 도달 | 닫음 |
| 종료가 시작됨 | 닫음 |
| 응답을 보내다 실패 | 닫음 |

닫기로 정한 응답에는 `Connection: close`를 넣습니다.

응답한 뒤 바로 닫으면, 서버가 읽지 않은 데이터가 남아 있을 때 FIN 대신 RST가 나가 클라이언트가 응답을 받지 못할 수 있습니다. 그래서 먼저 쓰기 방향만 닫아 응답이 끝났음을 알리고, 클라이언트가 닫을 때까지 최대 1초, 1 MiB까지 남은 데이터를 읽어 버린 뒤 닫습니다. 응답 없이 끝내는 연결은 이 과정을 거치지 않습니다. 정적 파일, CGI, 오류 응답은 전송에 실패해 닫을 때도 이 과정을 거칠 수 있고, 중계 응답은 전송에 실패하면 바로 닫습니다.

요청마다 메서드, URI, 버전, 상태 코드를 한 줄 로그로 남깁니다. 중계한 요청에는 연결한 백엔드 주소를 붙여 Round-Robin을 확인할 수 있습니다. 응답 없이 끝난 연결 중 요청을 다 읽지 못한 경우에는 로그를 남기지 않습니다.

```text
GET /home.html HTTP/1.1 200
GET /api/users HTTP/1.1 200 -> 127.0.0.1:8001
GET /api/users HTTP/1.1 200 -> 127.0.0.1:8002
```

### 5.7 종료 (M7)

SIGINT나 SIGTERM을 받으면 새 연결을 받지 않고, 처리 중인 요청과 작업 큐에 남은 연결의 첫 요청까지 응답한 뒤 종료합니다. 종료 시그널이 다시 오면 즉시 종료합니다.

```text
[시그널 스레드]  sigwait로 첫 번째 시그널 수신
                  → 종료 표시 → 종료 파이프에 1바이트 → 작업 큐 종료
                  → 두 번째 시그널이 오면 _exit(1)

[main 스레드]    종료 파이프를 보고 accept 중단 → 리스닝 소켓 닫기
                  → 작업 스레드가 모두 끝날 때까지 기다림
                  → 시그널 스레드를 깨워 끝냄 → 자원 해제 → 종료 코드 0

[작업 스레드]    처리 중인 요청을 마치고 Connection: close로 응답
                  → 작업 큐에 남은 연결의 첫 요청 처리 → 종료
                  연결 유지로 쉬던 연결은 종료 파이프를 보고 바로 닫음
```

스레드마다 기다리는 곳이 달라 깨우는 방법도 다릅니다. `poll`에서 기다리는 스레드는 종료 파이프가, 작업 큐에서 기다리는 스레드는 조건 변수가 깨웁니다. 종료 파이프의 1바이트는 아무도 읽지 않으므로 여러 스레드가 같은 알림을 볼 수 있습니다.

종료 알림과 소켓이 동시에 준비되면 스레드에 따라 순서가 다릅니다. main 스레드는 종료 알림을 먼저 보고 새 연결을 받지 않습니다. 작업 스레드는 이미 도착한 요청을 먼저 처리하고, 도착한 데이터가 없는 연결만 바로 닫습니다.

SIGPIPE는 무시합니다. 이미 끊긴 클라이언트에 데이터를 쓰면 기본 동작으로는 서버 전체가 종료되지만, 무시하면 쓰기 실패로 처리해 그 연결만 정리할 수 있습니다.

## 6. 응답 코드와 시간·크기 제한

### 6.1 응답 코드

| 코드 | 상황 | 연결 |
| --- | --- | --- |
| `100` | 본문이 있는 요청이 `Expect: 100-continue`를 보냄 | 계속 |
| `200` | 정적 파일, CGI 성공 | 유지 |
| `400` | 요청 줄·헤더 형식, `Host`, `Content-Length` 오류, 줄 중간에 끊김 | 닫음 |
| `403` | 허용하지 않는 경로, 폴더, 권한 없는 파일 | 유지 |
| `404` | 파일이 없음 | 유지 |
| `405` | 대상이 허용하지 않는 메서드. `Allow` 포함 | 유지 |
| `413` | 본문이 1 MiB 초과 | 닫음 |
| `414` | 요청 줄이 너무 김 | 닫음 |
| `417` | 지원하지 않는 `Expect` 값 | 닫음 |
| `500` | 정적 파일 준비 실패, CGI 실패 | 유지 |
| `500` | 본문 메모리 할당 실패 | 닫음 |
| `501` | 지원하지 않는 메서드, `Transfer-Encoding` | 닫음 |
| `502` | 백엔드에 연결하지 못함, 백엔드의 잘못된 응답 | 유지 |
| `504` | CGI 또는 백엔드의 시간 초과 | 유지 |
| `505` | 지원하지 않는 HTTP 버전 | 닫음 |
| 없음 | 줄과 줄 사이나 본문에서 끊김, 요청을 받다가 시간 초과, 중계 본문 전달 중 실패 | 닫음 |

`유지`는 5.6의 조건도 만족할 때를 뜻합니다. CGI와 중계 응답은 CGI나 백엔드가 준 상태 코드를 그대로 전달할 수도 있습니다.

### 6.2 시간 제한

| 구간 | 값 | 조절 방법 |
| --- | --- | --- |
| 첫 바이트와 연결 유지 중 다음 요청 대기 | 5초 | `--timeout` |
| 요청을 읽는 중 새 데이터가 없음 | 5초 | `--timeout` |
| 첫 바이트부터 헤더 끝까지 (마감) | 10초 | `--timeout`의 2배 |
| 요청 본문 전체 (마감) | 30초 | `--timeout`의 6배 |
| 클라이언트에 쓰기 한 번 | 10초 | `--timeout`의 2배 |
| CGI 실행 전체 (마감) | 10초 | 고정 |
| 백엔드 하나에 연결 | 3초, 남은 마감이 더 짧으면 그 시간 | 고정 |
| 백엔드 연결 시작부터 최종 응답 헤더까지 (마감) | 10초 | `--proxy-timeout` |
| 백엔드 본문의 새 데이터가 없음 | 10초 | `--proxy-timeout` |
| 응답 뒤 닫기 전에 남은 데이터 비우기 | 1초 | 고정 |

### 6.3 크기 제한

| 대상 | 값 |
| --- | --- |
| 요청 줄, 헤더 한 줄 | 각각 8,191바이트 |
| 요청 헤더 전체 | 8 KiB |
| 요청 본문 | 1 MiB |
| CGI 출력 (헤더 포함) | 1 MiB |
| 백엔드 응답 헤더 | 8 KiB |
| 라우팅 규칙, 규칙당 백엔드 | 16개, 8개 |

요청 본문과 CGI 출력에 쓰는 메모리는 작업 스레드 16개가 모두 상한을 채워도 최대 약 32 MiB입니다.

## 7. 주요 설계 결정

결정마다 비교한 방법과 선택한 이유를 적습니다. `근거 기록`은 자세한 비교가 남아 있는 문서의 항목입니다.

### 1. 실패는 그 요청에서 멈춘다

| 방법 | 결과 |
| --- | --- |
| CS:APP의 대문자 함수 사용 | 코드가 짧지만 함수 하나가 실패하면 서버 프로세스가 종료됨 |
| 반환값을 직접 확인 (선택) | 확인 코드가 늘지만 실패한 요청만 끝낼 수 있음 |

클라이언트 한 명의 문제로 다른 모두가 접속하지 못하는 일을 막기 위해 요청 처리 경로에서는 반환값을 확인합니다. 포트를 열지 못하는 것처럼 서버를 시작할 수 없는 오류만 프로세스를 종료합니다. `근거 기록: phase1 설계 선택 1`

### 2. 스레드 풀

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 멀티프로세스 | 요청끼리 격리됨 | 연결마다 프로세스를 만드는 비용이 큼 |
| 연결마다 스레드 | 구현이 짧음 | 연결 수만큼 스레드가 늘어남 |
| 스레드 풀 (선택) | 스레드 수가 고정되고 순차 코드를 그대로 씀 | 쉬는 연결도 작업 스레드 하나를 차지함 |
| 이벤트 루프 | 연결이 아주 많을 때 유리함 | 읽기, 쓰기, CGI 대기를 모두 상태 기반으로 다시 짜야 함 |

과제가 권장하는 방식이고, pthread는 Linux와 macOS에서 같은 코드로 동작합니다. 쉬는 연결의 단점은 타임아웃, 마감, 연결당 요청 수 상한으로 줄입니다.

아래는 시간 제한이 묶인 작업 스레드를 풀어 주는지 확인한 실험입니다. M4를 설계할 때 WSL에서 작업 스레드 16개를 모두 채운 뒤 새 정적 요청을 보낸 결과이며, 최종 코드의 측정값은 아닙니다.

| 작업 스레드를 채운 상황 | 제한 없음 | 제한 적용 |
| --- | --- | --- |
| 아무것도 보내지 않는 연결 | 9초 동안 응답 없음 | 4.89초 뒤 `200` |
| 다운로드를 멈춘 연결 | 45초 동안 응답 없음 | 29.5초 뒤 `200` |
| 끝나지 않는 CGI | 45초 동안 응답 없음 | 9초 뒤 `200` |

`근거 기록: m4m5 2.1, 2.4`

### 3. 작업 큐가 가득 차면 기다린다

`503`을 보내고 닫는 방법과 비교했습니다. 처리량은 작업 스레드 수가 정하므로 거절한다고 더 빨라지지 않습니다. 잠깐 몰린 연결도 기다리면 모두 처리할 수 있어 main 스레드가 기다리는 방식을 골랐습니다. 과부하가 계속되는 환경이라면 다시 검토합니다. `근거 기록: m4m5 2.2`

### 4. CGI 입력은 임시 파일, 출력은 파이프로 모은다

| 방법 | 500·504 응답 | 연결 유지 | 교착 위험 |
| --- | --- | --- | --- |
| 입력 파이프, 출력을 소켓에 직접 | 불가 | 불가 | 있음 |
| 입력과 출력 모두 파이프 | 가능 | 가능 | 입력과 출력이 모두 클 때 있음 |
| 입력과 출력 모두 임시 파일 | 가능 | 가능 | 없음. 출력 크기를 따로 제한해야 함 |
| 입력 임시 파일, 출력 파이프 (선택) | 가능 | 가능 | 없음 |

서버가 출력만 읽으므로 교착이 생기지 않고, 출력을 메모리에 모아 크기를 제한할 수 있습니다. CGI가 실패했는데 `200`이 나가는 Tiny의 문제도 함께 해결됩니다. 당시 WSL에서 1 MiB 입력으로 비교한 실험에서 임시 파일(중간값 1.9 ms)은 파이프(2.1~2.7 ms)보다 느리지 않았습니다. `근거 기록: m4m5 4.2, 4.3`

### 5. 연결 유지 규칙을 하나로 통일한다

정적 파일 성공만 유지하는 방법과 오류 응답까지 모두 유지하는 방법을 비교했습니다. 요청을 끝까지 읽었고 응답 길이를 아는지만 확인하면 모든 응답에 같은 규칙을 적용할 수 있습니다. 본문 길이가 잘못된 요청 뒤에 연결을 유지해 다음 요청의 시작을 잘못 읽는 일도 막습니다. `근거 기록: m4m5 5.2`

### 6. Reverse Proxy를 서버 안의 라우팅 단계로 둔다

Forward Proxy는 클라이언트를 대신해 바깥 서버에 요청하고, Reverse Proxy는 백엔드를 대신해 클라이언트의 요청을 받습니다. Reverse Proxy를 고른 이유는 백엔드를 직접 띄워 실패 상황까지 확인할 수 있고, 권장 요구사항인 Round-Robin으로 이어지기 때문입니다.

별도 프로그램으로 나누는 대신 기존 서버에 라우팅 단계를 넣어 스레드 풀, 요청 해석, 연결 유지 코드를 그대로 씁니다. 정적 요청이 프록시를 한 번 더 거치지도 않습니다. `근거 기록: m6m7 M6-1, M6-2`

### 7. 백엔드에는 HTTP/1.0으로 요청한다

| 방법 | 특징 |
| --- | --- |
| 클라이언트의 버전 그대로 | 요청마다 백엔드의 동작이 달라짐 |
| HTTP/1.1 고정 | 백엔드가 chunked로 응답할 수 있어 해석 코드가 필요함 |
| HTTP/1.0 고정 (선택) | chunked 응답이 오지 않고 요청마다 연결을 닫는 방식과 맞음 |

RFC 9112 6.1은 HTTP/1.1보다 낮은 버전의 요청에 `Transfer-Encoding`으로 응답하지 못하게 합니다. 클라이언트에게는 서버의 버전인 HTTP/1.1로 응답합니다. `근거 기록: m6m7 M6-9, M6-11`

### 8. 중계 응답은 헤더를 확인한 뒤 본문을 바로 전달한다

응답 전체를 모으면 실패할 때 항상 오류 응답을 보낼 수 있지만, 응답 크기만큼 메모리가 필요하고 큰 파일을 전달하지 못합니다. 헤더만 모아 확인하면 백엔드가 꺼졌거나 응답하지 않는 대부분의 실패를 `502`와 `504`로 알릴 수 있고 본문의 메모리 사용량은 일정합니다.

본문 도중의 실패는 curl로 확인해 처리 방법을 정했습니다. 길이가 없는 응답이 FIN으로 끊기면 curl이 성공으로 판단하기 때문에 RST로 닫습니다.

| 본문 도중 끊긴 응답 | FIN으로 닫음 | RST로 닫음 |
| --- | --- | --- |
| 길이 있음 | curl 오류 18 | curl 오류 56 |
| 길이 없음 | curl 성공 (잘린 것을 모름) | curl 오류 56 |

`근거 기록: m6m7 M6-11 ~ M6-13`

### 9. 연결 실패에만 다른 백엔드를 시도한다

재시도하지 않으면 백엔드 2대 중 1대가 꺼졌을 때 요청의 절반이 실패합니다. 반대로 요청을 보낸 뒤에도 재시도하면 같은 POST가 두 번 처리될 수 있습니다. 연결 단계의 실패는 요청을 보내지 않은 상태라 안전하게 재시도할 수 있습니다. 여러 백엔드를 시도해도 전체 시간은 처음 정한 마감을 넘지 않습니다. `근거 기록: m6m7 M6-14, M6-15`

### 10. 요청을 읽는 단계마다 마감을 둔다

타임아웃만 쓰면 조금씩 계속 보내는 연결을 막지 못하고, 헤더에만 마감을 두면 같은 공격을 본문으로 옮길 수 있습니다. 헤더와 본문에 각각 마감을 두고 `poll`로 기다립니다. `poll`을 쓰면서 쉬는 연결이 종료 파이프를 함께 볼 수 있게 되어 종료도 빨라졌습니다. `근거 기록: m6m7 M7-4`

### 11. 시그널 전용 스레드로 종료한다

시그널 핸들러는 아무 스레드에서나 실행되고 mutex를 쓸 수 없어 작업 큐를 안전하게 깨우지 못합니다. 종료 시그널을 모든 스레드에서 막고 전용 스레드가 `sigwait`로 받으면 일반 코드처럼 락을 쓸 수 있습니다. Linux와 macOS에서 같은 방식으로 동작합니다.

두 번째 종료 시그널은 종류와 상관없이 즉시 종료합니다. 정상 종료가 길어질 때 사용할 방법을 하나의 규칙으로 정했습니다. `근거 기록: m6m7 M7-5 ~ M7-8`

### 12. 경로가 잘못되면 고치지 않고 거절한다

`/static/../api`를 정리해서 처리하면 서버가 정리한 경로와 백엔드에 보낸 경로가 달라질 수 있습니다. 정상 클라이언트는 이런 경로를 거의 보내지 않으므로 라우팅 전에 `403`으로 거절합니다. `근거 기록: m6m7 M6-7`

### 13. CS:APP 코드는 필요한 부분만 남긴다

`csapp.c`를 모두 빼려면 부분 쓰기, 연결 끊김 같은 경계 상황을 다시 검증해야 합니다. 현재 서버는 `rio_writen`과 공통 상수만 쓰며, 실패하면 프로세스를 종료하는 대문자 함수는 쓰지 않습니다. 세마포어는 macOS에서 지원하지 않아 mutex와 조건 변수를 사용합니다. `근거 기록: 팀 회의 결정`

| M7 | 두 번째 종료 시그널에 즉시 종료 | 확인 |

M1의 재시작과 M2의 이미지, 폴더·권한 `403`은 서버를 실행해 직접 확인했고, 나머지는 자동 테스트에 들어 있습니다. 재시작은 CGI가 실행 중일 때 서버를 강제로 종료한 뒤 같은 포트로 다시 실행해 확인했습니다.

## 10. 한계와 남은 일

### 10.1 설계에서 선택한 한계

| 영역 | 한계 | 다시 검토할 조건 |
| --- | --- | --- |
| 동시성 | 연결이 작업 스레드 수보다 많으면 기다립니다. 계속 요청하는 연결은 최대 100건까지 작업 스레드를 차지합니다. | 부하 측정에서 대기가 길면 이벤트 루프나 부하에 따른 연결 유지 중단을 검토 |
| 동시성 | 스레드 하나의 메모리 오류가 서버 전체에 영향을 줍니다. | Sanitizer로 예방 |
| 과부하 | 작업 큐가 가득 차면 기다리기만 합니다. | 과부하가 계속되는 환경이면 `503` 검토 |
| 요청 | HTTP/1.1 수신자는 chunked를 해석해야 하지만(RFC 9112 7.1), 이 구현은 chunked 요청을 `501`로 거절합니다. | chunked로 보내는 클라이언트를 지원해야 할 때 |
| 요청 | 절대 URI와 `%` 인코딩 해석을 지원하지 않습니다. | 해당 클라이언트를 지원해야 할 때 |
| 요청 | 본문을 30초 안에 보내지 못하는 느린 업로드도 끊깁니다. | 정상 업로드가 끊기면 마감을 조정 |
| 응답 | 쓰기 제한은 `write` 한 번 기준이라 조금씩 계속 받는 클라이언트는 막지 못합니다. | 느린 수신자가 문제가 되면 쓰기 마감 추가 |
| 파일 | 심볼릭 링크가 루트 밖을 가리키는 것은 막지 않습니다. | 루트에 외부 링크를 두지 않는 것으로 관리 |
| CGI | 본문과 출력은 1 MiB까지입니다. 클라이언트가 끊겨도 CGI가 끝나거나 10초가 지날 때까지 작업 스레드가 기다립니다. | 큰 파일 처리가 필요할 때 |
| CGI | 서버가 강제 종료되면 실행 중인 CGI가 남을 수 있습니다. | 실제로 문제가 될 때 |
| 프록시 | 프록시가 멈추면 모든 백엔드에 접근할 수 없습니다. | 다중화가 필요할 때 |
| 프록시 | 백엔드 상태를 미리 확인하지 않아 꺼진 백엔드에도 연결을 시도합니다. | 응답 지연이 커지면 상태 확인 추가 |
| 프록시 | 요청마다 새 연결을 맺어 `TIME_WAIT`가 쌓이고, GET·POST·HEAD만 중계합니다. | 부하 측정 결과에 따라 |
| 프록시 | 백엔드의 주소는 다시 시작해야 갱신됩니다. 다른 프록시를 거쳐 돌아오는 요청은 감지하지 못합니다. | 운영 환경에 맞춰 |
| 프록시 | 길이 없는 응답을 보내던 백엔드 프로세스가 죽으면 완료된 응답과 구분할 수 없습니다. | 백엔드가 길이를 보내도록 구성 |
| 종료 | 정상 종료의 전체 시간에는 상한이 없습니다. 첫 요청을 보내지 않은 연결은 타임아웃(5초)까지 기다립니다. | 두 번째 종료 시그널로 즉시 종료 가능 |
| 종료 | SIGHUP에는 정리 없이 끝납니다. 작업 큐에 넣지 못한 연결은 응답 없이 끊깁니다. | 운영 환경에 맞춰 |
