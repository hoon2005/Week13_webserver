# 요약: 현재 상태와 선택한 것

## 과제 요구사항 대비 현재 상태

| 과제 항목 | 현재 | 담당 |
| --- | --- | --- |
| TCP 소켓 (socket → bind → listen → accept) | 완료 | M1 |
| 요청 라인 파싱 | 완료 | M2 |
| 헤더 파싱 (`Host`, `Content-Length`, `Connection`) | 읽고 버리기만 함 | M5 |
| 메서드 GET, POST | GET만. POST는 `501` | M5 |
| 응답 상태 줄 `HTTP/1.1 200 OK` | `HTTP/1.0` | M5 |
| keep-alive | 없음 | M5 |
| MIME (HTML, CSS, JS, PNG, JPG) | CSS, JS 없음 | M5 |
| 404 / 403 / 500 | 404, 403 완료. 500은 정적 파일만 (CGI 실패는 못 보냄) | M5 |
| 동적 요청 (CGI) | GET만 완료 | POST는 M5 |
| 동시 요청 처리 | 없음 (한 명씩) | **M4** |
| 동시성 모델 트레이드오프, C10K | 이 문서에서 정리 | **M4** |

## 선택한 것

| 주제 | 선택 | 한 줄 이유 |
| --- | --- | --- |
| **M4** 동시성 모델 | 스레드 풀. **시간 여유가 되면 이벤트 루프(I/O 멀티플렉싱)로 결정하면 좋겠음** | 과제 권장, 지금 blocking 코드 재사용. 이벤트 루프는 keep-alive와 많은 연결(C10K)에 더 강하지만 non-blocking으로 전부 다시 짜야 해서 일정상 다음 단계로. 코치님도 시간 여유가 있으면 I/O 멀티플렉싱도 해 보라고 함 |
| **M4** 큐가 가득 찼을 때 | main이 기다림 (새 연결은 커널 대기열에서 대기) | 우리 부하는 동시 수가 정해진 테스트라 줄이 끝없이 길어지지 않음. 503은 기다리면 처리될 요청까지 실패시킴 |
| **M4** 풀·큐 크기, 타임아웃 | 실행 인자로 받음 (기본: 작업자 8, 큐 64, 읽기 5초, 쓰기 10초) | 과제가 CLI 설정을 요구. CPU보다 기다리는 시간이 길어 코어 수보다 많아도 됨 |
| **M4** 타임아웃 | 읽기 + 쓰기 둘 다, 나면 응답 없이 닫기 | 접속만 하고 요청을 안 보내는 손님, keep-alive 대기 정리 |
| **M4** 공유 자원 | 작업 큐 하나를 mutex + condition variable로 보호 | 실제로 같이 바꾸는 변수는 큐뿐 |
| **M4** CGI | fork 전에 envp를 만들고 자식은 dup2, execve만 | 지금 코드의 fork 후 `setenv`는 스레드 환경에서 자식이 멈출 수 있음 |
| **M4** 종료 처리 | 시그널 전용 스레드(`sigwait`) + `pthread_join`, 마지막 단계(M4-3)로 | 시그널이 아무 스레드에나 갈 수 있고, 핸들러 안에서는 mutex를 못 씀 |
| **M5** 헤더 | Host, Content-Length, Connection + Content-Type, Transfer-Encoding, Expect | 과제 명시 3개 + 본문 처리에 필요한 3개. 나머지는 읽고 버림 |
| **M5** 본문 끝 판단 | `Content-Length`만 | 과제 중점 포인트가 "Content-Length 기반 본문 길이 처리" |
| **M5** chunked | `501`. CL과 같이 오면 `400` + 연결 닫기 | 범위 제한. 같이 오면 request smuggling 위험 |
| **M5** 본문 저장 | malloc 버퍼에 다 읽음 (상한 1 MiB) → CGI에 pipe로 | 큰 본문 엣지 케이스를 막는 것은 스트리밍이 아니라 상한 |
| **M5** `Expect: 100-continue` | 답함 (`100 Continue` 또는 바로 오류) | 단순하고, 큰 본문을 받기 전에 `413`으로 거절 가능. 무시하면 curl이 1초씩 기다림 |
| **M5** 본문 오류 | 없음 `411`, 잘못된 값 `400`, 너무 큼 `413`, chunked `501`, 모르는 Expect `417` | 404/403/500은 이미 있음. POST 본문 처리와 엣지 케이스("잘못된 HTTP 요청", "매우 큰 요청 본문")에 답하려고 추가. 꼭 구분할 것은 `400`, `413`이고 나머지는 원인을 정확히 알리려고 나눔 |
| **M5** 메서드 | GET, POST, **HEAD** (HEAD는 정적 파일만, CGI에 HEAD는 `501`). 그 외는 `501` | HEAD는 본문 없이 정보만 받는 용도이고 GET에서 본문만 빼면 됨. PATCH, DELETE는 파일 서버가 직접 처리할 일이 아님. 프록시에서는 그대로 전달 |
| **M5** keep-alive 닫는 시점 | idle 타임아웃(M4의 읽기 타임아웃 5초) + 연결당 요청 수 상한 100 (실행 인자로 변경 가능) | 타임아웃은 놀고 있는 연결을, 요청 수 상한은 쉬지 않고 요청하는 한 손님의 작업자 독점을 막음. 둘 다 구현이 작음. 연결 수명 상한은 요청 수 상한과 효과가 겹쳐 생략, 바쁠 때 닫기는 여유 있으면 확장 |
| **M5** 응답 형식 | 상태 줄 `HTTP/1.1`. 모든 응답(오류 포함)에 `Content-Length`와 `Connection` | 과제가 `HTTP/1.1 200 OK`를 명시. keep-alive에서는 클라이언트가 응답 끝을 알아야 다음 요청을 보낼 수 있음 (지금 오류 응답에는 Content-Length가 없음) |
| **M5** CGI 응답 구조 | CGI 출력을 파이프로 받아 끝까지 모은 뒤 서버가 응답을 만듦 (출력 상한 1 MiB). 실패하면 `500`, 시간 초과면 CGI를 끝내고 `504` | 지금은 200을 fork 전에 보내서 CGI가 실패해도 500을 못 보내고, CGI가 소켓에 직접 써서 응답 길이를 몰라 keep-alive도 안 됨. 모아서 확인한 뒤 보내면 둘 다 해결. 요청 본문의 버퍼링 + 상한과 같은 생각 |
| **M5** MIME | HTML, CSS, JS, PNG, JPG (+ 기존 GIF). 표에 없으면 `text/plain` | 과제 명시 목록. 지금 `FILE_TYPES` 표에 CSS(`text/css`), JS(`text/javascript`)를 한 줄씩 추가 |

# 고민한 흔적

### POST 본문의 끝을 어떻게 알까?

- **선택지:** `Content-Length`(본문 바이트 수가 헤더에 있음, 가장 흔함) / `Transfer-Encoding: chunked`(`크기\r\n데이터\r\n` 반복, 크기 0이면 끝. 보내는 쪽이 전체 길이를 모를 때) / 연결이 끊길 때까지(요청에는 못 씀. 끊으면 응답을 보낼 수 없어서 HTTP/1.0 응답에서만 쓰임).
- **정리:** 과제 헤더 파싱 항목과 중점 포인트 모두 Content-Length 기반이라 Content-Length를 지원합니다.
- **chunked를 같이 다루며 알게 된 것:** CL과 TE가 같이 오면 서버마다 본문 끝을 다르게 판단할 수 있고, 공격자가 그 틈으로 요청 하나 안에 다른 요청을 몰래 끼워 넣을 수 있습니다(request smuggling). chunked는 지원하지 않지만, 둘이 같이 오면 거절합니다.

### Expect는 왜 넣나?

- 큰 본문을 다 보냈는데 서버가 거절하면(`413`) 전송이 낭비라서, 클라이언트가 헤더만 먼저 보내고 서버가 괜찮다고 하면 본문을 보내는 방식입니다. 흐름: 헤더 → `HTTP/1.1 100 Continue` → 본문 → 진짜 응답.
- **두 가지 중:** 100 Continue를 보낸다 / 무시한다(curl이 약 1초 기다린 뒤 그냥 보냄, 동작은 하지만 느림).
- **선택:** 100 Continue를 보낸다. 그나마 단순하고, 상한과 같이 쓰면 큰 본문을 받기도 전에 거절할 수 있습니다.

### 큰 본문에는 스트리밍이 낫지 않나?

- **처음 생각:** 스트리밍은 본문이 커도 메모리를 조금만 쓰니, "매우 큰 요청 본문" 엣지 케이스에는 스트리밍이 좋지 않을까?
- **정리:** 엣지 케이스를 막는 것은 스트리밍이 아니라 **상한**입니다. 과제가 보려는 것은 "엄청 큰 본문이 와도 서버가 죽거나 메모리가 바닥나지 않는가"입니다.
  - 버퍼링 + 상한: Content-Length를 먼저 보고 상한보다 크면 malloc 전에 `413`. 메모리를 아예 쓰지 않습니다. 스레드 풀이면 최대 메모리도 계산됩니다(상한 × 작업자 수).
  - 스트리밍: 메모리는 적게 쓰지만 그래도 상한이 필요합니다. 없으면 10GB를 받는 동안 작업자 하나가 계속 묶이고 CGI도 오래 돕니다. 코드도 복잡하고, CGI가 입력을 안 읽으면 파이프가 차서 교착이 생길 수 있습니다.
- 스트리밍과 버퍼링은 TCP/UDP와 관계없습니다. 둘 다 TCP가 정확히 넘겨준 바이트를 받은 뒤 언제, 얼마나 모아서 넘기느냐의 차이입니다.

### GET, POST 말고 다른 메서드는?

- HEAD, PUT, DELETE, PATCH, OPTIONS, CONNECT, TRACE가 있습니다. 더 추가한다면 **HEAD**.
- **궁금증:** HEAD와 GET이 서버 입장에서 같다면, 본문까지 주는 GET 하나면 되지 않나?
- **정리:** 서버 입장에서는 거의 같지만 클라이언트 입장에서는 용도가 다릅니다. HEAD는 본문 없이 정보만 받고 싶을 때 씁니다(파일 크기, 바뀌었는지 확인, 링크가 살아 있는지, 디버깅). 본문만큼의 전송을 아끼는 것이 목적입니다.
- PATCH, DELETE는 우리 서버가 다루는 리소스가 디스크의 파일이라, 직접 처리하면 누구나 파일을 고치거나 지울 수 있게 됩니다. 보통 백엔드가 처리하는 메서드라 쓰지 않습니다.

### 500은 구현되어 있나?

- 404(파일 없음), 403(읽기 권한 없음, 폴더 요청), 500(정적 파일 열기 실패)은 구현되어 있습니다.
- **문제:** `cgi_serve`가 `200 OK`를 fork 전에 먼저 보내서, CGI가 실패해도 클라이언트는 200인데 본문이 빈 응답을 받습니다. 제대로 500을 보내려면 CGI 출력을 파이프로 받아 다 확인한 뒤 응답을 보내는 구조로 바꿔야 합니다(M5).

### keep-alive는 무엇이고 왜 요구하나?

- 응답을 보낸 뒤에도 연결을 끊지 않고, 같은 연결에서 다음 요청을 기다리는 것입니다(요청 → 응답 → 연결 유지 → 반복). 서버(프로세스)는 어느 경우에도 종료되지 않고, 닫히는 것은 그 클라이언트의 연결뿐입니다.
- HTTP/1.1에서는 연결 유지가 기본값이라, 과제가 `HTTP/1.1` 응답을 요구하는 만큼 keep-alive를 다뤄야 합니다.

### 동시성 모델: 왜 이벤트 루프가 아니라 스레드 풀인가?

| | 멀티프로세스 | 스레드 풀 | 이벤트 루프 |
| --- | --- | --- | --- |
| 메모리 | 가장 무거움 | 스레드마다 스택 | 가장 가벼움 |
| 격리 | 한 요청이 죽어도 무사 | 서버 전체가 죽음 | 서버 전체가 죽음 |
| 공유 데이터 | 안 나눠 씀 | 나눠 씀 → 락 | 락 거의 없음 |
| 느린 클라이언트 | 프로세스 하나 묶임 | 스레드 하나 묶임 | 안 묶임 |
| 동시 연결 한계 | 수백 | 풀 크기 | 수만 (C10K) |
| 코드 변경 | 작음 | 작음~중간 | 큼 |

- **고민:** 메모리로 봤을 땐 이벤트 루프가 좋은 것 같은데.. 왜 권장을 하지 않을까? 과제 권장 사항으로는 스레드 풀을 권장했다.
- **고민:** 과제 권장 사항이 스레드 풀인데, 왜 스레드 풀이 적합하고 권장하는 걸까??
- **C10K 문제:** 연결을 1만 개 동시에 유지한다면 문제다. 프로세스나 스레드는 연결 하나당 실행 단위라서 1만 개면 메모리와 문맥 전환 비용이 감당되지 않는다. 이벤트 루프가 버티는 건 연결이 많아도 실제로 데이터가 온 연결만 처리하기 때문이다.
- 현재 과제 요구사항에서는 HTTP/1.1을 다루기에 keep-alive를 요구하는 것인데…
- **근데 제 생각인데, 과제에선 스레드 풀을 권장하는데 사실 keep-alive를 잘 다루는 건 이벤트 루프가 아닌가?** 응답 후에도 계속 연결되어 있고, 다음 요청을 기다리는 동안 스레드 하나가 계속 붙잡힌다. (작업자가 8개인데 놀고 있는 keep-alive 연결이 8개면 새 클라이언트는 큐에서 기다려야 됨) 약간의 함정이라 생각함.
- 스레드 풀로 하게 되면 스레드 하나가 붙잡혀서 묶이게 되는데, 이벤트 루프의 문제는 성능이 아니라 구현과 일정이다. 지금 코드가 블로킹 방식이라서 소켓을 논블로킹으로 바꿔야 되는 대참사가 벌어짐. 그리고 CGI도 잘 맞지 않는데, CGI 출력 파이프도 이벤트로 관리해야 돼서 문제.
- 그래도 **스레드 풀로 한다면 타임아웃과 큐 상한을 걸어서 버틴다. 그냥 과제 규모상으로 봤을 때 스레드 풀을 권장하는 듯… (코치님이 시간 여유 있으니 I/O 멀티플렉싱도 하라고 했다는 피셜이 있음)**
- **= 본인도 가급적이면 이벤트 루프로 결정하면 좋겠음**

### 큐가 가득 차면 어떻게 할까?

- **선택지:** main이 기다림(단순, 새 연결은 커널 listen 대기열에 쌓임) / `503` 후 닫기(클라이언트가 바로 바쁨을 앎, 코드가 늘어남) / 그냥 닫기(최악).
- **처음 선택:** `503` 후 닫기. 바로바로 다음을 처리할 수 있으니 효율적이고, main이 기다리면 뒤에 있는 것도 다 멈춰야 한다고 생각했습니다.
- **정리:**
  - main이 기다리는 동안 멈추는 것은 새 연결을 꺼내는 일(accept)뿐입니다. 작업자는 계속 처리하고, 새 연결은 사라지지 않고 커널 대기열(backlog)에 줄을 섭니다. 작업자가 비면 → 큐에 자리 → main이 깨어나 accept → 대기열 순서대로 처리. 즉 멈추는 게 아니라 **줄이 길어지고, 늦게라도 응답을 받습니다.**
  - 처리량은 작업자 수가 정하므로 503이 더 효율적인 것은 아닙니다. 두 방식의 차이는 넘친 손님을 어떻게 대하느냐입니다. 계속 과부하면 503이 낫고, 잠깐 몰렸을 때는 몇 ms만 기다리면 처리될 손님도 거절되는 게 503의 문제입니다.
  - 우리 부하는 동시 수가 정해진 테스트라 줄이 끝없이 길어지지 않고, 서버가 느릴수록 503은 실패만 늘립니다. 그래서 **main 기다림으로 바꿨습니다.**

### 경쟁 상태와 mutex

- 경쟁 상태: 여러 스레드가 같은 변수를 동시에 건드려서 실행 순서에 따라 결과가 달라지는 것. 생기는 조건은 ① 같은 메모리를 씀 ② 하나 이상이 값을 바꿈 ③ 그 작업이 한 번에 끝나지 않음(`count++`는 읽기 → 더하기 → 쓰기).
- mutex: 임계 구역에 한 번에 한 스레드만 들어가게 하는 자물쇠.
- 우리 서버: 작업자 A, B가 mutex 없이 동시에 큐에서 꺼내면 같은 connfd를 두 번 처리하거나 연결이 사라질 수 있습니다. 그래서 넣기와 꺼내기를 모두 mutex로 감쌉니다.

### 프로세스와 스레드의 메모리 차이

- 프로세스: 각자 자기 메모리 공간을 따로 가집니다. fork하면 통째로 복사됩니다(실제로는 쓸 때 복사, Copy-on-Write).
- 스레드: 한 프로세스 안에서 코드, 전역 변수, 힙, 파일 디스크립터 표를 같이 쓰고 스택만 따로 가집니다.
- 그래서 우리 서버에서 `doit`의 지역 변수는 스레드마다 따로라 안전하고, 실제로 공유해서 바꾸는 것은 작업 큐 하나입니다.

### 풀 크기, 큐 크기, 타임아웃

- 풀·큐 크기: 고정값 / CPU 코어 수 기반 / 실행 인자 중에서, 과제가 CLI 설정을 요구하므로 **실행 인자**로 받습니다. 지금은 CPU 계산보다 기다리는 시간이 많아 코어 수보다 많아도 됩니다.
- 읽기 타임아웃(`SO_RCVTIMEO`): 접속만 하고 요청을 안 보내는 클라이언트를 끊습니다. keep-alive에 필수입니다. 한 글자도 안 보냈을 때와 보내다 멈췄을 때 모두 응답 없이 닫습니다(후자는 `408`도 가능).
- 쓰기 타임아웃(`SO_SNDTIMEO`): 응답을 아주 느리게 받아 가는 클라이언트도 스레드를 붙잡습니다. 드물지만 필요합니다. 상대가 안 읽어서 나는 것이라 그냥 닫습니다.

### 종료 처리 (SIGINT / SIGTERM)

- 시그널은 운영체제가 실행 중인 프로세스에 보내는 짧은 알림입니다. SIGINT(Ctrl+C)와 SIGTERM(`kill`)은 둘 다 종료 요청이고, 기본 동작은 즉시 종료라 처리 중이던 요청이 잘릴 수 있습니다.
- 안전한 셧다운: accept 중단 → 작업자에게 종료 알림 → 처리 중인 요청 마무리 → `pthread_join`(특정 스레드가 끝날 때까지 기다렸다가 자원 회수) → 자원 해제.
- **고민:** 시그널이 아무 스레드에나 전달될 수 있다면 아예 따로 빼는 게 맞지 않나?
- **정리:** 맞습니다. **시그널을 받는 스레드를 따로 하나 둡니다.** 다른 스레드를 만들기 전에 SIGINT, SIGTERM을 막아 두고, 전용 스레드가 `sigwait`로 받습니다. 범위로는 스레드 풀 구조에 의존하므로 M4의 마지막 단계로 합니다.

## 목표와 범위

지금 서버는 `accept` → `doit` → `close`를 한 연결씩 차례로 합니다. 그래서 한 손님이 접속만 하고 요청을 보내지 않으면 `doit` 안의 `rio_readlineb`에서 멈추고, 그동안 다른 손님은 아무도 응답을 받지 못합니다 (M4 질문 1).

목표 달성 기준은 다음과 같습니다.

- 터미널 A에서 `nc localhost 8000`으로 연결만 걸어 둔 상태에서, 터미널 B의 `curl`이 바로 응답을 받습니다.
- 동시에 보낸 요청 여러 개(정적 파일, CGI 섞어서)가 모두 정상 응답을 받습니다.
- 요청을 보내지 않는 연결은 읽기 타임아웃 뒤 서버가 닫습니다.
- 작업 큐의 단위 테스트가 `make tsan`(ThreadSanitizer)에서 경고 없이 통과하고, CI에서 돌아갑니다.
- 기존 기능 테스트(`make verify`)가 그대로 통과합니다.
- 단일 스레드 대비 처리량을 부하 테스트로 측정해 `docs/measurements/`에 남깁니다.

단계는 셋으로 나눕니다.

| 단계 | 내용 |
| --- | --- |
| M4-1 | 연결 하나 = 스레드 하나 (`pthread_create` + `pthread_detach`) |
| M4-2 | 스레드 풀 + 작업 큐, 읽기·쓰기 타임아웃, 실행 인자, CGI의 fork 후 `setenv` 수정 |
| M4-3 | 종료 처리: 시그널 전용 스레드 + `pthread_join` |

이번 범위에 넣지 않는 것입니다.

| 항목 | 이유 |
| --- | --- |
| 이벤트 루프 | 지금 코드를 non-blocking 상태 머신으로 다시 짜야 함. 아래 설계 선택 1 |
| 큐가 가득 찼을 때 503 | 우리 부하는 동시 수가 정해진 테스트라 기다림으로 충분. 아래 설계 선택 3 |
| 요청 전체 시간 제한 (Slowloris 대응) | `SO_RCVTIMEO`는 read 한 번 기준이라 못 막음. 한계로 남김. 아래 설계 선택 5 |
| keep-alive | M5. 다만 keep-alive 연결이 작업자를 붙잡는 문제는 이 문서의 타임아웃이 전제 조건임 |

## 설계 선택

### 1. 동시성 모델

| | 멀티프로세스 (`fork`) | 스레드 풀 (`pthread`) | 이벤트 루프 (`poll`/`epoll`/`kqueue`) |
| --- | --- | --- | --- |
| 방식 | 연결마다 자식 프로세스 | 미리 만든 N개 스레드가 큐에서 연결을 꺼내 처리 | 스레드 하나가 여러 연결 중 준비된 것만 골라 처리 |
| 메모리 | 프로세스마다 주소 공간 → 가장 무거움 | 스레드마다 스택 | 연결마다 상태 구조체 → 가장 가벼움 |
| 격리 | 한 요청이 죽어도 다른 요청은 무사 | 한 스레드가 메모리를 망가뜨리면 서버 전체가 죽음 | 마찬가지 |
| 공유 데이터 | 기본적으로 따로 → 단순 | 힙과 전역을 같이 씀 → 락 필요 | 스레드 하나라 락이 거의 없음 |
| 느린 연결, keep-alive | 프로세스 하나가 묶임 | **스레드 하나가 묶임** | 묶이지 않음 |
| 동시 연결 한계 | 수백 | 풀 크기 | 수만 (C10K) |
| 지금 코드에서 바꿀 양 | 작음 | 작음 | **큼** |

**추천은 스레드 풀입니다.**

- 과제가 "요청 처리 스레드 풀 권장"이라고 적었고, 팀 마일스톤도 "스레드 하나씩 → 스레드 풀" 순서입니다.
- 지금의 blocking 코드(`rio_readlineb` 등)를 그대로 쓸 수 있습니다. 이벤트 루프는 "요청 줄을 반만 읽음", "본문 200/700바이트 받음" 같은 상태를 연결마다 저장하는 구조로 M2와 M5 코드를 모두 다시 짜야 합니다. CGI를 `waitpid`로 기다리는 부분도 이벤트로 바꿔야 합니다.
- 스레드 수가 N개로 고정되어, 손님이 몰려도 스레드가 끝없이 늘지 않습니다. 연결마다 스레드를 만들고 없애는 비용도 없습니다.

**한계도 분명합니다.** 놀고 있는 연결(접속만 한 손님, keep-alive 대기)도 작업자 하나를 붙잡습니다. 이 약점을 가장 잘 해결하는 것은 이벤트 루프입니다. 스레드 풀에서는 읽기 타임아웃(설계 선택 5)으로 버팁니다. 우리 테스트는 수십~수백 연결 수준이라 이것으로 충분하다고 봅니다.

### 2. 1단계: 연결 하나 = 스레드 하나

스레드 풀 전에 가장 단순한 형태로 동시 처리를 먼저 확인합니다.

```c
while (1) {
    int *connfdp = malloc(sizeof(int));   /* 연결마다 따로 */
    *connfdp = accept(listenfd, ...);
    pthread_create(&tid, NULL, conn_thread, connfdp);
}

void *conn_thread(void *arg) {
    int connfd = *(int *)arg;
    free(arg);
    pthread_detach(pthread_self());       /* 끝나면 알아서 회수 */
    doit(connfd);
    close(connfd);
    return NULL;
}
```

- `&connfd`(main의 지역 변수 주소)를 넘기면, 스레드가 값을 읽기 전에 main이 다음 `accept`로 덮어쓸 수 있습니다. 그래서 연결마다 따로 `malloc`해서 넘기고, 스레드가 읽은 뒤 `free`합니다.
- 스레드를 기다리는 쪽이 없으므로 `pthread_detach`로 끝나면 알아서 회수되게 합니다. 하지 않으면 끝난 스레드의 자원이 남습니다.
- 이 단계는 동시 처리 확인용이고, 손님 수만큼 스레드가 생기므로 M4-2에서 스레드 풀로 바꿉니다.

### 3. 스레드 풀 구조와 큐가 가득 찼을 때

```text
main 스레드:   accept → 큐에 connfd 넣기 (가득 찼으면 자리가 날 때까지 기다림) → 반복
작업자 N개:    큐에서 connfd 꺼내기 (비었으면 들어올 때까지 기다림) → doit → close → 반복
```

작업 큐는 고정 크기 원형 버퍼 하나와 mutex 하나, condition variable 두 개(`not_empty`, `not_full`)로 만듭니다.

- **mutex가 필요한 이유:** main은 넣고 작업자들은 꺼내므로 `head`, `tail`, `count`를 여러 스레드가 동시에 바꿉니다. 락이 없으면 두 작업자가 같은 connfd를 꺼내거나 연결 하나가 사라질 수 있습니다 (M4 질문 4).
- **condition variable:** 큐가 비었을 때 작업자가 헛돌지 않고 잠들었다가, main이 넣으면 깹니다. 깨어나면 `while`로 조건을 다시 확인합니다. 다른 작업자가 먼저 꺼내 갔거나, 이유 없이 깨는 경우(spurious wakeup)가 있기 때문입니다.
- **락은 큐를 만지는 순간만 잡습니다.** `doit`을 락 안에서 부르면 한 번에 한 요청만 처리되어 스레드 풀의 의미가 없어집니다.
- **큐를 별도 모듈로 둡니다** (`src/conn_queue.c`). 지금 `make tsan`은 단위 테스트만 TSan으로 빌드합니다. 그래서 큐를 `tiny.c` 밖으로 빼고, 여러 스레드가 동시에 넣고 꺼내는 단위 테스트(`tests/conn_queue_test.c`)를 만들어야 TSan이 실제로 큐를 검사합니다.

**큐가 가득 차면 main이 기다립니다.**

| | main 기다림 | 503 후 닫기 |
| --- | --- | --- |
| 넘친 손님 | 커널 listen 대기열(backlog, `LISTENQ`)에서 기다렸다가 늦게라도 응답을 받음 | 바로 실패를 받음 |
| 잠깐 몰린 경우 | 모두 처리됨 | 조금만 기다리면 처리될 손님도 거절됨 |
| 계속 과부하인 경우 | 줄이 길어져 결국 타임아웃 | 받은 손님의 응답 시간을 지킴 |
| 구현 | `pthread_cond_wait` 하나 | 503 작성, 쓰기 타임아웃, 읽지 않은 요청 때문에 RST가 나지 않게 `shutdown` 후 읽고 버리기 |

main이 기다리는 동안 멈추는 것은 새 연결을 꺼내는 일뿐입니다. 작업자는 계속 처리하고, 새 연결은 커널 대기열에 줄을 섭니다. 우리 부하는 `ab -c 100`, `wrk -c 100`처럼 **동시 수가 정해진 테스트**라 줄이 끝없이 길어지지 않습니다. 503 방식이면 서버가 느릴 때 기다리면 처리될 요청까지 실패로 집계되어 부하 테스트 결과가 왜곡됩니다. 503의 장점은 처리량이 아니라 과부하 때 응답 시간을 지키고 빨리 실패를 알리는 것인데, 우리 상황에서는 필요성이 낮습니다.

### 4. 풀 크기, 큐 크기, 타임아웃 값

과제가 설정을 CLI 인자로 받으라고 하므로 실행 인자로 받고, 없으면 기본값을 씁니다. 포트는 지금처럼 첫 번째 인자로 두어 기존 기능 테스트가 그대로 동작하게 합니다.

```text
./build/tiny <port> [--threads N] [--queue N] [--timeout 초]
```

| 값 | 기본값 | 근거 |
| --- | --- | --- |
| 작업자 수 | 8 | 우리 서버는 CPU 계산보다 기다리는 시간(네트워크, 디스크, CGI)이 길어 코어 수보다 많아도 됨. 최종 값은 부하 테스트로 정함 |
| 큐 크기 | 64 | 큐가 "얼마나 기다리게 할지"의 한도. 넘치면 커널 대기열로 넘어감 |
| 읽기 타임아웃 | 5초 | 접속만 한 손님, keep-alive 대기 정리. Apache keep-alive 기본값과 같음 |
| 쓰기 타임아웃 | 10초 | 큰 파일 전송 여유 |

### 5. 타임아웃

`accept`로 받은 소켓에 `setsockopt`로 `SO_RCVTIMEO`(읽기)와 `SO_SNDTIMEO`(쓰기)를 겁니다.

| | 막는 상황 | 났을 때 |
| --- | --- | --- |
| 읽기 타임아웃 | 접속만 하고 요청을 안 보냄, keep-alive 대기, 요청을 아주 천천히 보냄 | 응답 없이 닫음 |
| 쓰기 타임아웃 | 응답을 아주 천천히 받아 감 | 응답을 보낼 수 없으므로 닫음 |

지금 코드는 이미 이렇게 동작합니다. 타임아웃이 나면 `read`가 -1(`EAGAIN`)을 돌려주고, `rio_readlineb`도 -1을 돌려주며, `request_line_read`와 `request_headers_skip`은 -1이면 응답 없이 요청을 끝냅니다. `setsockopt`만 추가하면 됩니다. 요청을 보내다 멈춘 경우 `408 Request Timeout`을 보낼 수도 있지만, 한 글자도 안 보낸 경우와 구분해야 해서 이번에는 똑같이 닫습니다.

**한계:** `SO_RCVTIMEO`는 `read` 한 번마다 걸리는 시간입니다. 4초마다 한 글자씩 보내면 read가 매번 성공해서 타임아웃이 나지 않고, 작업자 하나를 아주 오래 붙잡을 수 있습니다(Slowloris). 막으려면 "요청 시작부터 N초 안에 헤더 끝"처럼 전체 시간을 따로 재야 합니다. 이번에는 한계로 남깁니다.

### 6. 스레드 안전성

스레드는 코드, 전역 변수, 힙, 파일 디스크립터 표, 환경 변수를 같이 쓰고, 스택(지역 변수)만 따로 가집니다 (M4 질문 2). 지금 코드에서 무엇이 공유되는지 정리하면 다음과 같습니다.

| 코드 | 위치 | 판단 |
| --- | --- | --- |
| `doit`의 `buf`, `rio`, `filename` 등 | 스택 | 안전. 스레드마다 따로 있음 |
| `FILE_TYPES` 표 | 전역 | 안전. 읽기만 함 |
| M5의 본문 버퍼 | 힙 | 안전. 그 요청을 맡은 스레드만 포인터를 가짐 |
| **작업 큐** | 힙 | **mutex 필요.** 실제로 공유해서 바꾸는 것은 사실상 이것 하나 |
| **CGI 자식의 `setenv`** | 환경 변수 | **수정 필요.** 아래 |
| `printf` 로그 | 공용 stdout | 깨지지는 않지만 스레드끼리 줄이 섞일 수 있음. 동작에는 문제없음 |

**fork 후 `setenv` 문제 (지금 코드에 있는 버그):** `cgi_child_run`은 fork한 자식에서 `setenv`를 부릅니다. 스레드가 여럿인 프로세스에서 fork하면 자식에는 fork를 부른 스레드 하나만 복사됩니다. 그 순간 다른 스레드가 malloc 내부 락을 잡고 있었다면, 자식에서 그 락은 영원히 잠긴 채 남습니다. `setenv`는 내부에서 malloc을 쓰므로 자식이 멈출 수 있습니다. fork와 exec 사이에서는 async-signal-safe 함수만 써야 합니다.

- **수정:** fork 전에 부모가 환경 변수 배열(`QUERY_STRING=1&2` 등)을 만들어 두고, 자식은 `dup2` → `execve(filename, argv, envp)`만 합니다. M5의 `CONTENT_LENGTH`, `REQUEST_METHOD`도 같은 방식으로 넘깁니다.
- **`waitpid(pid)`는 유지합니다.** `wait(NULL)`로 바꾸면 다른 스레드의 CGI 자식을 대신 회수해 버립니다.

### 7. 종료 처리 (SIGINT / SIGTERM)

SIGINT(Ctrl+C)와 SIGTERM(`kill`, `docker stop`)의 기본 동작은 즉시 종료라 처리 중이던 응답이 중간에 잘립니다. 스레드가 있으면 시그널이 아무 스레드에나 전달될 수 있고, 시그널 핸들러 안에서는 mutex 같은 함수를 쓸 수 없습니다.

**시그널 전용 스레드를 둡니다.**

1. 다른 스레드를 만들기 전에 main에서 `pthread_sigmask`로 SIGINT, SIGTERM을 막습니다. 이후 만드는 스레드는 이 설정을 물려받아 시그널을 받지 않습니다.
2. 시그널 전용 스레드 하나가 `sigwait`로 기다립니다. 시그널은 항상 이 스레드만 받고, 평범한 코드로 처리할 수 있습니다.
3. 시그널이 오면: 종료 플래그 설정 → main의 accept 중단 → `pthread_cond_broadcast`로 작업자를 모두 깨움 → 작업자는 큐에 남은 연결까지 처리하고 끝남 → main이 `pthread_join`으로 모두 기다림 → 큐 해제 → 종료.

- **accept에서 멈춘 main을 깨우는 방법은 OS마다 다릅니다.** Linux는 `shutdown(listenfd)`로 깨어나지만 macOS에서는 보장되지 않습니다. 그래서 main이 `poll`로 listen 소켓과 종료 알림용 pipe를 같이 기다리게 하는 방식을 제안합니다. 구현할 때 두 OS에서 확인합니다.
- 작업자가 놀고 있는 연결에서 read로 기다리는 중이어도, 읽기 타임아웃(5초) 안에 끝나므로 종료가 무한히 늦어지지 않습니다.
- 스레드 풀 구조(작업자를 깨우고 join하기)에 의존하므로 M4-3으로 마지막에 합니다.

### 선택을 다시 검토할 조건

- **시간 여유가 되면 이벤트 루프(I/O 멀티플렉싱)로 넘어가는 것을 목표로 합니다.** keep-alive와 많은 연결에 더 강하고, 스레드 풀과 부하 테스트로 비교하면 트레이드오프를 숫자로 설명할 수 있습니다. 동시 연결 수가 풀 크기를 크게 넘어 응답 시간이 타임아웃 수준까지 늘어나는 경우에도 이벤트 루프로 갑니다.
- 실제 외부 트래픽처럼 손님이 멈추지 않고 몰려오는 상황을 다뤄야 하면, 큐가 가득 찼을 때 503(부하 차단)으로 바꿉니다.
- Slowloris처럼 아주 느린 요청이 실제 문제가 되면 요청 전체 시간 제한을 추가합니다.

## 요청 흐름

```text
[main]        listen_socket_open → 시그널 막기 → 작업자 N개, 시그널 스레드 생성
              → 반복: accept → 소켓에 읽기/쓰기 타임아웃 설정
                     → 큐에 connfd 넣기 (가득 찼으면 기다림)

[작업자 1..N]  반복: 큐에서 connfd 꺼내기 (비었으면 기다림)
                     → doit(connfd)  (지금 코드 그대로)
                       CGI면: fork 전에 envp 만들기 → fork → 자식은 dup2, execve
                              → 부모 작업자는 waitpid(pid)
                     → close(connfd)

[시그널 스레드] sigwait → 종료 플래그 → main과 작업자 깨우기

[종료]        main이 작업자 join → 큐 해제 → exit
```

예: 손님 A가 `nc`로 연결만 걸고, 손님 B가 `curl /home.html`을 보냅니다.

1. main이 A를 accept해서 큐에 넣고, 작업자 1이 꺼내 `rio_readlineb`에서 기다립니다.
2. main은 바로 다음 accept로 B를 받아 큐에 넣고, 작업자 2가 꺼내 `200`과 `home.html`을 보냅니다.
3. A가 5초 동안 아무것도 보내지 않으면 작업자 1의 read가 타임아웃으로 -1을 돌려주고, 연결을 닫고 큐로 돌아갑니다.

# M5 헤더 파싱과 요청 본문 처리

> M5 중 **헤더 파싱**과 **요청 본문(POST) 읽기**를 다룹니다. 본문의 끝은 `Content-Length`로 판단하고, 본문은 상한을 둔 메모리 버퍼에 모두 읽습니다. `Expect: 100-continue`를 처리해서 큰 본문은 받기 전에 거절합니다.

회의에서 정할 질문

1. 어떤 헤더를 꺼내 저장하고, 어떤 헤더는 읽고 버릴까?
2. 본문의 끝은 무엇으로 판단할까? (`Content-Length` / `Transfer-Encoding: chunked`)
3. 본문은 다 모은 뒤 처리할까(버퍼링), 읽으면서 바로 넘길까(스트리밍)?
4. `Expect: 100-continue`에 답할까, 무시할까?

## 목표와 범위

지금 서버는 헤더를 빈 줄까지 읽고 버리기만 합니다(`request_headers_skip`). 그래서 본문이 있는 요청(POST)을 처리할 수 없고, keep-alive에서 다음 요청이 어디서 시작하는지도 알 수 없습니다.

이번 범위에서 할 일은 다음과 같습니다.

- 헤더 줄을 `이름: 값`으로 나눠 필요한 값을 요청 구조체에 저장합니다.
- `Content-Length`만큼 본문을 정확히 읽습니다. 상한을 넘는 본문은 읽지 않고 거절합니다.
- `Expect: 100-continue`가 오면 본문을 받기 전에 `100 Continue` 또는 오류로 답합니다.
- 잘못된 헤더와 본문에 맞는 오류 응답을 보내고, 서버는 계속 동작합니다.

목표 달성 기준은 다음과 같습니다.

- `curl -d "a=1&b=2"` 요청의 본문 7바이트가 CGI 프로그램에 그대로 전달됩니다.
- 상한을 넘는 본문은 본문 전송 전에 `413`으로 거절됩니다.
- 아래 [오류 응답](#오류-응답) 표의 요청마다 기대한 상태 코드가 오고, 다음 요청에도 정상 응답합니다.
- 파서 단위 테스트 `tests/http_test.c`가 통과합니다.

이번 범위에 넣지 않는 것입니다.

| 항목 | 처리 | 이유 |
| --- | --- | --- |
| `Transfer-Encoding: chunked` 해석 | `501` | 과제 문구가 "`Content-Length` 기반 본문 길이 처리". `curl -d`와 HTML form은 Content-Length로 보냄. 여유가 있으면 확장 (아래 [다시 검토할 조건](#다시-검토할-조건)) |
| 본문 스트리밍 | 버퍼링만 | 이번 POST는 form 데이터 수준. 아래 설계 선택 3 |
| CGI 출력 스트리밍 | 버퍼링만 | 우리 CGI(adder) 출력은 수백 바이트. 아래 설계 선택 6 |
| `Host` 기반 라우팅 | 저장과 검사만 | Proxy 단계에서 씀 |

## 설계 선택

### 1. 어떤 헤더를 꺼낼까?

HTTP 헤더는 종류가 정해져 있지 않고 클라이언트가 상황에 따라 골라 보냅니다. 서버는 **필요한 헤더만 꺼내고 나머지는 읽고 버립니다.** 모르는 헤더는 무시하는 것이 HTTP 규칙입니다. 헤더 이름은 대소문자를 구분하지 않으므로 `strcasecmp`로 비교하고, 값 앞뒤의 공백은 잘라냅니다.

| 헤더 | 저장할 값 | 쓰는 곳 |
| --- | --- | --- |
| `Host` | 문자열 | HTTP/1.1인데 없으면 `400`. 지금은 검사만 하고 Proxy에서 백엔드를 고를 때 씀 |
| `Content-Length` | 0 이상의 정수, 있었는지 여부 | 본문을 몇 바이트 읽을지 |
| `Connection` | `close` / `keep-alive` / 없음 | 응답 후 연결을 닫을지. 없으면 HTTP/1.1은 유지, HTTP/1.0은 닫음 |
| `Content-Type` | 문자열 | 서버는 해석하지 않고 CGI에 `CONTENT_TYPE`으로 넘김 |
| `Transfer-Encoding` | 있었는지 여부 | 있으면 거절 |
| `Expect` | `100-continue` / 그 외 / 없음 | 본문을 받기 전에 답할지 |

요청 구조체 예시는 다음과 같습니다. 파서는 소켓을 모르고 문자열만 받아 이 구조체를 채우게 해서, 단위 테스트에서 소켓 없이 검증할 수 있게 합니다.

```c
struct http_request {
    char method[16], uri[MAXLINE], version[16];
    char host[256];
    char content_type[256];
    long content_length;     /* has_content_length가 0이면 의미 없음 */
    int  has_content_length;
    int  has_transfer_encoding;
    int  expect_continue;    /* Expect: 100-continue */
    int  keep_alive;         /* 버전과 Connection 헤더로 결정 */
    char *body;              /* malloc. 요청이 끝나면 free */
};
```

### 2. 본문의 끝은 무엇으로 판단할까?

TCP는 바이트가 끊김 없이 이어지는 흐름이라, 본문이 어디서 끝나는지를 HTTP가 따로 알려 줘야 합니다.

| 방식 | 설명 | 결정 |
| --- | --- | --- |
| `Content-Length: n` | 정확히 n바이트가 본문 | **지원** |
| `Transfer-Encoding: chunked` | `크기\r\n데이터\r\n` 반복, 크기 0이면 끝 | 이번엔 `501` |
| 연결 끊김까지 | 상대가 닫으면 끝 | 요청에는 쓸 수 없음 (끊으면 응답을 못 보냄) |

**`Content-Length`와 `Transfer-Encoding`이 같이 오면 `400`을 보내고 연결을 닫습니다.** 서버마다 다른 쪽을 믿으면 본문이 끝나는 위치를 서로 다르게 판단하게 됩니다. 그러면 남은 바이트가 같은 연결의 "다음 요청"으로 처리되는 request smuggling이 생길 수 있습니다. 지금은 서버 한 대라 다음 요청이 꼬이는 버그 수준이지만, Reverse Proxy와 keep-alive를 같이 만들면 보안 문제가 됩니다.

`Content-Length`가 여러 번 오는데 값이 서로 다르거나, 숫자가 아니거나, 음수이면 `400`을 보냅니다.

### 3. 본문은 버퍼링할까, 스트리밍할까?

둘 다 TCP 위에서 받은 같은 바이트를 다루며 정확도는 같습니다. 차이는 받은 바이트를 **언제, 얼마나 모아서 넘기는지**입니다.

| | 버퍼링 | 스트리밍 |
| --- | --- | --- |
| 방식 | Content-Length만큼 `malloc`해서 다 읽은 뒤 CGI에 넘김 | 조금 읽을 때마다 바로 CGI 파이프에 씀 |
| 메모리 | 본문 크기만큼 | 작은 고정 버퍼 |
| 구현 | 단순. 파서와 처리부가 분리되어 단위 테스트가 쉬움 | 읽기와 쓰기가 섞이고, 중간 실패 처리가 복잡 |
| 큰 본문 | 상한으로 거절 | 받을 수는 있지만 작업자 스레드가 그동안 묶임. 결국 상한이 필요 |

**추천은 버퍼링 + 상한입니다.** "매우 큰 요청 본문" 엣지 케이스를 막는 것은 스트리밍이 아니라 **상한**입니다. 헤더에서 `Content-Length`를 먼저 확인하고, 상한을 넘으면 `malloc`하기 전에 `413`을 보냅니다. 상한보다 큰 본문에는 메모리를 쓰지 않습니다.

- **상한 값:** `BODY_MAX = 1 MiB` (1,048,576바이트)를 제안합니다. form 데이터에는 충분히 큽니다.
- **최대 메모리:** M4에서 스레드 풀을 쓰면 본문 버퍼 최대 메모리는 `BODY_MAX × 작업자 수`로 계산됩니다 (예: 1 MiB × 8 = 8 MiB).
- **해제:** 본문 버퍼는 응답 후, 그리고 중간에 실패해서 요청을 끝낼 때 모두 `free`합니다. ASan으로 누수를 확인합니다.

### 4. `Expect: 100-continue`에 답할까?

curl은 POST 본문이 일정 크기(보통 1KB)를 넘으면 `Expect: 100-continue`를 붙이고, 서버가 "보내도 된다"고 답할 때까지 본문을 미룹니다.

- **무시하면:** 서버는 본문을, curl은 서버 답을 서로 기다립니다. curl이 약 1초 뒤 포기하고 본문을 보내므로 결과는 같지만 그런 요청마다 1초씩 늦어집니다. 큰 본문 테스트와 부하 테스트 숫자가 왜곡됩니다.
- **답하면:** 본문 검사(411, 413 등)를 본문을 읽기 전에 하고, 통과하면 `HTTP/1.1 100 Continue\r\n\r\n`을 보낸 뒤 본문을 읽습니다. 통과하지 못하면 `100` 없이 바로 오류를 보냅니다.

**추천은 답하는 쪽입니다.** 어차피 하려던 검사를 본문 읽기 앞으로 옮기고 분기 하나를 더하는 정도입니다. 그리고 상한을 넘는 본문을 **보내기도 전에** 거절할 수 있어서, 설계 선택 3의 상한과 잘 맞습니다.

| 조건 | 처리 |
| --- | --- |
| HTTP/1.1, `Expect: 100-continue`, 본문 검사 통과, `Content-Length > 0` | `100 Continue` 전송 후 본문 읽기 |
| `Expect: 100-continue`, 본문 검사 실패 | `100` 없이 오류 응답 후 **연결 닫기**. 클라이언트가 기다리다 본문을 보낼 수 있는데, 연결을 유지하면 그 본문이 다음 요청으로 읽힘 |
| `100-continue`가 아닌 Expect 값 | `417 Expectation Failed` |
| HTTP/1.0 요청 | Expect 무시 (100 Continue는 HTTP/1.1에만 있음) |

### 5. keep-alive: 연결을 언제 닫을까?

같은 연결에서 요청을 여러 번 처리합니다. 작업자는 연결 하나를 받아 요청 처리를 반복하고, 닫을 조건이 되면 닫습니다.

```c
rio_readinitb(&rio, connfd);   /* 연결당 한 번만 */
for (n = 1; ; n++) {
    keep = handle_request(connfd, &rio, n < KEEPALIVE_MAX);  /* 요청 하나 처리, 유지할지 돌려줌 */
    if (!keep) break;
}
close(connfd);
```

- **`rio`는 연결당 한 번만 초기화합니다.** 클라이언트가 요청을 연달아 보내면(파이프라이닝) 다음 요청 앞부분이 이미 rio 버퍼에 들어와 있을 수 있습니다. 지금은 `doit` 안에서 rio를 만들므로 바깥으로 옮깁니다.
- **다음 요청의 시작:** 요청 줄, 헤더, 빈 줄, 본문(정확히 Content-Length 바이트)을 다 읽으면 그다음 바이트가 다음 요청입니다. 설계 선택 2~3의 규칙(본문을 정확히 다 읽기, 처리하지 않는 본문도 읽고 버리기)이 그 전제입니다.

**연결을 유지할지는 요청과 서버 상황으로 정합니다.**

| 조건 | 결정 |
| --- | --- |
| HTTP/1.1, Connection 헤더 없음 또는 `keep-alive` | 유지 |
| HTTP/1.1, `Connection: close` | 응답 후 닫음 |
| HTTP/1.0, Connection 헤더 없음 | 응답 후 닫음 |
| HTTP/1.0, `Connection: keep-alive` | 유지 |
| 본문 경계를 모르는 오류 (`400`, `411`, `413`, `417`, `501`) | 응답 후 닫음 |
| CGI 응답 | 정적 파일과 같이 유지. 서버가 CGI 출력을 모아 길이를 세므로 (설계 선택 6) |
| 이 연결의 요청 수가 상한에 도달 | 응답 후 닫음 |
| 다음 요청 줄을 읽었는데 0 (클라이언트가 끊음) | 조용히 닫음 |
| 다음 요청이 타임아웃 안에 안 옴 | 조용히 닫음 |

닫기로 했으면 응답에 `Connection: close`를 넣습니다. HTTP/1.0 요청에 유지할 때는 `Connection: keep-alive`를 넣습니다.

**클라이언트가 계속 유지하려 할 때 서버가 언제 끊을지는 네 가지 방식을 비교했습니다.**

| 방식 | 막는 문제 | 구현 | 결정 |
| --- | --- | --- | --- |
| idle 타임아웃 | 놀고 있는 연결이 작업자를 붙잡음 | M4의 읽기 타임아웃 그대로 | **사용** |
| 연결당 요청 수 상한 | 쉬지 않고 요청하는 손님이 작업자를 독점 | 카운터 하나 | **사용 (100)** |
| 연결 수명 상한 | 가끔 요청해서 타임아웃에 안 걸리는 연결 | 시간 계산 | 요청 수 상한과 효과가 겹쳐 생략 |
| 바쁠 때 닫기 | 큐에 기다리는 손님이 있으면 keep-alive를 포기 | 큐 상태 확인 (락 필요) | 여유 있으면 확장 |

- **idle 타임아웃:** M4의 읽기 타임아웃(5초)을 그대로 씁니다. 첫 요청을 기다릴 때와 요청 사이를 기다릴 때를 같은 값으로 둡니다. 요청 사이만 더 짧게(예: 2초) 하면 작업자를 더 빨리 돌려받지만, 요청마다 `setsockopt`를 다시 걸어야 해서 이번에는 한 값으로 갑니다.
- **요청 수 상한:** 100은 Apache의 `MaxKeepAliveRequests` 기본값입니다. 닫히면 클라이언트가 다시 연결하면서 큐 뒤에 줄을 서므로 다른 손님에게도 차례가 갑니다. 실행 인자 `--keepalive-max N`으로 바꿀 수 있게 해서 부하 테스트로 비교합니다.
- **바쁠 때 닫기**는 스레드 풀의 약점(놀고 있는 연결이 작업자를 붙잡음)을 직접 겨냥하는 방식이라, 스레드 풀을 유지한다면 다음 확장으로 좋습니다. 이벤트 루프로 넘어가면 이 문제 자체가 사라집니다.

### 6. CGI 응답 구조

지금 구조에는 문제가 두 가지 있습니다.

```text
서버 → 소켓: "HTTP/1.0 200 OK\r\nServer: ...\r\n"   ← fork 전에 먼저 보냄
fork → 자식: dup2(소켓 → stdout) → execve(adder)
adder → 소켓: 나머지 헤더와 본문을 직접 씀
서버: waitpid → close
```

- **500을 못 보냅니다.** 200을 먼저 보내서, CGI가 실패하면 클라이언트는 200인데 본문이 빈 응답을 받습니다.
- **keep-alive를 못 합니다.** CGI가 소켓에 직접 써서 서버는 응답이 어디서 끝나는지 모릅니다.

| 방식 | CGI 실패 시 500 | CGI keep-alive | 메모리 | 구현 |
| --- | --- | --- | --- | --- |
| A. 지금 그대로 + CGI 뒤에는 닫기 | 못 보냄 | 안 됨 | 적음 | 없음 |
| **B. 파이프로 받아 전부 모은 뒤 응답** | **보냄** | **됨** | 출력 크기 (상한) | 중간 |
| C. 파이프로 받으며 바로 보내기 (chunked 응답) | 헤더를 보낸 뒤에는 못 보냄 | 됨 | 적음 | 중간 |
| D. 일정 크기까지 모으고, 넘으면 스트리밍 | 작은 출력만 | 됨 | 상한까지 | 큼 |

**B로 합니다.** 앞에서 남겨 둔 CGI 500 문제와 keep-alive 문제가 같이 풀립니다. 요청 본문에서 고른 "버퍼링 + 상한"을 응답 쪽에도 똑같이 적용하는 것이라, 양방향 모두 "모아서 확인한 뒤 넘긴다"로 통일됩니다. 우리 CGI(adder)의 출력은 수백 바이트라 메모리 걱정도 없습니다. 나중에 Reverse Proxy에서 백엔드 응답을 다 받아 두고 보낼지 고민할 때도 이 구조를 재사용할 수 있습니다.

```text
fork 전: 입력 파이프(본문용), 출력 파이프 생성, envp 준비
자식:    dup2(입력 파이프 → stdin), dup2(출력 파이프 → stdout) → execve
부모:    입력 파이프에 본문을 쓰고 닫음 (CGI가 EOF를 알게)
         출력 파이프를 EOF까지 읽어 버퍼에 모음 (상한 1 MiB, 시간 제한 10초)
         waitpid로 종료 상태 확인
         → 정상 종료 + 출력이 올바름: 서버가 응답을 만들어 보냄
         → 그 외: 500 또는 504
```

**CGI 출력 해석 (CGI 표준):** CGI는 상태 줄 없이 `헤더 몇 줄 + 빈 줄 + 본문`을 출력합니다. 서버는 빈 줄에서 헤더와 본문을 나누고 응답을 만듭니다.

| 항목 | 처리 |
| --- | --- |
| 상태 줄 | CGI가 `Status: 404 Not Found` 헤더를 주면 그 값, 없으면 `HTTP/1.1 200 OK` |
| `Content-Type` 등 CGI 헤더 | 그대로 전달 |
| `Content-Length` | 서버가 센 본문 길이로 직접 씀 (CGI가 쓴 값은 무시) |
| `Connection` | 서버가 keep-alive 규칙(설계 선택 5)으로 직접 씀 (CGI가 쓴 값은 무시) |
| HEAD 요청 | 이번에는 CGI에 HEAD를 지원하지 않음 (`501`). 이 구조에서는 본문만 빼면 되므로 나중에 쉽게 추가 가능 |

**실패 처리:** 응답을 보내기 전에 확인하므로 모두 오류 응답을 보낼 수 있습니다.

| 상황 | 응답 |
| --- | --- |
| `execve` 실패, CGI가 0이 아닌 값으로 종료, 시그널로 죽음 | `500` |
| 출력이 비었거나 헤더와 본문을 나누는 빈 줄이 없음 | `500` |
| 출력이 상한(1 MiB)을 넘음 | CGI를 `kill`, `500` |
| 출력을 10초 안에 다 내지 않음 | CGI를 `kill`, `504 Gateway Timeout` |
| fork, pipe 실패 | `500` |

- **시간 제한:** 지금은 CGI가 끝나지 않으면 작업자가 `waitpid`에서 무한정 기다립니다. 출력 파이프를 읽을 때 시간 제한을 두고, 넘으면 `kill` 후 `waitpid`로 회수해 좀비를 남기지 않습니다. 실패(`500`)와 시간 초과(`504`)를 나누면 원인을 구분하기 쉽습니다.
- **adder 수정:** adder가 출력하는 `Connection: close`, `Content-length`는 CGI 표준상 서버가 정할 값이므로 뺍니다. `Content-type`과 본문만 출력합니다.
- **교착 한계:** 서버는 본문을 다 쓴 뒤에 출력을 읽습니다. 그런데 CGI가 입력을 다 읽기 전에 파이프 버퍼(보통 64KB)보다 많이 출력하면, 서버는 쓰기에서, CGI는 출력에서 서로 기다리는 교착이 생깁니다. adder처럼 입출력이 작으면 생기지 않습니다. 완전히 막으려면 `poll`로 두 파이프를 같이 다뤄야 하며, 이번에는 한계로 남깁니다. 시간 제한(10초)이 있어서 교착이 생겨도 작업자가 영원히 묶이지는 않습니다.

### 다시 검토할 조건

- CGI 출력이 커져서(예: 파일 다운로드를 CGI로 생성) 1 MiB 상한이 문제가 되면 C(chunked 스트리밍)나 D(섞기)를 검토합니다.
- 파일 업로드처럼 1 MiB를 넘는 본문을 **정상으로** 받아야 하면 스트리밍을 검토합니다.
- chunked로 보내는 클라이언트를 지원해야 하면 chunked 디코딩을 추가합니다. RFC 7230은 HTTP/1.1 수신자가 chunked를 해석할 수 있어야 한다(MUST)고 정하므로, 이번 `501`은 표준을 다 지킨 것이 아니라 **범위 제한**입니다. 조각을 모아 버퍼에 붙이고 모은 길이를 `CONTENT_LENGTH`로 넘기면 되므로 버퍼링 구조에 그대로 들어갑니다.

## 요청 흐름

`curl -d "a=1&b=2" http://127.0.0.1:8000/cgi-bin/adder` 요청을 예로 듭니다.

```text
요청 라인 읽기        "POST /cgi-bin/adder HTTP/1.1"
  → 메서드 확인        GET, POST 허용 (그 외 501)
  → 헤더 파싱          빈 줄까지 한 줄씩 "이름: 값"으로 나눠 구조체에 저장
                       Host=127.0.0.1:8000, Content-Length=7,
                       Content-Type=application/x-www-form-urlencoded
  → 헤더 검사          Host 없음(1.1) 400 / TE 있음 501 / CL+TE 400
                       POST인데 CL 없음 411 / CL > BODY_MAX 413 / 이상한 Expect 417
  → Expect 처리        100-continue였으면 "HTTP/1.1 100 Continue" 전송
  → 본문 읽기          같은 rio로 rio_readnb(&rio, body, 7)
                       7바이트보다 적게 오면(연결 끊김) free 후 종료
  → URI 확인, 해석, 파일 찾기, 권한 확인 (지금과 같음)
  → CGI 실행           입력·출력 파이프 생성, envp 준비
                       (REQUEST_METHOD=POST, CONTENT_LENGTH=7, CONTENT_TYPE) → fork
                       자식: 입력 파이프를 STDIN으로, 출력 파이프를 STDOUT으로 dup2 → execve
                       부모: 입력 파이프에 본문 7바이트 쓰고 닫음 (CGI가 EOF를 알게)
                             → 출력 파이프를 EOF까지 읽어 모음 → waitpid
  → 응답               CGI 출력을 헤더와 본문으로 나눔
                       "HTTP/1.1 200 OK" + Content-type + Content-Length(서버가 셈)
                       + Connection → 본문 → body와 출력 버퍼 free
```

구현할 때 주의할 점입니다.

- **본문은 반드시 헤더를 읽은 같은 `rio`로 읽습니다.** `rio_readlineb`는 소켓에서 넉넉히 읽어 두기 때문에 본문 앞부분이 이미 rio 버퍼에 있을 수 있습니다. 소켓에서 `read`를 직접 하면 그 앞부분을 잃습니다.
- **GET에 본문이 붙어 와도 읽어서 버립니다** (상한 적용). 읽지 않으면 keep-alive에서 그 본문이 다음 요청으로 읽힙니다.
- **CGI가 stdin을 읽지 않고 끝나도 서버는 멈추지 않습니다.** 부모의 파이프 쓰기가 `EPIPE`로 실패하는데, `SIGPIPE`는 이미 무시하므로 쓰기를 멈추고 출력 읽기로 넘어갑니다. 입출력이 모두 클 때의 교착은 설계 선택 6의 한계를 봅니다.
- **본문 경계를 확신할 수 없는 오류**(CL+TE, 잘못된 CL, 본문 도중 끊김, Expect 거절)는 응답 후 **연결을 닫습니다.**
- `adder`도 POST를 받도록 고칩니다. `REQUEST_METHOD`가 POST이면 stdin에서 `CONTENT_LENGTH`만큼 읽어 쿼리 문자열 대신 씁니다. 출력에서는 `Connection`, `Content-length`를 뺍니다 (서버가 정함).

### 오류 응답

과제의 기본 오류 응답(404 / 403 / 500)은 Phase 1에서 이미 구현되어 있습니다. 404는 파일 없음, 403은 읽기·실행 권한 없음, 폴더 요청, `..` 경로이고, 500은 정적 파일 열기 실패입니다. CGI 실패 때의 500은 아직 못 보냅니다. 아래는 M5에서 **POST 본문 처리와 엣지 케이스** 때문에 새로 생기는 오류 응답입니다.

| 상황 | 응답 | 연결 | 왜 (과제 항목) |
| --- | --- | --- | --- |
| 헤더 줄에 `:`가 없음, 헤더 줄이 `MAXLINE`보다 김 | `400` | 닫음 | 잘못된 HTTP 요청 (불완전한 헤더) |
| HTTP/1.1인데 `Host` 없음 | `400` | 닫음 | 잘못된 HTTP 요청. RFC 7230이 HTTP/1.1 요청에 Host를 요구 |
| `Content-Length`가 숫자가 아님, 음수, 서로 다른 값으로 여러 번 | `400` | 닫음 | 잘못된 HTTP 요청. 본문 길이를 믿을 수 없음 |
| `Content-Length`와 `Transfer-Encoding`이 같이 옴 | `400` | 닫음 | 본문 끝이 애매해 request smuggling 위험 |
| `Transfer-Encoding`만 옴 | `501` | 닫음 | chunked는 이번 범위에서 구현하지 않음 |
| POST인데 `Content-Length` 없음 | `411 Length Required` | 닫음 | Content-Length 기반 본문 처리라 길이가 없으면 읽을 수 없음 |
| `Content-Length > BODY_MAX` | `413 Payload Too Large` | 닫음 | 매우 큰 요청 본문. malloc 전에 거절 |
| `Expect` 값이 `100-continue`가 아님 | `417 Expectation Failed` | 닫음 | Expect를 처리하기로 해서 생긴 경우 |
| 본문 도중 연결 끊김 | 없음 (상대가 없음) | 닫음 | 클라이언트의 갑작스러운 연결 종료 |
| CGI 실패 (exec 실패, 비정상 종료, 출력이 깨짐, 출력 상한 초과) | `500` | 유지 | 기본 오류 응답 500. 설계 선택 6 |
| CGI가 10초 안에 출력을 끝내지 않음 | `504 Gateway Timeout` | 유지 | 응답 없는 동적 처리 |

`411`, `417`, `501`은 `400`으로 합쳐도 동작에는 문제없지만, 원인을 정확히 알리려고 나눴습니다. 꼭 구분해야 하는 것은 `400`과 `413`입니다.

## 검증 계획

**준비:** `make`로 빌드하고, `tests/fixtures/www`를 루트로 서버를 `8000`번에 띄웁니다. `cgi-bin/adder`는 POST 본문을 읽도록 고친 버전입니다.

| 요청 | 성공 조건 |
| --- | --- |
| `curl -i -d "a=1&b=2" localhost:8000/cgi-bin/adder` | `200`, 본문에 `1 + 2 = 3` |
| `curl -i 'localhost:8000/cgi-bin/adder?1&2'` | 기존 GET 결과 그대로 (회귀 없음) |
| `head -c 2000 /dev/zero \| curl -v --data-binary @- localhost:8000/cgi-bin/adder` | 로그에 `< HTTP/1.1 100 Continue`가 보이고 1초 지연 없이 응답 |
| `head -c 2000000 /dev/zero \| curl -v --data-binary @- localhost:8000/cgi-bin/adder` | 본문을 보내지 않고 바로 `413` |
| `printf 'POST /cgi-bin/adder HTTP/1.1\r\nHost: x\r\n\r\n' \| nc localhost 8000` | `411` |
| `printf 'GET / HTTP/1.1\r\n\r\n' \| nc localhost 8000` | `400` (Host 없음) |
| `printf 'POST / HTTP/1.1\r\nHost: x\r\nContent-Length: 5\r\nTransfer-Encoding: chunked\r\n\r\n' \| nc localhost 8000` | `400` 후 연결 닫힘 |
| `printf 'POST / HTTP/1.1\r\nHost: x\r\nContent-Length: abc\r\n\r\n' \| nc localhost 8000` | `400` |
| `curl -i -H "Expect: foo" -d x localhost:8000/cgi-bin/adder` | `417` |
| `printf 'POST /cgi-bin/adder HTTP/1.1\r\nHost: x\r\nContent-Length: 100\r\n\r\nab' \| nc -w1 localhost 8000` (본문 도중 끊김) | 서버가 죽지 않고, 이어서 보낸 `curl localhost:8000/` 이 `200` |

**keep-alive** (`--keepalive-max 3`으로 띄운 경우 포함)

| 요청 | 성공 조건 |
| --- | --- |
| `curl -v localhost:8000/home.html localhost:8000/home.html` | 두 번째 요청에 `Re-using existing connection` |
| `curl -v -H "Connection: close" localhost:8000/home.html` | 응답에 `Connection: close`, 연결 닫힘 |
| `curl -v --http1.0 localhost:8000/home.html` | 응답 후 연결 닫힘 |
| `printf 'GET /home.html HTTP/1.1\r\nHost: x\r\n\r\nGET /home.html HTTP/1.1\r\nHost: x\r\n\r\n' \| nc localhost 8000` | 응답 두 개가 순서대로 옴 (파이프라이닝) |
| `--keepalive-max 3`에서 같은 연결로 요청 4개 | 세 번째 응답에 `Connection: close`, 네 번째는 새 연결 |
| `nc localhost 8000`에 요청 하나 보낸 뒤 대기 | 응답 후 약 5초 뒤 서버가 연결을 닫음 |
| 잘못된 요청(예: `Content-Length: abc`) 뒤에 요청을 이어 보냄 | `400` 후 연결 닫힘, 뒤 요청은 처리되지 않음 |
| `curl -v 'localhost:8000/cgi-bin/adder?1&2' 'localhost:8000/cgi-bin/adder?3&4'` | CGI 응답에도 `Content-Length`가 있고, 두 번째에 `Re-using existing connection` |
| `ab -k -n 10000 -c 50` vs `ab -n 10000 -c 50` | keep-alive 쪽 처리량이 더 높음 (`docs/measurements/`에 기록) |

**CGI 응답 구조:** 테스트용 CGI를 `cgi-bin/`에 둡니다. `fail`은 아무것도 출력하지 않고 1로 종료하고, `nohdr`는 빈 줄 없이 본문만 출력하며, `slow`는 `sleep 30`합니다.

| 요청 | 성공 조건 |
| --- | --- |
| `curl -i localhost:8000/cgi-bin/fail` | `500` (지금은 200 + 빈 본문) |
| `curl -i localhost:8000/cgi-bin/nohdr` | `500` |
| `curl -i localhost:8000/cgi-bin/slow` | 약 10초 뒤 `504`, `ps`에 `slow`가 남지 않음 |
| `curl -i -d "a=1&b=2" localhost:8000/cgi-bin/adder` | `200`, 응답 헤더에 서버가 센 `Content-Length` 하나만 있음 |

위 요청들 뒤에 `curl localhost:8000/home.html`이 매번 `200`이면 서버가 살아 있는 것입니다. 기능 테스트는 `tests/functional/`에 같은 요청으로 추가합니다.

**단위 테스트 `tests/http_test.c`:** 파서에 문자열을 넣고 구조체 값을 확인합니다.

- 헤더 이름 대소문자 무시 (`content-length`, `CONTENT-LENGTH`)
- 값 앞뒤 공백 제거 (`Content-Length:   7  `)
- `Connection` 기본값: HTTP/1.1 → keep-alive, HTTP/1.0 → close, 명시하면 그 값
- 잘못된 `Content-Length` (`abc`, `-1`, `7` 다음 `8`) → 오류
- CL+TE, TE만, Host 없음(1.1), Host 없음(1.0은 허용)
- 모르는 헤더(`X-Foo: bar`)는 무시

**누수:** 위 요청을 모두 보낸 뒤 서버를 종료했을 때 ASan(Linux에서는 LeakSanitizer 포함)이 누수를 보고하지 않는지 확인합니다. 특히 413, 본문 도중 끊김, CGI 실패 경로에서 `body`가 해제되는지 봅니다.
