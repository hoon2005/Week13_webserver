## 0. 내 선택 요약

> **과제의 Reverse Proxy 방식에서 정적 요청은 프록시가 직접 서빙합니다.** 라우팅 규칙에 걸리지 않는 요청은 우리 서버가 정적 파일(또는 CGI)로 바로 응답합니다(4.5). 정적 경로를 백엔드로 보내고 싶으면 `--route /static=...`처럼 규칙을 주면 됩니다.

### M6 Reverse Proxy

| 항목                | 선택                                                                               | 한 줄 이유                                                          |
| ------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 프록시 종류         | **Reverse 먼저**, 시간이 남으면 Forward 추가                                       | 과제가 라우팅·Round-Robin을 구체적으로 요구하고, 로컬 테스트가 안정적 |
| 프록시 위치         | **지금 서버에 라우팅 단계 추가** (nginx 방식)                                      | 스레드 풀·keep-alive·타임아웃·오류 응답을 그대로 씀. 성능도 같거나 더 좋음 |
| 라우팅 기준         | **경로 접두사**                                                                    | 코치님 조언: URI를 자원 단위로 설계하면 라우팅이 깔끔해짐           |
| 규칙 받는 방법      | **CLI 반복 옵션 `--route`**                                                        | 지금 `args_parse` 방식 그대로, 테스트가 쉬움                         |
| 접두사 매칭         | **`/` 경계 + 가장 긴 접두사**                                                       | `/api`가 `/apiary`에 걸리지 않게                                    |
| 백엔드로 보낼 경로  | **그대로 전달** (`/api/users/3` → `/api/users/3`)                                  | 경로를 고쳐 쓰는 코드와 엣지 케이스가 없음                          |
| 안 걸리는 요청      | **지금처럼 정적 파일 / CGI**                                                       | 기존 기능 유지. 과제 R16에 "정적은 프록시가 직접 서빙"으로 답함     |
| 백엔드 주소         | **`호스트:포트`**, **서버를 켤 때 한 번 해석**                                     | 이름과 IP를 둘 다 받고, `getaddrinfo`는 표준 함수                    |
| 요청 헤더 만들기    | **원본 헤더 블록을 줄 단위로 걸러내고 필요한 줄을 추가**                          | 구조체로 다시 만들면 `Content-Type` 등 모르는 헤더가 사라짐          |
| 요청 줄 버전        | **`HTTP/1.1` 고정**                                                                | 동작이 일정하고 과제 응답 예시와 맞음                               |
| 홉 단위 헤더        | **RFC 목록 + `Connection`에 적힌 이름까지 빼고 `Connection: close` 추가**          | 백엔드가 응답 후 닫아야 EOF로 응답 끝을 앎. `Upgrade` 등도 막음      |
| Host                | **클라이언트 값 그대로**, 없으면 백엔드 주소로 추가                                | 백엔드가 tiny라 Host로 가상 호스트를 고르지 않음. 1.1은 Host 필수    |
| X-Forwarded-For     | **클라이언트 IP로 덮어쓰기**                                                       | 원래 클라이언트 IP를 알려 주고, 맨 앞 프록시라 받은 값은 믿지 않음  |
| `Expect: 100-continue` | **우리가 처리하고, 백엔드에는 빼고 보냄**                                       | 넘기면 백엔드의 `100`을 최종 응답으로 착각함                        |
| 응답 전달           | **헤더는 모아서 확인, 본문은 흘려보내기**                                          | 실패 대부분이 헤더 단계 → 깔끔한 502·504. 본문은 메모리 고정         |
| 응답의 끝           | **백엔드가 연결을 닫을 때 (EOF)**                                                  | 가장 단순하고, 요청마다 백엔드 연결을 새로 여는 것과 맞음           |
| 클라이언트 keep-alive | **백엔드 응답에 `Content-Length`가 있으면 유지, 없으면 닫기**                    | 길이가 있어야 클라이언트도 응답 끝을 앎                             |
| 응답 `Connection` 헤더 | **우리가 다시 씀**                                                              | 백엔드의 `Connection`은 프록시와 백엔드 사이의 이야기               |
| 오류 코드           | **연결 실패·이상한 응답 → 502, 시간 초과 → 504, 503은 쓰지 않음**                  | 백엔드 상태를 주기적으로 확인하지 않으므로 "전부 꺼짐"을 미리 모름  |
| 시간 제한 방식      | **`SO_RCVTIMEO` / `SO_SNDTIMEO`**                                                  | 지금 클라이언트 소켓과 같은 방식                                    |
| 재시도              | **처음에는 안 함** → 여유가 있으면 **connect 실패만** 다음 백엔드로                | connect 실패는 요청을 보내기 전이라 POST도 안전                     |
| 로드 밸런싱         | **Round-Robin + Least Connections 둘 다**                                          | 작업자가 백엔드를 기다리며 묶이므로, 느린 백엔드를 피하는 LC가 의미 있음 |

### M7 안전한 종료

큰 방향은 [bloro.md](bloro.md) 7장(final.md 2.7)에서 정한 것을 그대로 따르고, keep-alive와 M6 때문에 생긴 빈칸을 새로 정했습니다.

| 항목                     | 선택                                                                 | 한 줄 이유                                                        |
| ------------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 시그널 받기              | **`sigwait` 전용 스레드** (bloro.md)                                 | 핸들러는 아무 스레드에서나 돌고 mutex를 못 씀                     |
| main 깨우기              | **`poll`(listen 소켓 + 종료 pipe)** (bloro.md)                       | `shutdown(listenfd)`는 macOS에서 accept를 깨운다는 보장이 없음    |
| 받은 연결                | **큐에 남은 것까지 처리, 처리 중인 요청은 끝까지** (bloro.md)       | 이미 accept한 클라이언트는 응답을 받게                            |
| 정리 주체                | **시그널 스레드는 알리기만, main이 join하고 해제** (bloro.md)        | 만든 쪽이 해제해야 짝을 확인하기 쉬움                             |
| keep-alive 연결          | **종료 플래그를 보면 지금 응답에 `Connection: close`를 붙이고 닫기** | 계속 요청하는 연결이 `--keepalive-max`까지 종료를 붙잡지 않게    |
| CGI 자식                 | **`execve` 전에 시그널 마스크와 SIGPIPE를 기본값으로 되돌림**        | 막힘·무시 설정이 `execve` 뒤에도 남음                             |
| 대기 상한                | **1번째 시그널 = 안전한 종료, 2번째 = 즉시 종료** (SIGINT·SIGTERM 구분 없음) | 느린 수신자가 종료를 오래 붙잡을 때의 비상구                |
| 시그널 스레드 종료       | **main이 `pthread_kill`로 깨우고 join**                              | 모든 스레드를 join해서 끝냄                                       |
| 누수 검사                | **Linux CI에서 SIGTERM 한 번 → 종료 코드 0이면 통과** (LeakSanitizer) | 누수가 있으면 LeakSanitizer가 0이 아닌 코드로 끝냄                |
| 끊김 시 자원 회수 확인   | **강제 끊김 전후 열린 fd 수 비교 + 좀비 확인**                       | 메모리 누수 검사는 fd와 자식 프로세스를 보지 않음                 |
| 동시 다중 클라이언트     | **정적·CGI·프록시를 섞은 동시 요청 50개 기능 테스트**                | 과제 필수인데 레포에 없음                                         |

## 1. 목표와 범위

### M6 완료 기준

- `--route /api=127.0.0.1:8001,127.0.0.1:8002`로 켠 서버에 `GET /api/...`를 보내면 두 백엔드가 번갈아 응답합니다.
- `/api`에 걸리지 않는 요청(`/home.html`, `/cgi-bin/adder?1&2`)은 지금처럼 우리 서버가 응답합니다.
- 백엔드를 끄면 `502`, 응답하지 않는 백엔드면 약 10초 뒤 `504`를 받습니다.
- POST 본문과 `DELETE` 같은 메서드도 백엔드까지 전달됩니다.
- 백엔드 응답에 `Content-Length`가 있으면 클라이언트 연결이 유지됩니다.

### M7 완료 기준

- 서버에 `SIGINT`/`SIGTERM`을 보내면 처리 중인 응답을 끝내고 종료 로그를 남긴 뒤 종료 코드 0으로 끝납니다. 종료 중에는 새 연결이 거부됩니다.
- 종료 중에 시그널을 한 번 더 보내면 즉시 종료합니다.
- 종료 후 LeakSanitizer가 누수를 보고하지 않습니다(Linux).
- 큰 파일을 받는 중에 `curl`을 강제로 끊어도 서버가 살아 있고, 열린 fd 수가 늘지 않습니다.
- 정적·CGI·프록시 요청을 섞은 동시 다중 클라이언트 테스트가 통과합니다.

### LMS 요구사항 연결

| LMS 항목                                          | 구분     | 이 문서               |
| ------------------------------------------------- | -------- | --------------------- |
| Proxy 또는 Reverse Proxy 구현                     | 필수     | 2장 ~ 10장             |
| 경로 또는 Host 헤더 기반 라우팅                   | Reverse 시 필수 | 4장            |
| Round-Robin 등 단순 로드 밸런싱                   | 권장     | 9장                   |
| 라우팅 규칙을 CLI 인자 또는 설정 파일로           | 필수     | 4.2                   |
| 정적 요청을 프록시가 직접 서빙할지                | 선택     | 4.5 (직접 서빙)       |
| 백엔드 서버 응답 없음 / 타임아웃                  | 엣지 케이스 | 7장                |

| 항목                         | 이유                                                  |
| ---------------------------- | ----------------------------------------------------- |

## 2. 프록시 방식: Forward와 Reverse

두 방식 모두 **중간에서 요청을 대신 전달하는 서버**입니다. 차이는 **누구 편에 서서 누구를 대신하느냐**입니다.

### Forward Proxy: 클라이언트를 대신함

```
[클라이언트] → [Forward Proxy] → 인터넷의 아무 서버
```

- 클라이언트가 프록시를 알고 일부러 씁니다(`curl -x` 같은 설정).
- 원 서버는 요청이 프록시에서 왔다고만 알고, 진짜 클라이언트는 숨겨집니다.
- 목적지가 정해져 있지 않습니다. 클라이언트가 가자고 하는 곳 어디든 갑니다.
- **요청 줄이 다릅니다.** 목적지를 알려야 해서 전체 URL이 옵니다. 프록시는 URL에서 호스트와 포트를 꺼내 `getaddrinfo`로 주소를 찾고, 새 TCP 연결을 만들어 `GET /index.html`로 바꿔 전달합니다.

```
GET http://example.com/index.html HTTP/1.1   ← Forward Proxy가 받는 요청 (absolute-form)
GET /index.html HTTP/1.1                     ← 일반 서버가 받는 요청 (origin-form)
```

**어디에 쓰나**
- 보안: 회사나 학교 네트워크에서 나가는 접속을 한곳으로 모아 차단하고 기록합니다. 클라이언트 IP도 숨깁니다.
- 캐싱: 여러 사람이 받는 같은 페이지를 프록시가 저장해 두고 대신 줍니다.
- 로드 밸런싱: 거의 해당 없습니다.

### Reverse Proxy: 서버를 대신함

```
                                     ┌→ 백엔드 A (8001)  /api/*
[클라이언트] → [Reverse Proxy :8000] ─┼→ 백엔드 B (8002)  /api/*  (A와 번갈아)
                                     └→ 백엔드 C (8003)  /static/*
```

- 클라이언트는 프록시가 있는지 모릅니다. 그냥 `localhost:8000`이라는 서버에 요청했다고 생각합니다.
- 숨겨지는 쪽은 백엔드입니다.
- 목적지는 운영자가 정한 백엔드 목록뿐이고, 요청 줄은 일반 형태(`GET /api/users`) 그대로 옵니다.
- 프록시는 경로나 Host 헤더를 보고 라우팅 규칙에서 백엔드를 고릅니다. 같은 일을 하는 백엔드가 여럿이면 Round-Robin으로 번갈아 보냅니다.

**어디에 쓰나**
- 로드 밸런싱: 요청을 여러 백엔드에 나눠 보내고, 죽은 백엔드는 뺍니다.
- 보안: 백엔드를 외부에 드러내지 않고, 잘못된 요청을 입구에서 거릅니다. M5에서 만든 400·413·414와 CL+TE 거절이 여기서 그대로 쓰입니다.
- 캐싱: 정적 파일이나 백엔드 응답을 프록시가 들고 있다가 줍니다.

### 비교

|                    | Forward                      | Reverse                          |
| ------------------ | ---------------------------- | -------------------------------- |
| 누구를 대신하나    | 클라이언트                   | 서버                             |
| 존재를 아는 쪽     | 클라이언트(설정함)           | 서버 운영자(클라이언트는 모름)   |
| 숨겨지는 쪽        | 클라이언트                   | 백엔드                           |
| 목적지             | 요청마다 다름                | 정해진 백엔드 목록               |
| 요청 줄            | `GET http://host/path`       | `GET /path`                      |
| 핵심 로직          | URL 파싱, DNS 조회           | 라우팅 표, 로드 밸런싱           |
| 보안               | **나가는** 트래픽을 통제     | **들어오는** 트래픽을 막음       |
| 로드 밸런싱        | 거의 없음                    | Reverse의 일                     |
| 캐싱               | 여러 사이트의 콘텐츠를 여러 사용자에게 | 우리 서비스의 콘텐츠를 모든 사용자에게 |
| 우리 과제에서 테스트 | 외부 사이트가 필요해 CI가 흔들릴 수 있음 | 로컬 백엔드 2개로 끝      |
| 위험               | 내부망 주소로도 접속해 줌(SSRF) | 설정한 백엔드로만 감          |

### 내 선택: Reverse 먼저, 시간이 남으면 Forward

로드 밸런싱으로 백엔드 여러 대에 요청을 나눠 처리량과 가용성을 높이고, 한 주소 뒤에 여러 서비스를 묶을 수 있습니다. 과제가 라우팅·Round-Robin·라우팅 규칙 인자까지 자세히 적어 두었고, M5에서 만든 원본 헤더 보존과 "모아서 확인 후 보내기" 구조를 그대로 쓸 수 있습니다.

**Reverse의 단점으로 알고 가는 것**
- 프록시가 죽으면 백엔드가 멀쩡해도 서비스 전체가 멈춥니다(단일 장애점).
- 모든 요청이 한 번 더 거쳐 가서 지연이 조금 늘어납니다.
- 프록시가 병목이 될 수 있습니다.
- 원래 클라이언트 IP가 백엔드에 보이지 않습니다(`X-Forwarded-For`로 대응, 5.5).

Forward를 하지 않으면 "클라이언트를 대신한다"는 관점과 캐싱 경험을 잃습니다. 못 하더라도 README에 위 비교표를 넣어 중점 포인트를 설명합니다.

## 3. 프록시를 어디에 넣을까

### 후보

**(a) 지금 서버 안에 라우팅 단계 추가 (nginx 방식)**

```
요청 → 파싱 → 라우팅 표 확인 ─┬ 걸림   → 프록시로 백엔드에 전달
                              └ 안 걸림 → 지금처럼 정적 파일 / CGI
```

- 장점: 스레드 풀, accept, keep-alive 루프, 타임아웃, 오류 응답을 그대로 씁니다. 바뀌는 곳이 적어 빨리 동작시킬 수 있습니다.
- 단점: 요청 처리 함수에 분기가 늘고, 프록시와 정적 서버의 역할이 한 프로그램에 섞입니다.

**(b) 프록시만 하는 실행 파일을 따로 만들기**

```
./build/proxy 8000 --route /api=:8001,:8002 --route /=:8003
./build/tiny 8001   ./build/tiny 8002   ./build/tiny 8003
```

- 장점: 역할이 분명합니다(프록시는 중계만, tiny는 서빙만). 팀 분담이 쉽고 실제 구조(nginx + 앱 서버)를 보여 줍니다.
- 단점: accept·스레드 풀·keep-alive 루프가 지금 `tiny.c`의 `main` 쪽에 있어서 `src/` 모듈로 옮기거나 복사해야 합니다. 정적 요청도 한 번 더 거쳐 갑니다.

**(c) 실행 파일은 하나, 실행 인자로 역할 선택**

- (a)와 (b)의 중간입니다. 코드는 한 파일에 있고 실행할 때 역할만 나눕니다.
- 장점: 루프를 다시 쓰지 않으면서 역할을 분리해 보여 줄 수 있습니다.
- 단점: (a)와 거의 같은 코드인데 모드 분기만 늘어나 얻는 게 적습니다.

### 고민: 성능으로 보면 (b)처럼 나누는 게 좋지 않나?

**성능만 보면 오히려 (a)가 같거나 더 좋습니다.**

| 요청                  | (a) 한 서버                         | (b) 프록시 따로                                         |
| --------------------- | ----------------------------------- | ------------------------------------------------------- |
| 정적 파일 `/home.html` | 클라이언트 → tiny가 바로 응답       | 클라이언트 → 프록시 → tiny → 프록시 → 클라이언트. 연결 하나와 복사가 더 생겨 느림 |
| 프록시 경로 `/api/*`  | 클라이언트 → 프록시 → 백엔드        | 같음 (중계 코드가 같음)                                 |

프로세스를 나눠도 동시성은 스레드 풀이 맡고, 우리 테스트는 한 컴퓨터에서 돌아 CPU도 같습니다. (b)가 유리한 경우는 성능이 아니라 운영과 구조 쪽입니다.
- 프록시와 백엔드를 서로 다른 컴퓨터에 두고 각각 늘릴 때
- 한쪽이 죽어도 다른 쪽이 살아 있어야 할 때
- 역할을 나눠 구조를 보여 주고 싶을 때

AI로 구현하더라도 연결 루프를 옮기는 리팩터링은 기존 기능 테스트를 다시 지켜야 하고, 팀 기준상 리뷰에서 바뀐 범위를 모두 설명해야 합니다.

### 내 선택: (a) 지금 서버에 라우팅 단계 추가

백엔드로 우리 tiny를 여러 개 띄우면 (b)의 장점 하나(실제 구조처럼 보여 주기)도 얻을 수 있습니다.

```
./build/tiny 8001 --root backend1/
./build/tiny 8002 --root backend2/
./build/tiny 8000 --route /api=127.0.0.1:8001,127.0.0.1:8002
```

## 4. 라우팅 규칙

### 4.1 무엇을 보고 고르나: 경로 접두사

> **코치님 조언:** URI를 자원 단위로 설계하면 라우팅 규칙이 깔끔해진다.
>
> ```
> 나쁜 예: GET /getUser?id=3     POST /deleteUser
> 좋은 예: GET /users/3           DELETE /users/3
> ```

자원은 **경로**로 가리키고(`/users/3`), 무엇을 할지는 **메서드**로 말합니다(GET, DELETE). 리버스 프록시는 경로 앞부분을 보고 백엔드를 고르므로, 경로가 자원 단위면 규칙이 접두사 하나로 끝납니다.

```
좋음:  /api/users/3, /api/orders/5  → /api 규칙 하나로 API 백엔드에
나쁨:  /getUser?id=3, /getOrder?id=5 → 공통 접두사가 없어 규칙을 하나씩 만들어야 함
```

- 이 조언이 적용되는 곳은 **Reverse**입니다. Forward는 URL의 호스트로 목적지를 고르고, 경로는 남의 서버가 설계한 것이라 우리가 바꿀 수 없습니다.
- **새로 URI를 설계하는 곳은 M6의 라우팅 규칙과 백엔드 경로**입니다. 시연용 백엔드 경로를 `/api/users`, `/api/users/3`처럼 자원 단위로 만듭니다.
- 기존 `/cgi-bin/adder?1&2`는 바꾸지 않습니다. 자원을 가리키는 게 아니라 계산할 값을 넘기는 것이라 쿼리가 어색하지 않고, `/cgi-bin/프로그램?인자`는 CGI 표준 관례입니다.

### 4.2 규칙을 어떻게 받나: CLI 반복 옵션

```
--route /api=127.0.0.1:8001,127.0.0.1:8002 --route /static=127.0.0.1:8003
```

과제는 CLI 인자와 설정 파일 중 하나를 요구합니다. CLI를 고른 이유는 이렇습니다.
- 지금 `args_parse`로 `--root`, `--threads` 등을 받는 방식에 옵션 하나만 더하면 됩니다.
- 기능 테스트가 서버를 인자와 함께 띄우므로 테스트가 쉽습니다. 설정 파일이면 테스트마다 임시 파일을 만들어야 합니다.
- 우리 규칙은 2~3개라 명령 한 줄에 들어갑니다.

설정 파일이 나은 경우(규칙 10개 이상, 규칙마다 주석, 실행 중 다시 읽기)는 우리 과제에 해당하지 않습니다. 값 한 줄을 해석하는 함수(`route_parse_line`)를 따로 두면, 나중에 설정 파일을 붙일 때 파일을 한 줄씩 읽어 같은 함수에 넘기기만 하면 됩니다. 이 함수는 라우팅 단위 테스트 대상이 됩니다.

### 4.3 접두사를 어떻게 매칭하나: `/` 경계 + 가장 긴 접두사

```
규칙 /api
  /api           → 걸림
  /api/users/3   → 걸림
  /apiary        → 안 걸림   ← 단순 문자열 비교면 걸려 버림

--route /api=:8001  --route /api/admin=:8009
  /api/admin/x   → 8009      ← 더 긴 접두사가 이김
  /api/users     → 8001
```

쿼리는 보지 않습니다. `?` 앞의 경로만 비교합니다.

### 4.4 백엔드에 경로를 어떻게 보내나: 그대로

| 방식              | `/api/users/3` 요청이 백엔드에 | 비고                                                               |
| ----------------- | ------------------------------ | ------------------------------------------------------------------ |
| **그대로** (선택) | `/api/users/3`                 | 가장 단순. 백엔드도 `/api/...` 경로를 가짐                          |
| 접두사 떼기       | `/users/3`                     | 백엔드가 자기가 `/api` 아래에 있는지 몰라도 되지만, 경로를 고쳐 쓰는 코드와 엣지 케이스(`/api` → `/`)가 생김 |

### 4.5 어느 규칙에도 안 걸리면: 정적 파일 / CGI

지금처럼 우리 서버가 처리합니다. 404로 막으면 기존 기능이 전부 사라집니다.

### 4.6 백엔드 주소: `호스트:포트`, 서버를 켤 때 한 번 해석

| 형식              | 예                                 | 장점                         | 단점                         |
| ----------------- | ---------------------------------- | ---------------------------- | ---------------------------- |
| **`호스트:포트`** (선택) | `127.0.0.1:8001`, `localhost:8001` | 익숙하고 이름과 IP를 둘 다 받음 | `getaddrinfo`가 필요 (표준 함수) |
| IPv4 숫자만       | `127.0.0.1:8001`                   | `inet_pton` 하나, DNS 없음   | `localhost`를 못 씀          |
| 포트만            | `:8001`                            | 가장 짧고 로컬 테스트에 편함 | 다른 컴퓨터의 백엔드를 못 가리킴 |
| IPv6 포함         | `[::1]:8001`                       | 완전함                       | 대괄호 파싱 추가. 과제에 필요 없음 |

주소는 **서버를 켤 때 한 번만 해석**합니다. 틀린 주소면 사용법을 출력하고 바로 종료합니다. 요청마다 해석하면 DNS 지연이 생기고 결과를 매번 `freeaddrinfo`로 해제해야 합니다. 우리 백엔드는 로컬 고정 주소라 IP가 바뀔 일이 없습니다.

## 5. 요청 전달: 백엔드에 보낼 때 무엇을 고치나

백엔드에 보낼 요청은 **요청 줄 + 헤더 + 본문**입니다. 메서드와 경로·쿼리는 그대로 보내고(4.4), 본문과 `Content-Length`도 이미 다 받아 두었으므로 그대로 보냅니다. 고칠지 정할 것은 아래 여섯 가지입니다.

### 5.1 헤더를 무엇으로 만드나: 원본 블록 + 걸러내기 + 추가

| 방식                       | 내용                                                  | 장점                    | 단점                                                       |
| -------------------------- | ----------------------------------------------------- | ----------------------- | ---------------------------------------------------------- |
| 그대로 복사                | 받은 헤더 블록을 손대지 않고 보냄                     | 가장 단순               | `Connection: keep-alive`, `Expect`가 그대로 가서 동작이 깨짐 (5.3, 5.6) |
| 구조체로 다시 만들기       | 파싱한 `struct http_request` 필드로 헤더를 새로 씀    | 무엇을 보내는지 명확    | 구조체에는 Host, CL, Connection, Expect만 있어서 `Cookie`, `Authorization`, `Content-Type` 등이 사라짐 |
| **원본 블록 + 걸러내기 + 추가** (선택) | M5에서 보존한 `raw_headers`(최대 8 KiB)를 한 줄씩 보면서 뺄 줄은 빼고, 넣을 줄은 끝에 붙임 | 모르는 헤더도 모두 전달 | 줄 단위로 걸러내는 함수가 필요 (대신 단위 테스트하기 좋음) |

**내 선택: 원본 블록 + 걸러내기 + 추가.** 구조체로 다시 만들면 POST의 `Content-Type`이 빠져 백엔드가 본문을 해석하지 못합니다. M5에서 원본 헤더 블록을 보존한 이유(final.md 3.1)가 바로 이것입니다.

원본 8 KiB에 `Connection: close`, `X-Forwarded-For` 등을 더하면 8 KiB를 조금 넘을 수 있으므로, 보낼 헤더 버퍼는 여유 있게 잡습니다(구현할 때 정함).

### 5.2 요청 줄의 버전: `HTTP/1.1` 고정

| 방식                       | 장점                                              | 단점                                                     |
| -------------------------- | ------------------------------------------------- | -------------------------------------------------------- |
| 클라이언트 버전 그대로     | 손대는 게 없음                                    | 1.0과 1.1이 섞여 백엔드 동작이 요청마다 달라짐           |
| **`HTTP/1.1` 고정** (선택) | 동작이 일정하고, 과제의 응답 예시(`HTTP/1.1 200 OK`)와 맞음 | 백엔드가 chunked로 응답할 수 있음 → 6.2의 "`Content-Length`가 없으면 클라이언트 연결 닫기"로 처리 |
| `HTTP/1.0` 고정 (CSAPP Proxy Lab 방식) | 백엔드가 chunked를 쓰지 않음              | 오래된 버전으로 낮춤. 그래도 응답에 CL이 없을 수 있어 "닫기" 규칙은 여전히 필요 |

### 5.3 홉 단위 헤더 빼기

헤더에는 두 종류가 있습니다.
- **끝 단위(end-to-end)**: 최종 목적지까지 가는 정보. 예: `Content-Type`, `Cookie`
- **홉 단위(hop-by-hop)**: 바로 옆 연결 하나에만 해당하는 정보. 예: `Connection: keep-alive`는 클라이언트와 프록시 사이의 연결을 유지하자는 뜻이라 백엔드에 넘기면 안 됩니다.

RFC 9110이 홉 단위로 정한 헤더는 `Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Transfer-Encoding`, `Upgrade`, `Proxy-Authorization`, `Trailer`입니다. **`Connection` 값에 이름이 적힌 헤더**도 홉 단위입니다(`Connection: close, X-Foo`면 `X-Foo`도 뺌).

| 방식                                             | 장점                         | 단점                                                       |
| ------------------------------------------------ | ---------------------------- | ---------------------------------------------------------- |
| 빼지 않음                                        | 코드 없음                    | `Connection: keep-alive`가 넘어가 백엔드가 연결을 닫지 않음 → EOF로 응답 끝을 판단하는 6.2 방식이 시간 제한까지 멈춤 |
| `Connection`, `Keep-Alive`만 빼기                | 간단                         | `Upgrade` 등이 넘어가면 백엔드가 프로토콜 전환을 시도할 수 있음 |
| **RFC 목록 전체 + `Connection`에 적힌 이름까지** (선택) | 표준대로라 근거를 설명하기 쉬움 | 목록 비교와 `Connection` 값 파싱이 조금 필요               |

**내 선택: RFC 목록 전체와 `Connection`에 적힌 이름까지 빼고, 끝에 `Connection: close`를 붙입니다.** 백엔드가 이 헤더를 보고 응답 후 연결을 닫기 때문에 "백엔드 EOF = 응답 끝"(6.2)이 성립합니다. `Transfer-Encoding`은 M5에서 이미 501로 거절하므로 실제로는 올 일이 없습니다.

### 5.4 Host 헤더: 클라이언트 값 그대로

| 방식                               | 백엔드가 받는 값         | 장점                                                       | 단점                                                       |
| ---------------------------------- | ------------------------ | ---------------------------------------------------------- | ---------------------------------------------------------- |
| **클라이언트 값 그대로** (선택)    | `Host: localhost:8000`   | 백엔드가 사용자가 접속한 주소를 앎 → 리다이렉트나 링크를 올바른 주소로 만듦. 코드가 가장 적음 | 백엔드가 Host로 가상 호스트를 고르면 맞지 않을 수 있음      |
| 백엔드 주소로 바꾸기 (nginx 기본)  | `Host: 127.0.0.1:8001`   | 백엔드 입장에서 자기 주소라 자연스러움                     | 백엔드가 만든 링크가 내부 주소를 가리켜 클라이언트가 못 감 |
| 그대로 + `X-Forwarded-Host`        | 둘 다                    | 정보 손실 없음                                             | 헤더 하나 더. 우리 백엔드는 쓰지 않음                      |

**고민:** 우리는 경로로 라우팅하고, 백엔드도 Host로 가상 호스트를 고르는 서버가 아니라 우리 tiny입니다. 그래서 바꿀 이유가 없어 **그대로 둡니다.**

**예외:** HTTP/1.0 클라이언트는 Host를 보내지 않을 수 있습니다(M5에서 허용). 5.2에서 `HTTP/1.1`로 고정했고 1.1은 Host가 필수이므로, **Host가 없으면 백엔드 주소로 넣어 줍니다.**

### 5.5 X-Forwarded-For: 클라이언트 IP로 덮어쓰기

백엔드 입장에서는 모든 요청이 프록시 IP(`127.0.0.1`)에서 옵니다. 2장에 적은 Reverse의 단점("원래 클라이언트 IP가 보이지 않음")에 대한 대응으로, 프록시가 진짜 클라이언트 IP를 헤더로 알려 줍니다.

| 방식                                   | 장점                                                     | 단점                                                       |
| -------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| 넣지 않음                              | 코드 없음                                                | 백엔드 로그가 전부 프록시 IP                               |
| **`X-Forwarded-For: <클라이언트 IP>` 덮어쓰기** (선택) | 사실상 표준. 우리가 맨 앞 프록시라 클라이언트가 보낸 값은 믿을 수 없으므로 덮어쓰는 게 안전 | 앞에 다른 프록시가 있는 구조로 바뀌면 그 정보를 잃음       |
| 기존 값 뒤에 덧붙이기 (`a, b`)         | 프록시를 여러 개 거쳐도 경로가 남음                      | 클라이언트가 가짜 값을 미리 넣어 IP를 속일 수 있음         |
| 표준 `Forwarded: for=...` (RFC 7239)   | 정식 표준                                                | 실제로는 X-Forwarded-For가 더 널리 쓰임                    |

클라이언트 IP는 `accept`할 때 이미 받으므로 작업자에게 넘겨 주기만 하면 됩니다. 필수 기능은 아니라 M6-2(단일 백엔드 중계) 뒤에 붙여도 됩니다.

### 5.6 `Expect: 100-continue`: 우리가 처리하고, 백엔드에는 빼고 보냄

M5에서 우리 서버가 100-continue를 직접 처리합니다(본문 검사 → `100 Continue` → 본문 읽기, final.md 3.6). 그리고 라우팅은 본문을 다 읽은 뒤에 합니다(10장).

| 방식                                              | 장점                                                    | 단점                                                       |
| ------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------- |
| **우리가 처리하고, 백엔드에는 `Expect`를 빼고 보냄** (선택) | 지금 M5 동작에서 바뀌는 게 없음. 백엔드 응답은 항상 최종 응답 하나 | 백엔드가 본문을 거절할 상황(백엔드의 크기 제한 등)이어도 본문이 일단 프록시까지 옴 (최대 1 MiB라 영향이 작음) |
| 백엔드에 그대로 넘기고 백엔드의 `100`을 중계      | 백엔드가 본문을 받을지 직접 결정                        | 라우팅을 본문 읽기 전으로 옮겨야 하고, 중간 응답 `100`을 읽어 전달한 뒤 최종 응답을 다시 읽어야 함 |

**`Expect`를 꼭 빼야 하는 이유:** 빼지 않고 넘기면 백엔드가 먼저 `HTTP/1.1 100 Continue\r\n\r\n`을 보냅니다. 우리는 응답 헤더를 `\r\n\r\n`까지 모아 확인하므로(6.1) **이 100을 최종 응답으로 착각해 클라이언트에 보내 버립니다.** 그래서 5.3의 걸러내기 목록에 `Expect`를 넣습니다.

### 5.7 정리

| 항목            | 처리                                                              |
| --------------- | ----------------------------------------------------------------- |
| 요청 줄         | 메서드·경로·쿼리 그대로, 버전은 `HTTP/1.1`                       |
| 뺄 헤더         | RFC 홉 단위 목록, `Connection`에 적힌 이름, `Expect`, 기존 `X-Forwarded-For` |
| 붙일 헤더       | `Connection: close`, `X-Forwarded-For: <클라이언트 IP>`, (없을 때만) `Host: <백엔드 주소>` |
| 그대로 둘 것    | `Host`, `Content-Length`, `Content-Type`, `Cookie` 등 나머지 헤더와 본문 |

## 6. 응답 받기

### 6.1 언제 클라이언트에 보내나: 헤더는 모아서 확인, 본문은 흘려보내기

**방식 1. 전부 모아서 보내기 (CGI와 같은 구조)**
- 장점: 다 받은 뒤 보내므로 실패하면 언제든 깔끔한 502를 보낼 수 있습니다. CGI 코드를 그대로 씁니다.
- 단점: 응답 크기만큼 `malloc`해야 해서 상한이 필요합니다. 큰 파일은 다 받을 때까지 클라이언트가 기다립니다. 동시 요청 수 × 응답 크기만큼 메모리를 씁니다. **메모리 문제가 클 것 같습니다.**

**방식 2. 받는 대로 흘려보내기**
- 장점: 응답 크기와 상관없이 메모리가 고정입니다(버퍼 하나, `malloc` 없음). 첫 바이트가 바로 나가 지연이 짧고, 프록시 본연의 동작입니다.
- 단점: 상태 줄을 이미 보낸 뒤 백엔드가 끊기면 502를 보낼 수 없어 연결을 닫는 수밖에 없습니다. 백엔드가 이상한 응답을 보내도 그대로 전달될 수 있습니다.

**고민: 둘을 합칠 수는 없나?**

```
백엔드 → [상태 줄 + 헤더를 \r\n\r\n까지 모음, 최대 8 KiB]
           → 확인: 상태 줄 형식, 헤더 크기
           ├ 이상함 / 시간 초과 / 끊김 → 502·504 (아직 아무것도 안 보냈으므로 가능)
           └ 정상 → 헤더 전송 → 본문은 받는 대로 흘려보내기
```

- 장점: 실패의 대부분(백엔드 꺼짐, 무응답, 이상한 응답)이 헤더 단계에서 나므로 깔끔한 502·504를 보냅니다. 본문은 메모리 고정이고 크기 제한이 없습니다. 헤더 상한 8 KiB는 요청 쪽 `HDR_RAW_MAX`와 같습니다.
- 단점: 본문 도중에 끊기면 여전히 연결을 닫습니다(어떤 프록시도 피할 수 없음). 방식 1, 2보다 코드가 조금 큽니다.

**내 선택: 둘을 합치기**

### 6.2 응답이 어디서 끝나나: 백엔드가 연결을 닫을 때 (EOF)

| 방식                                   | 내용                                                         |
| -------------------------------------- | ------------------------------------------------------------ |
| **백엔드 EOF** (선택)                  | 프록시가 백엔드에 `Connection: close`를 보내므로 백엔드가 응답 후 닫음. `read`가 0을 돌려주면 끝 |
| `Content-Length`나 chunked 해석        | 길이만큼, 또는 청크 끝까지 읽음. 백엔드 연결을 재사용할 때만 필요 |

가장 단순하고, 요청마다 백엔드 연결을 새로 여는 결정과 맞습니다.

**주의:** M5에서 chunked를 지원하지 않기로 한 것은 **클라이언트가 보내는 요청** 쪽입니다(`Transfer-Encoding` → 501). **백엔드가 보내는 응답**은 백엔드가 정합니다. 우리 tiny는 항상 `Content-Length`를 보내지만, 다른 HTTP/1.1 서버는 chunked로 보낼 수 있습니다. 그래서 다음 예외 규칙을 둡니다.

> 백엔드 응답에 `Content-Length`가 없으면(chunked나 EOF로 끝나는 응답) 그대로 흘려보내고 **클라이언트 연결을 닫는다.**

클라이언트가 chunked는 직접 해석하고, EOF 응답은 연결 종료로 끝을 압니다.

### 6.3 클라이언트 연결을 유지할 수 있나: `Content-Length`가 있으면

| 백엔드 응답               | 클라이언트 연결                                     |
| ------------------------- | --------------------------------------------------- |
| `Content-Length` 있음     | **유지.** 그 길이만큼 보내면 클라이언트도 응답 끝을 앎 |
| chunked                   | 닫음 (청크를 해석하지 않기 위해)                    |
| 둘 다 없음 (EOF로 끝)     | 반드시 닫음                                         |

응답의 `Connection`, `Keep-Alive` 같은 **홉 단위 헤더는 우리가 다시 씁니다.** 백엔드가 보낸 `Connection: close`는 프록시와 백엔드 사이의 이야기이므로, 클라이언트에게는 위 표의 결정에 맞는 `Connection` 헤더를 넣습니다. keep-alive를 유지할 때도 final.md 5장의 규칙(요청 수 상한, 읽기 타임아웃)을 그대로 따릅니다.

## 7. 실패와 시간 제한

### 7.1 오류 코드

| 코드    | 이름                | 의미                                          | 누구 잘못      |
| ------- | ------------------- | --------------------------------------------- | -------------- |
| **502** | Bad Gateway         | 백엔드에 연결이 안 되거나 이상한 응답을 받음  | 백엔드         |
| **504** | Gateway Timeout     | 백엔드가 시간 안에 답하지 않음                | 백엔드 (느림)  |
| 503     | Service Unavailable | 프록시가 지금 요청을 받을 수 없음             | 서비스 상태    |

502와 504를 나누는 이유는 원인이 다르기 때문입니다. 502는 "꺼졌거나 고장 남", 504는 "살아는 있는데 느림"이라 고치는 방법이 다릅니다. CGI에서 500과 504를 나눈 것(final.md 4.4)과 같은 이유입니다.

**고민: 503은 어떻게 아나?** 백엔드가 전부 꺼진 걸 **미리 알 때** 씁니다. 우리는 백엔드 상태를 주기적으로 확인하지 않으므로 미리 알 수 없습니다. **그래서 503은 쓰지 않고 502로 통일합니다.**

### 7.2 단계별 실패

```
① connect → ② 요청 보내기 → ③ 응답 헤더 받기 → ④ 본문 흘려보내기
```

`connect`는 상대 서버에 TCP 연결(3-way handshake)을 거는 클라이언트 쪽 함수입니다. 지금까지 우리 서버는 `accept`만 했지만, 프록시에서는 백엔드에 대해 클라이언트가 되므로 처음으로 `connect`를 씁니다.

| 단계 | 상황                                           | 응답                 |
| ---- | ---------------------------------------------- | -------------------- |
| ①    | 연결 거부 (백엔드 꺼짐, `ECONNREFUSED`)        | 502                  |
| ①    | 갈 수 없는 주소 (`ENETUNREACH`)                | 502                  |
| ①    | 연결 시간 초과 (백엔드 컴퓨터 무응답)          | 504                  |
| ②    | 보내는 중에 백엔드가 끊음                      | 502                  |
| ③    | 헤더가 오기 전에 끊김                          | 502                  |
| ③    | 상태 줄 형식이 이상함, 헤더가 8 KiB를 넘음     | 502                  |
| ③    | 헤더가 시간 안에 안 옴                         | 504                  |
| ④    | 본문 도중 끊김이나 시간 초과                   | 클라이언트 연결 닫기 |

### 7.3 시간 제한은 왜 필요한가

백엔드가 답하지 않으면 그 요청을 맡은 **작업자 스레드가 계속 묶입니다.** 작업자가 16개면 느린 백엔드 하나가 16개를 모두 붙잡아 정적 파일 요청까지 멈출 수 있습니다. 시간 제한은 504를 보내는 기준이면서 **작업자를 지키는 장치**입니다.

특히 `connect`는 응답 없는 주소로 연결하면 OS 기본값으로 수십 초~2분까지 막히므로 따로 시간 제한이 필요합니다.

### 7.4 시간 제한 방식

| 방식                               | 내용                                                     | 장점                             | 단점                                  |
| ---------------------------------- | -------------------------------------------------------- | -------------------------------- | ------------------------------------- |
| **`SO_RCVTIMEO` / `SO_SNDTIMEO`** (선택) | 소켓에 시간 제한을 걸면 `read`/`write`가 시간이 지나면 -1 | 지금 클라이언트 소켓과 같은 방식 | `read` **한 번** 기준이라 전체 시간이 아님 |
| 논블로킹 connect + `poll`          | 논블로킹 `connect` → `poll`로 최대 N초 대기 → `getsockopt(SO_ERROR)`로 결과 확인 | connect 시간 제한을 정확히 거는 표준 방법 | 코드가 15줄 정도 늘어남 |
| 데드라인 + `poll`                  | 시작 시각을 기록하고 매번 남은 시간만큼 `poll`           | 전체 시간을 정확히 지킴          | 읽기마다 남은 시간을 계산             |
| `alarm` / `SIGALRM`                | 시그널로 깨움                                            | 단순해 보임                      | **스레드 환경에서 쓰면 안 됨.** 어느 스레드가 시그널을 받을지 모르고, M7 `sigwait` 구조와도 충돌 |

**내 선택: `SO_RCVTIMEO` / `SO_SNDTIMEO`.** 지금 방식과 같아서입니다. 다만 이 옵션이 `connect`에도 걸리는지는 OS마다 다를 수 있어 확인이 필요합니다(12장). 걸리지 않으면 connect만 논블로킹 + `poll`로 바꿉니다. 헤더 전체 데드라인(백엔드 쪽 Slowloris 대응)은 하지 않고, 나중에 클라이언트 쪽 Slowloris를 다룰 때 함께 봅니다.

## 8. 재시도

백엔드 하나가 실패했을 때 **같은 요청을 다른 백엔드에 다시 보내는 것**입니다. 가용성은 올라가지만 같은 요청이 두 번 처리될 위험이 있습니다.

### 멱등성: 재시도해도 되는 요청인가

| 메서드      | 두 번 처리되면?               | 재시도       |
| ----------- | ----------------------------- | ------------ |
| GET, HEAD   | 조회만 하므로 같은 결과       | 안전         |
| PUT, DELETE | 결과가 같음 (멱등)            | 대체로 안전  |
| **POST**    | 주문이 두 번 들어갈 수 있음   | **위험**     |

### 방식

| 방식                    | 내용                                                    | 장점                         | 단점                                  |
| ----------------------- | ------------------------------------------------------- | ---------------------------- | ------------------------------------- |
| 재시도 안 함            | 실패하면 바로 502·504                                   | 가장 단순, 두 번 처리될 위험 없음 | 백엔드 하나가 꺼지면 요청의 1/N이 502 |
| connect 실패만 재시도   | ①단계 실패면 다음 백엔드로. 요청을 아직 안 보냈으므로 POST도 안전 | 꺼진 백엔드를 건너뜀 | 루프와 시도 횟수 상한이 필요         |
| 멱등 메서드만 재시도    | GET 등은 ③단계 실패도 재시도                            | 가용성이 가장 높음           | 규칙이 복잡하고, 백엔드에 이중 부하   |

**내 선택: 처음에는 재시도 안 함 → 여유가 생기면 connect 실패만 재시도.**

- 시간 제한이 지나도 이번 요청이 자동으로 다음 백엔드로 가지는 않습니다. 다음 **요청**은 Round-Robin 차례대로 다음 백엔드로 갑니다.
- connect 재시도를 넣으면 connect 단계의 거부와 시간 초과는 다음 백엔드로 넘어갑니다. 시도는 백엔드 수만큼(한 바퀴)만 합니다.
- **응답을 기다리다 시간이 지나면 어떤 경우에도 504**입니다. 백엔드가 이미 요청을 받아 처리 중일 수 있기 때문입니다.

## 9. 로드 밸런싱

같은 일을 하는 백엔드 여러 대에 요청을 나눠 주는 것입니다. 목적은 두 가지입니다.
- 한 대에 몰리지 않게 → 처리량
- 한 대가 죽어도 나머지가 처리 → 가용성

### 방식 비교

| 방식                 | 고르는 법                         | 장점                               | 단점                                  |
| -------------------- | --------------------------------- | ---------------------------------- | ------------------------------------- |
| Round-Robin (과제 예시) | 차례대로                       | 단순, 공평, 상태는 카운터 하나     | 성능이나 요청 무게가 다르면 쏠림      |
| Weighted RR          | 가중치만큼 더 자주 (`A:3, B:1`)   | 성능이 다른 서버에 맞춤            | 가중치 설정과 분배 계산이 추가됨      |
| Least Connections    | 지금 처리 중인 요청이 가장 적은 곳 | 느린 요청이 섞여도 균형            | 백엔드마다 처리 중 개수를 세야 함     |
| Random               | 무작위                            | 상태가 없어 락이 필요 없음         | 짧은 구간에서는 고르지 않음           |
| IP Hash              | 클라이언트 IP로 고정              | 같은 사용자는 같은 서버            | 특정 IP가 많으면 쏠림                 |

### 고민: 과제는 단순 로드 밸런싱을 권장하는데, Least Connections도 추가하면 안 되나?

우리 작업자는 백엔드 응답을 **기다리는 동안 묶여 있습니다.** 그래서 백엔드 하나가 느려지면 차이가 납니다.

```
Round-Robin:        느린 A에도 차례가 오면 계속 보냄 → A 쪽 요청이 쌓이고 작업자가 묶임
Least Connections:  A의 처리 중 수가 늘어남 → 새 요청은 다른 백엔드로 감
```

**내 선택: Round-Robin과 Least Connections 둘 다**

- 실행 인자로 고릅니다: `--balance rr`(기본) / `--balance least`
- Least Connections는 **동점이면 Round-Robin**으로 고릅니다. 동점일 때 항상 첫 번째를 고르면, 한가할 때(모두 0) 모든 요청이 첫 백엔드로만 갑니다. nginx `least_conn`도 이 방식입니다.
- 구현 순서는 Round-Robin(과제 권장)을 먼저 동작시키고 Least Connections를 더합니다.
- M8에서 느린 백엔드를 섞어 두 방식의 처리량과 504 수를 비교합니다.

### 구현할 때 주의할 점

**공유 카운터.** 여러 작업자가 같은 Round-Robin 카운터를 쓰면 데이터 경쟁이 생깁니다(`make tsan`이 잡음).

| 방식                                 | 장점                      | 단점                             |
| ------------------------------------ | ------------------------- | -------------------------------- |
| mutex                                | 익숙함 (M4 큐와 같은 방식) | 요청마다 락                      |
| C11 atomic `atomic_fetch_add`        | 락 없이 한 줄             | `<stdatomic.h>` 사용 (C11 표준)  |
| 작업자별 카운터                      | 공유하지 않음             | 전체로는 Round-Robin이 아님      |

라우팅 표는 읽기만 하고 카운터만 바뀌므로 카운터를 atomic으로 두는 것이 가장 단순합니다(12장에서 확정).

**Least Connections의 +1/−1 짝.** 요청 시작에 +1, 끝에 −1을 합니다. 502, 504, 클라이언트 끊김, 본문 도중 실패까지 **모든 종료 경로에서 −1**을 해야 합니다. 하나라도 빠지면 그 백엔드는 영원히 "바쁨"으로 보여 요청을 받지 못합니다. `malloc`/`free` 짝 맞추기와 같은 종류의 문제라 과제 중점 포인트("끊김 · 비정상 종료 시 자원 회수")와 연결됩니다. 고르기와 +1 사이에 두 작업자가 같은 백엔드를 고를 수 있지만, 약간 쏠리는 정도라 허용합니다.

**꺼진 백엔드.** 순수 Round-Robin은 꺼진 백엔드에도 차례가 오면 보내므로 백엔드 2대 중 1대가 꺼지면 요청 절반이 502가 됩니다. 8장의 "connect 실패만 재시도"로 해결합니다.

## 10. 요청 흐름

```
./build/tiny 8000 --route /api=127.0.0.1:8001,127.0.0.1:8002

[main]    accept → 큐에 넣기                                       (M4 그대로)
[작업자]  요청 줄·헤더·본문 읽기                                   (M5 그대로)
  → 경로 정리 (../ 처리)
  → 라우팅 표 확인: /api/users/3 → /api 규칙 (가장 긴 접두사)
      ├ 안 걸림 → 정적 파일 / CGI                                  (지금 그대로)
      └ 걸림   → 백엔드 고르기 (Round-Robin 또는 Least Connections)
                → socket + connect (시간 제한)       실패: 502 / 504
                → 요청 보내기 (HTTP/1.1, 홉 단위 헤더·Expect 빼기,

                → 상태 줄 + 헤더 모으기 (최대 8 KiB)   실패: 502 / 504
                → Connection 헤더를 다시 써서 클라이언트에 전송
                → 본문을 백엔드 EOF까지 흘려보내기    실패: 연결 닫기
                → 백엔드 소켓 닫기
  → Content-Length가 있었으면 다음 요청 대기 (keep-alive), 없었으면 닫기
```

**왜 핸들러가 아니라 `sigwait` 전용 스레드인가**

| 방식                       | 장점                                   | 단점                                                                  |
| -------------------------- | -------------------------------------- | --------------------------------------------------------------------- |
| 핸들러 + 플래그            | 가장 짧음                              | 핸들러가 아무 스레드에서나 돎. 핸들러 안에서 mutex, `printf`, `malloc` 사용 불가. accept 중인 main을 깨우기 어려움 |
| 핸들러 + self-pipe         | main을 확실히 깨움                     | 어느 스레드에서 도는지는 여전히 모름. `EINTR` 처리가 곳곳에 필요      |
| **`sigwait` 전용 스레드** (선택) | 시그널이 보통 함수 흐름으로 들어와 mutex·로그 사용 가능. 다른 스레드는 `EINTR`을 보지 않음 | 스레드가 하나 늘고, 다른 스레드를 만들기 전에 막아야 함 |
| `signalfd` / `kqueue`      | 시그널을 fd로 받음                     | Linux 전용 / BSD·macOS 전용이라 `#ifdef` 두 벌                        |

7.4에서 `alarm`을 고르지 않은 것도 같은 이유입니다.

**왜 `poll` + 종료 pipe인가**

| 방식                               | 단점                                                           |
| ---------------------------------- | -------------------------------------------------------------- |
| `shutdown(listenfd)`               | Linux에서는 accept가 깨지만 macOS에서는 보장되지 않음          |
| 다른 스레드에서 `close(listenfd)`  | 닫힌 fd 번호가 바로 다른 파일에 재사용될 수 있어 위험          |
| listen 소켓에 시간 제한 + 주기 확인 | 최대 N초 늦게 멈추고, 할 일 없이 계속 깨어남                  |
| **`poll`(listen 소켓 + 종료 pipe)** (선택) | pipe와 `poll` 코드가 추가되지만 두 OS에서 똑같이 바로 깨어남 |

### 11.2 M7에서 새로 정한 것

#### A. 요청을 계속 보내는 keep-alive 연결: 지금 응답에 `Connection: close`

놀고 있는 연결은 5초면 끝나지만, **요청을 계속 보내는** 연결은 `--keepalive-max`(100)까지 끝나지 않습니다.

| 방식                                                     | 장점                                       | 단점                                                       |
| -------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| 아무것도 안 함                                           | 코드 없음                                  | 클라이언트가 계속 요청하면 종료가 늦어짐                   |
| **종료 플래그를 보고 지금 응답에 `Connection: close`를 붙이고 닫기** (선택) | 처리 중인 응답은 끝내고 다음 요청은 받지 않음. atomic 플래그 하나만 확인 | 다음 요청을 기다리는 중인 작업자는 읽기 타임아웃(5초)까지 기다림 |
| 열린 연결을 모두 기록해 두고 `shutdown(fd, SHUT_RD)`로 깨우기 | 놀고 있는 연결도 즉시 끝남              | 작업자마다 fd를 공유 표에 등록·해제해야 함 → 락, 등록 누락 버그 |

놀고 있는 연결은 bloro.md의 결정대로 5초 시간 제한에 맡깁니다.

#### B. CGI 자식에게 물려주는 설정 되돌리기

`fork`한 자식은 **시그널 마스크와 "무시" 설정을 `execve` 뒤에도 물려받습니다.** 그대로 두면 CGI 프로그램이 SIGINT·SIGTERM이 막히고 SIGPIPE를 무시하는 상태로 시작합니다(SIGPIPE는 지금도 그렇습니다). 그래서 자식에서 `execve` 전에 **시그널 마스크를 원래대로, SIGPIPE를 기본 동작(`SIG_DFL`)으로** 되돌립니다. 시간 초과 때 쓰는 `SIGKILL`은 막을 수 없는 시그널이라 지금 동작에는 영향이 없지만, CGI 프로그램이 일반 프로그램처럼 동작하게 하려면 필요합니다.

#### C. 두 번째 시그널: 즉시 종료

A대로 해도 종료 대기에는 딱 정해진 상한이 없습니다. 예를 들어 `SO_SNDTIMEO`는 `write` 한 번 기준이라, 아주 느리게 받아 가는 클라이언트는 큰 파일을 보내는 동안 작업자를 오래 붙잡을 수 있습니다.

| 방식                                   | 장점                                                  | 단점                                                         |
| -------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------ |
| 끝날 때까지 기다림                     | 가장 단순                                             | 이론상 오래 걸릴 수 있음                                     |
| **횟수로 나누기: 1번째 = 안전한 종료, 2번째 = 즉시** (선택) | 사람이 판단하는 비상구. `sigwait` 루프에서 두 번째를 받으면 `_exit` | 자동 상한은 아님                                    |
| 종류로 나누기 (nginx: SIGQUIT = 안전, SIGTERM·SIGINT = 즉시) | 운영 도구와 맞추기 쉬움                 | Ctrl-C가 정리 없이 꺼져 과제의 "SIGINT 안전한 셧다운"과 맞지 않음 |
| 횟수 + 데드라인 (N초 뒤 스스로 즉시 종료) | 자동 상한 보장                                     | 타이머나 `sigtimedwait`가 필요한데 macOS에는 `sigtimedwait`가 없음 |

```
[시그널 스레드]
  sigwait → 첫 번째 (SIGINT든 SIGTERM이든)
            → 종료 플래그 → 종료 pipe에 1바이트 → 로그 "shutting down"
            → 다시 sigwait
  sigwait → 두 번째 (SIGINT든 SIGTERM이든)
            → 로그 "forced exit" → _exit(1)
```

- SIGINT와 SIGTERM은 구분하지 않고 같이 셉니다. Ctrl-C 뒤에 `kill`을 보내도 두 번째입니다.
- 종료 코드 0은 첫 번째로 끝났을 때만 나옵니다. 누수 검사(11.6)는 시그널을 한 번만 보냅니다.

#### D. 시그널 스레드 자신의 종료: 깨워서 join

시그널 스레드는 두 번째 시그널을 기다리며 `sigwait`에 멈춰 있어서 그냥은 join할 수 없습니다.

| 방식                                                    | 장점                                   | 단점                                            |
| ------------------------------------------------------- | -------------------------------------- | ----------------------------------------------- |
| **main이 정리 끝에 `pthread_kill`로 깨우고 join** (선택) | 모든 스레드를 join했다고 말할 수 있음  | 시그널 스레드가 "종료 중에 온 이 시그널은 main이 보낸 것"임을 플래그로 구분해야 함 |
| detach하고 join하지 않음                                 | 코드가 적음 (할당이 없어 누수에도 안 걸림) | 스레드 하나가 정리되지 않은 채로 끝남        |

### 11.3 종료 흐름

```
[시그널 스레드]  sigwait → 종료 플래그 = 1 → 종료 pipe에 1바이트 → 로그 "shutting down"
                 → 다시 sigwait (두 번째면 _exit, main이 깨운 것이면 끝)

[main]  poll에서 종료 pipe를 보고 accept 루프를 빠져나옴
  1. close(listenfd)           새 연결은 거부됨
  2. conn_queue_shutdown       작업자에게 "큐에 남은 것만 처리하고 끝내라"
  3. pthread_join × 작업자      처리 중인 요청 + 큐에 남은 연결이 끝날 때까지
  4. conn_queue_destroy, free(workers)
  5. pthread_kill → 시그널 스레드 join
  6. 종료 pipe 닫기
  7. 로그 "stopped" → return 0

[작업자]  지금 요청을 끝까지 처리
          → 종료 플래그가 서 있으면 응답에 Connection: close를 붙이고 연결 닫기 (A)
          → conn_queue_pop이 -1이면 스레드 종료
```

### 11.4 M6 때문에 더해지는 것

| 항목                         | 내용                                                                 |
| ---------------------------- | -------------------------------------------------------------------- |
| 백엔드 소켓                  | 종료 중에도 처리 중인 프록시 요청은 끝까지 처리하고 백엔드 소켓을 닫음 |
| 종료가 늦어지는 시간         | 작업자가 백엔드를 기다리는 중이면 최대 connect 3초 + 응답 10초. 각 시간 제한이 상한 역할을 하므로 따로 할 일은 없음 |
| Least Connections 카운터     | 종료 경로에서도 +1/−1 짝이 맞는지 (11.5와 함께 확인)                  |
| 라우팅 표                    | 고정 배열이면 해제할 것이 없음. 동적 할당이면 종료 시 해제 (12장)    |

### 11.5 끊김 · 비정상 종료 시 자원 회수

과제 중점 포인트입니다. 오류로 함수를 빠져나갈 때 이미 연 fd와 메모리를 어디서 해제하는지를 경로별로 정리합니다.

| 상황                                   | 회수할 자원                                       |
| -------------------------------------- | ------------------------------------------------- |
| 클라이언트가 응답 도중 끊김            | 클라이언트 소켓, (프록시면) 백엔드 소켓, LC 카운터 |
| 백엔드가 본문 도중 끊김                | 백엔드 소켓, 클라이언트 소켓, LC 카운터           |
| 요청 본문 도중 끊김                    | 본문 버퍼 (M5에서 처리됨)                         |
| CGI 실행 중 끊김                       | 자식 프로세스, 파이프 (M5에서 처리됨)             |

메모리 누수 검사(11.6)는 **fd와 자식 프로세스는 보지 않으므로** 따로 확인합니다.

| 방식                         | 장점                                       | 단점                         |
| ---------------------------- | ------------------------------------------ | ---------------------------- |
| 코드 리뷰로 오류 경로 점검   | 비용이 작음                                | 빠뜨리기 쉬움                |
| **열린 fd 수 비교** (선택)   | 강제 끊김 수십 번 전후로 서버의 열린 fd 수가 같으면 회수된 것 | OS마다 세는 방법이 다름 (Linux `/proc/<pid>/fd`, macOS `lsof -p`). Linux CI에서만 돌려도 충분 |
| **좀비 확인** (선택)         | CGI 도중 끊김 뒤 `ps`에 `<defunct>`가 없음 | —                            |

끊김 시나리오: 큰 파일을 받는 도중, POST 본문 도중, CGI 실행 도중, 프록시 응답 도중, keep-alive 대기 중에 클라이언트를 강제로 끊습니다.

### 11.6 서버 전체 누수 검사

지금은 서버를 Ctrl-C로 끄면 LeakSanitizer가 보고하지 않아 단위 테스트로만 누수를 확인합니다(final.md 8.6). bloro.md에서는 "서버를 종료했을 때 보고하지 않는지 확인"까지 정했고, 판정 방법을 새로 정합니다.

| 방식                                | 장점                                                         | 단점                                              |
| ----------------------------------- | ------------------------------------------------------------ | ------------------------------------------------- |
| **LeakSanitizer (Linux CI)** (선택) | 개발 빌드에 ASan이 이미 켜져 있음. `exit`할 때 자동 검사하고 **누수가 있으면 종료 코드가 0이 아님** → 테스트가 종료 코드만 보면 됨 | macOS에서는 동작하지 않음 |
| valgrind (Linux)                    | 과제가 직접 언급                                             | ASan과 같이 쓸 수 없어 빌드가 하나 더 필요. 스레드가 많으면 매우 느림 |
| macOS `leaks --atExit`              | macOS에서도 확인                                             | CI와 결과가 다를 수 있고 자동화가 번거로움        |

```
서버 시작 → 정적·CGI·POST·프록시·keep-alive 요청, 413·본문 도중 끊김·CGI 실패 경로
→ SIGTERM 한 번 → 종료 코드 0이면 통과
```

**주의:** 이 검사는 `return`이나 `exit()`로 끝날 때만 돕니다. 두 번째 시그널의 `_exit`나 시그널 기본 동작으로 끝나면 검사하지 않습니다. 그래서 "첫 번째 시그널 = 정리 후 정상 종료"(C)가 누수 검사의 전제입니다.

### 11.7 동시 다중 클라이언트 기능 테스트

과제 품질 필수 항목인데 지금 `tests/functional`에 없습니다. final.md M4 완료 기준("정적과 CGI를 섞은 동시 요청 50개가 모두 정상 응답, 좀비 없음")을 테스트로 옮기고, 프록시 요청도 섞습니다. 파이썬 `concurrent.futures`로 50개를 동시에 보냅니다.

## 13. 검증 계획

### 준비

- 우리 tiny를 백엔드로 2개 띄웁니다. `--root`를 다르게 해서 응답 본문으로 어느 백엔드인지 구분합니다.
- 작은 파이썬 테스트 백엔드를 둡니다. 받은 메서드, 경로, 본문 길이, 자기 포트를 돌려줍니다. 옵션으로 일부러 늦게 응답하거나(504 확인), `Content-Length` 없이 응답합니다(연결 닫기 확인).
- 경로는 자원 단위로 둡니다: `/api/users`, `/api/users/3`

### 단위 테스트

| 대상                 | 확인할 것                                                       |
| -------------------- | --------------------------------------------------------------- |
| `route_parse_line`   | 정상 규칙, 백엔드 여러 개, 틀린 형식, 상한 초과                 |
| 라우팅 매칭          | `/` 경계(`/apiary` 안 걸림), 가장 긴 접두사, 쿼리 무시, 매칭 없음 |
| 요청 헤더 걸러내기   | 홉 단위 헤더와 `Connection`에 적힌 이름 제거, `Expect` 제거, `X-Forwarded-For` 덮어쓰기, Host 없을 때 추가, 모르는 헤더(`Content-Type`, `Cookie`) 유지 |
| 응답 헤더 확인       | 상태 줄 형식 오류, 8 KiB 초과, `Content-Length` 유무            |
| Least Connections    | 동점이면 Round-Robin, 처리 중 수가 적은 곳 선택                 |

### 기능 테스트

| 요청                                                         | 기대 결과                                   |
| ------------------------------------------------------------ | ------------------------------------------- |
| `GET /api/users` 여러 번                                     | 두 백엔드가 번갈아 응답                     |
| `GET /home.html`                                             | 우리 서버가 직접 `200`                      |
| `POST /api/users` (본문 포함)                                | 백엔드가 같은 본문 길이와 `Content-Type`을 받음 |
| 큰 본문 POST (`curl`이 `Expect: 100-continue`를 붙임)        | 약 1초 지연 없이 응답, 백엔드는 `Expect`를 받지 않음 |
| `Connection: keep-alive`를 붙인 `GET /api/users`             | 백엔드는 `Connection: close`만 받고, 응답이 시간 제한 없이 바로 끝남 |
| `GET /api/users`                                             | 백엔드가 받은 `X-Forwarded-For`가 클라이언트 IP |
| `DELETE /api/users/3`                                        | 백엔드까지 전달됨                           |
| 백엔드를 끄고 `GET /api/users`                               | `502`                                       |
| 늦게 응답하는 백엔드에 `GET /api/slow`                       | 약 10초 뒤 `504`                            |
| 같은 연결로 `/api/users`를 두 번 (`Content-Length` 있음)     | 연결 재사용                                 |
| `Content-Length` 없는 백엔드 응답                            | 본문은 그대로 오고, 연결이 닫힘             |
| `--balance least` + 느린 백엔드 하나                         | 새 요청이 빠른 백엔드로 몰림                |
| 정적·CGI·프록시 요청을 섞은 동시 다중 클라이언트             | 모두 정상 응답                              |
| 큰 파일을 받는 중 `curl` 강제 종료                           | 서버가 살아 있음                            |
| 큰 파일을 받는 중에 서버에 `SIGTERM`                         | 받던 파일은 끝까지 받고 서버 종료, 그 뒤 새 연결은 거부 (bloro.md) |
| 여러 요청을 보낸 뒤 서버에 `SIGTERM` 한 번                   | 종료 코드 0, LeakSanitizer 보고 없음 (Linux) |
| 종료 중에 시그널 한 번 더                                    | 즉시 종료                                   |
| 종료 중에 keep-alive 연결로 요청                             | 응답에 `Connection: close`가 붙고 연결이 닫힘 |
| 강제 끊김 수십 번 (큰 파일, POST 본문, CGI, 프록시 도중)     | 전후로 서버의 열린 fd 수가 같고 `<defunct>` 프로세스 없음 (Linux) |
| `trap` 등으로 SIGPIPE·시그널 설정을 출력하는 CGI             | 기본값으로 시작함                           |

### 동시성 검사

- `make tsan`으로 Round-Robin 카운터와 Least Connections 카운터에 데이터 경쟁이 없는지 확인합니다.
