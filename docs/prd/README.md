# PRD 작성 방법

PRD(Product Requirements Document)는 무엇을 왜 만들지, 어디까지 만들지를 적은 문서입니다. 이 폴더는 팀원 각자의 초안을 모아 최종본 하나로 합치는 곳입니다.

## 순서

```text
1. 각자 초안 작성   docs/prd/<이름>.md   (각자 작업 브랜치에서)
2. 팀 회의          초안을 같이 읽고 후보 중 하나를 고름
3. 최종 PRD 작성    docs/prd/final.md   (정한 내용, 이유, 작업 체크리스트)
```

- **초안 파일:** `docs/prd/<이름>.md` 하나에 씁니다(예: `docs/prd/dabin.md`). 각자 자기 파일만 고치므로 같은 파일을 동시에 편집할 일이 없습니다.
- **최종 PRD:** 회의에서 정한 내용과 그 이유를 `docs/prd/final.md`에 모읍니다. 최종 PRD가 나온 뒤에는 초안을 고치지 않습니다. 초안은 그 시점의 생각을 남긴 기록이기 때문입니다.
- **작업 분배:** `final.md`의 작업 체크리스트에 담당자 이름을 적는 것으로 시작합니다. 티켓 파일이나 별도 결정 기록은 필요해지면 그때 만듭니다.

## 초안에 쓰는 것

LMS 문서(웹 서버 만들기)의 항목을 기준으로 씁니다. 범위는 아래 여섯 가지로 나눠 적습니다.

| 범위 | 뜻 | 예 |
| --- | --- | --- |
| LMS 필수 | LMS가 반드시 구현하라고 한 것 | Proxy와 Reverse Proxy 중 최소 하나, 동시성 방식 하나 이상 |
| LMS 권장 | LMS가 하면 더 좋다고 한 것 | 스레드 풀(pthread를 고를 때), 두 프록시 모두 구현, Round-Robin 로드 밸런싱 |
| LMS 선택 | LMS가 선택으로 둔 것 | Forward Proxy 캐싱 |
| LMS 품질 항목 | LMS의 "품질" 절이 정한 검사 종류 | 단위 테스트, 기능 테스트, 부하 테스트, 메모리 누수 검사, 엣지 케이스 |
| 팀 합의 | LMS에는 없지만 팀이 정한 것 | 실행 인자 형식, 각 검사의 세부 시나리오(어떤 요청을 몇 개, 어떤 도구로) |
| 하지 않는 것 | 일부러 범위에서 뺀 것 | |

| 절 | 내용 |
| --- | --- |
| 목표 | 무엇을 만들고, 어떤 상태가 되면 끝인지 |
| 범위 | 위 여섯 가지 구분 |
| 결정할 것 | 동시성 모델, Proxy 방식 등 회의에서 정할 항목과 각 후보의 구현 난이도, 디버깅 난이도 |
| 요청 흐름 | 요청 하나가 연결 수락부터 응답까지 거치는 단계 |
| 테스트 | 각 기능을 curl, 로그, 단위 테스트로 어떻게 확인할지 |
