# 엣지케이스: 브라우저·로드밸런싱 검증 중 찾은 것

> 기준 코드: `demo/bloro` 브랜치 (75d1a3d). 확인일 2026-11-25, macOS.
> 정상 경로의 테스트 케이스는 [`test-cases.md`](test-cases.md)에 있습니다.

판정 기준:

- 🐞 **버그 후보**: 사용자가 정상이라고 기대할 요청이 실패합니다. 고칠지 팀에서 정합니다.
- ⚠️ **알아 둘 동작**: 의도했거나 범위 밖이지만, 발표나 확장할 때 헷갈릴 수 있습니다.
- ✅ **의도대로**: 경계에서 맞게 동작함을 확인했습니다.

"확인 방법"이 `실행`이면 직접 요청을 보내 결과를 봤고, `코드`면 코드를 읽고 판단했습니다.

## 브라우저 / 정적 파일 / CGI

### E-01 🐞 정적 파일에 쿼리 문자열을 붙이면 404

- **확인 방법:** 실행
- **재현:**
  ```sh
  curl -s -o /dev/null -w '%{http_code}\n' 'http://localhost:8000/style.css?v=2'   # 404
  curl -s -o /dev/null -w '%{http_code}\n' 'http://localhost:8000/home.html?x=1'   # 404
  ```
  404 본문에 `./home.html?x=1`처럼 `?` 뒤까지 파일 이름으로 찍힙니다.
- **원인:** `src/main/tiny.c`의 `uri_parse`가 `cgi-bin`이 아닌 경로에서는 `?`를 자르지 않고 URI 전체를 파일 이름으로 씁니다. CGI 쪽은 `?` 앞까지만 씁니다.
- **영향:** 브라우저와 프레임워크가 흔히 쓰는 캐시 무효화(`style.css?v=2`), 추적 파라미터(`?utm_source=...`)가 붙은 링크가 모두 깨집니다.
- **기대:** `?` 앞 경로로 파일을 찾고 200.

### E-02 🐞 경로 어디에든 `cgi-bin`이 있으면 CGI로 취급

- **확인 방법:** 실행 (임시 루트에 `docs/cgi-bin-guide.html` 생성)
- **재현:** `GET /docs/cgi-bin-guide.html` → **403** (같은 폴더의 `plain.html`은 정상)
- **원인:** `uri_parse`가 `strstr(uri, "cgi-bin")`으로 판단해서, `/cgi-bin/`으로 시작하는 경로가 아니라 문자열 `cgi-bin`이 들어간 모든 경로를 CGI로 봅니다. 실행 권한이 없는 HTML이라 403이 납니다.
- **기대:** `/cgi-bin/`으로 시작할 때만 CGI. Tiny 원본에서 물려받은 동작입니다.

### E-03 ⚠️ 퍼센트 인코딩을 풀지 않음

- **확인 방법:** 실행
- **재현:** `/crying%5Fcat.jpg` (`_` = `%5F`) → 404. `/crying_cat.jpg`는 200.
- **영향:** 지금 데모 파일 이름은 영문·숫자·`_`·`.`뿐이라 브라우저가 인코딩하지 않아 문제가 없습니다. 파일 이름에 공백이나 한글이 들어가면 브라우저가 `%20`, `%EA%B3%A0...`로 보내므로 404가 됩니다.

### E-04 ⚠️ `/favicon.ico` 404

- **확인 방법:** 실행
- 브라우저가 페이지를 열 때 스스로 요청합니다. Network 탭에 빨간 404 줄이 하나 생기는데 서버 오류가 아닙니다. 발표 중 질문이 나오면 이렇게 설명하거나, `demo/www/favicon.ico`를 넣어 없앨 수 있습니다.

### E-05 ⚠️ CGI 입력이 잘못돼도 200

- **확인 방법:** 실행
- | 요청 | 응답 |
  |---|---|
  | `?a=&b=` (빈 폼 제출) | 200, `Invalid number. Use integers like 1&2 or a=1&b=2` |
  | `?a=abc&b=2` | 200, 같은 문구 |
  | `?a=99999999999&b=1` (int 범위 밖) | 200, 같은 문구 |
  | `?a=-3&b=1.5` (소수) | 200, 같은 문구 |
  | `?a=+1&b=2` | 200, `1 + 2 = 3` (`+` 부호 허용) |
  | 인자 없음 | 200, `Usage: /cgi-bin/adder?1&2 or POST a=1&b=2` |
- `adder`가 오류 안내를 정상 페이지로 돌려줍니다. 사람에게는 충분하지만 상태 코드만 보는 쪽(스크립트, 모니터링)은 실패를 알 수 없습니다. 400으로 바꿀지는 선택입니다.
- 주의: 폼에 공백을 넣으면 브라우저가 `+`로 보냅니다(`" 1"` → `a=+1`). 그래서 앞 공백은 우연히 통과합니다.

### E-06 ✅ CGI 폴더 자체, 없는 CGI

- **확인 방법:** 실행
- `/cgi-bin/` → 403 (실행 파일이 아님), `/cgi-bin/nope` → 404. 서버는 계속 살아 있습니다.

## 로드밸런싱 / 리버스 프록시

### E-07 🐞 프록시를 거친 쿼리 문자열도 404

- **확인 방법:** 실행
- `/api/whoami.txt?x=1` → 프록시는 쿼리를 포함해 그대로 전달하고, 백엔드(tiny)가 E-01 때문에 404를 돌려줍니다. 프록시 쪽 문제는 아니고, 백엔드가 tiny일 때만 생깁니다. E-01을 고치면 함께 해결됩니다.

### E-08 ⚠️ 접두사 자체와 끝의 `/`

- **확인 방법:** 실행
- `/api` → 403: 규칙에 걸려 백엔드로 가고, 백엔드에서 `./api`가 폴더라 "정규 파일이 아님"으로 403입니다.
- `/api/` → 404: 백엔드가 `./api/home.html`을 찾는데 없습니다.
- 일반 웹 서버라면 `/api` → `/api/`로 301 리다이렉트를 하겠지만, 이 서버는 리다이렉트를 하지 않습니다.

### E-09 ⚠️ 헬스 체크가 없어 꺼진 백엔드에도 계속 차례가 돌아감

- **확인 방법:** 실행 + 코드 (`src/proxy.c`의 `backends_try`)
- Round-Robin 순번(`proxy_backend_start`)은 백엔드가 살아 있는지와 상관없이 매 요청 1씩 오릅니다. A가 꺼진 상태에서는 A 차례인 요청이 매번 A에 연결을 시도하고, 실패하면 B로 넘어갑니다.
- 같은 컴퓨터에서는 꺼진 포트가 바로 연결 거부(`ECONNREFUSED`)를 돌려주므로 지연이 거의 없습니다 (L-07에서 확인).
- 하지만 백엔드가 다른 컴퓨터이고 패킷을 그냥 버리는 경우(전원 꺼짐, 방화벽)에는 **A 차례인 요청마다 연결 시간 상한 `PROXY_CONNECT_MS`(3초)를 기다린 뒤** B로 넘어갑니다. 요청 절반이 3초씩 느려집니다. `test_connect_timeout_mixed_is_504`가 이 경로를 일부 다루지만 macOS에서는 skip됩니다.
- 반대로 E-15처럼 복구도 자동이라는 장점이 있습니다.

### E-10 ⚠️ 연결 뒤의 실패는 재시도하지 않음

- **확인 방법:** 코드 (`proxy_forward`)
- 다음 백엔드로 넘어가는 것은 **연결 단계의 실패**뿐입니다. 연결된 뒤에 백엔드가
  - 응답 헤더 전에 끊으면 → 502
  - 시간 안에 답하지 않으면 → 504
  - 본문 도중 끊으면 → 클라이언트 연결을 닫음(길이를 모르면 RST)
- 요청을 이미 보낸 뒤라 POST를 두 번 실행할 위험이 있으므로 재시도하지 않는 것이 안전한 선택입니다. 다만 "백엔드 하나가 죽어도 사용자는 모른다"는 설명은 연결 단계에만 맞습니다.
- 백엔드가 500을 돌려주는 것은 "정상 응답"이라 그대로 전달합니다.

### E-11 ⚠️ 경로 접두사를 떼지 않고 전달

- **확인 방법:** 실행 (`demo/lb/www_a/api/whoami.txt` 구조)
- `/api/whoami.txt`는 백엔드에도 `/api/whoami.txt`로 갑니다. 그래서 백엔드 루트 안에 `api/` 폴더가 있어야 합니다. nginx의 `proxy_pass http://b/;`처럼 접두사를 떼는 기능은 없습니다.

### E-12 ⚠️ (데모) 포트를 바꿔도 응답 문구는 8001/8002

- **확인 방법:** 실행
- `demo/lb/www_a/api/whoami.txt`의 내용이 `나는 서버 A (포트 8001)`로 고정돼 있습니다. `BASE=9000`으로 실행하면 실제 포트는 9001인데 본문은 8001이라고 말합니다. A/B 구분에는 문제가 없지만, 발표에서 포트를 바꿨다면 "문구는 고정 텍스트"라고 말해 두면 좋습니다.

### E-13 ⚠️ (데모) `web.sh`와 `lb.sh`의 포트 충돌

- **확인 방법:** 코드 (`demo/lb.sh`의 `wait_port`)
- 둘 다 8000을 씁니다. `web.sh`를 끄지 않고 `lb.sh`를 실행하면 프록시가 포트를 열지 못합니다. 그런데 `wait_port`는 그 포트에서 응답이 오기만 하면 통과하므로, 이미 떠 있는 `web.sh` 서버가 대신 답해서 스크립트가 멈추지 않고 진행될 수 있습니다. 그러면 `/api/whoami.txt`가 A/B 대신 404로 보입니다. 순서대로 하나씩 실행합니다.

### E-14 ✅ keep-alive 연결 하나 안에서도 요청마다 분배

- **확인 방법:** 실행 (`curl`에 URL 4개 → 한 연결)
- A, B, A, B. 분배 단위가 연결이 아니라 요청입니다. 세션 고정(sticky session)은 없습니다.

### E-15 ✅ 꺼진 백엔드가 다시 켜지면 바로 복구

- **확인 방법:** 실행
- A를 끄면 B만 응답하고, A를 다시 켜면 다음 요청부터 A, B 번갈아 응답합니다. 프록시를 다시 시작할 필요가 없습니다 (E-09의 헬스 체크가 없는 구조 덕분).
