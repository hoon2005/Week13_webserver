# Phase 2 PRD: M6 리버스 프록시와 M7 안정성 (yehoon)

> 개인 PRD 초안. 구현 계획 카드의 M6, M7 범위와 리뷰에서 나온 "세 문서 모두 빠뜨린 것"을 다룸. M4·M5(phase2/yehoon)가 끝난 코드 위에서 진행함.

## 목표와 범위

**M6 리버스 프록시**

- 서버가 직접 답하지 않고, 뒤에 있는 백엔드 서버에 요청을 대신 전달해서 받은 답을 손님에게 돌려줌
- 목표 달성 기준
  - 같은 도메인으로 반복 요청하면 백엔드 2개에 번갈아 전달됨 (백엔드 로그에 번갈아 찍힘)
  - GET, POST 모두 백엔드까지 전달되고 응답이 그대로 돌아옴
  - 백엔드를 끄면 502, 백엔드가 응답하지 않으면 504
  - 라우팅 표에 없는 도메인은 지금처럼 정적 파일·CGI로 직접 응답함 (기존 테스트 그대로 통과)

**M7 안정성**

- 끊김, 이상한 요청, 종료 신호가 와도 서버가 죽지 않고 자원을 정리함
- 목표 달성 기준
  - 서버 Ctrl+C → 처리 중이던 응답을 마치고 종료 로그를 남기며, 누수 보고(LeakSanitizer)가 없음
  - 메서드 형식 오류 400, 지원하지 않는 메서드 501이 구분됨
  - 헤더를 아주 천천히 보내는 연결(Slowloris)이 10초 안에 끊김

**카드와 달라지는 부분**

- 라우팅 기준: 카드는 "경로별 라우팅"인데 **Host 헤더 기준**으로 결정함
- Forward 관련 항목(요청 URL에서 호스트 꺼내기, `curl -x` 확인 명령)은 범위에서 제외
- 캐싱(선택)은 범위에서 제외

**이번 범위에서 제외**

- Forward Proxy, 캐싱
- 백엔드 연결 재사용(풀링), 백엔드 헬스 체크
- 설정 파일 (라우팅 규칙은 실행 인자로만 받음)

## 설계 선택: M6 리버스 프록시

### M6-1. 프록시 범위 (Forward와 Reverse 둘 다 / Reverse만 / Forward만) → Reverse만

동작

- 손님은 우리 서버에만 접속하고, 우리 서버가 정해진 규칙으로 뒤의 백엔드에 요청을 나눠 보냄

선택 이유

- 팀 결정
- 과제 필수 조건(최소 1개)을 충족함
- 라우팅과 Round-Robin으로 로드 밸런싱까지 보여 줄 수 있음

장점

- 라우팅과 로드 밸런싱에 집중할 수 있음

단점

- Forward까지 하면 받을 수 있는 가산점은 없음

선택하지 않은 선택지

- Forward와 Reverse 둘 다: 필수 범위를 넘고, Forward용 URL 해석과 임의 호스트 연결까지 만들어야 해서 구현과 테스트가 거의 두 배가 됨
- Forward만: 백엔드 여러 개에 일을 나누는 로드 밸런싱을 보여 줄 수 없음

### M6-2. 프록시 실행 방식 (같은 tiny에 옵션으로 켜기 / 프록시 전용 실행 파일) → 같은 tiny에 옵션으로 켜기

동작

- 실행할 때 `--route` 옵션을 주면 프록시 기능이 켜짐
- 옵션이 없으면 지금과 똑같이 정적 파일·CGI만 처리함

선택 이유

- M4·M5에서 만든 스레드 풀, 요청 파서, keep-alive, 오류 응답을 그대로 재사용함
- 옵션이 없으면 지금과 똑같이 동작해서 기존 테스트에 영향이 없음
- M6-4(규칙에 없는 요청은 직접 처리)도 이 방식이어야 가능함

장점

- 다시 만들 것이 거의 없음
- 한 서버가 정적 파일과 프록시를 같이 처리할 수 있음

단점

- tiny.c가 커지고 일반 서버 코드와 프록시 코드가 한 파일에 섞임 (프록시 코드는 `src/proxy.c`로 분리해 완화)

선택하지 않은 선택지

- 프록시 전용 실행 파일: 역할은 분명해지지만, 스레드 풀과 파서를 공유 모듈로 빼고 다시 연결하는 작업이 분리해서 얻는 이점보다 큼. 실행 파일과 테스트 설정도 늘어남

### M6-3. 라우팅 기준 (경로 앞부분 / Host 헤더 / 둘 다) → Host 헤더

동작

- 요청의 Host 헤더를 보고 백엔드 그룹을 정함 (예: `api.local` → 백엔드 8001, 8002)
- Host 값의 포트를 떼고 비교함 (`api.local:8080` → `api.local`)
- 대소문자 구분 없이 비교함
- 요청 경로는 바꾸지 않고 그대로 백엔드에 전달함

선택 이유

- 실제 리버스 프록시처럼 도메인별로 서비스를 나눌 수 있음
- M5 파서가 이미 Host를 꺼내 두고 있고, HTTP/1.1은 Host가 필수라 항상 있음
- 경로를 손대지 않아 백엔드가 원래 요청을 그대로 처리함

장점

- 실제 서비스와 같은 구성
- 경로 변환 코드가 필요 없음

단점

- 로컬 테스트 때 Host를 직접 지정해야 함 (`curl -H "Host: api.local" localhost:8080/`)
- Host가 없는 HTTP/1.0 요청은 라우팅할 수 없음 (규칙에 없는 요청으로 처리)

선택하지 않은 선택지

- 경로 앞부분(`/api/*`): 구현은 쉽지만 한 도메인 안에서 경로로만 나눠서, 실제 리버스 프록시의 도메인별 분배를 보여 주지 못함
- 둘 다: Host와 경로가 둘 다 맞을 때의 우선순위까지 정해야 해서 규칙과 테스트가 두 배가 됨

### M6-4. 규칙에 없는 요청 (정적 파일·CGI로 직접 처리 / 404 / 기본 백엔드로 보냄) → 정적 파일·CGI로 직접 처리

동작

- 라우팅 표에 없는 Host(예: `localhost`)로 온 요청은 지금처럼 우리 서버가 정적 파일이나 CGI로 직접 답함

선택 이유

- 기존 요청(home.html, adder)과 테스트가 그대로 동작함
- M6-2를 같은 tiny로 했기 때문에 추가 코드 없이 따라옴

장점

- 기존 기능 유지
- "등록된 도메인은 백엔드로, 나머지는 직접" 구성으로 nginx와 비슷함

단점

- 서버가 하는 일이 두 가지라 설명할 때 구분이 필요함

선택하지 않은 선택지

- 404: 동작은 단순하지만, 지금 잘 되는 정적 파일 기능을 쓰려고 정적 파일용 백엔드를 하나 더 띄워야 해서 오히려 복잡해짐
- 기본 백엔드로 보냄: 직접 처리하면 되는 요청을 굳이 다른 서버로 보낼 이유가 없고, 설정이 하나 늘고 잘못 설정하면 엉뚱한 서버로 감

### M6-5. 백엔드 응답 읽기 (백엔드가 닫을 때까지 읽기 / Content-Length만큼 읽기) → Content-Length만큼 읽기

동작

- 백엔드 응답 헤더의 Content-Length를 보고 그만큼 본문을 읽음
- Content-Length가 없으면 백엔드가 닫을 때까지 읽고 손님 연결도 닫음

선택 이유

- 프록시를 거치는 요청도 손님 keep-alive가 유지됨
- M5의 "응답 길이를 알면 연결 유지" 규칙과 같음
- 백엔드가 우리 tiny면 M5 이후 모든 응답에 Content-Length가 있음

장점

- 손님 keep-alive 유지

단점

- 백엔드 응답 헤더를 해석해야 함

선택하지 않은 선택지

- 백엔드가 닫을 때까지 읽기: 가장 단순하지만 손님에게 응답 길이를 미리 알려 줄 수 없어서, 프록시 요청만 매번 연결을 끊어야 함. M5의 keep-alive가 의미 없어짐. 다만 Content-Length가 없는 응답에 한해서는 이 방식으로 대비함

### M6-6. 백엔드 시간 제한 (짧게: 연결 1초·응답 5초 / 중간: 연결 3초·응답 10초 / 길게: 응답 30초 이상) → 연결 3초, 응답 10초

동작

- 백엔드 연결이 거부되면 `502 Bad Gateway`
- 3초 안에 연결이 안 되거나, 10초 안에 응답이 오지 않으면 `504 Gateway Timeout`

선택 이유

- CGI 시간 제한(10초)과 같아서 "서버가 다른 프로그램을 기다리는 최대 시간은 10초"로 한 번에 설명됨
- 꺼진 백엔드는 대부분 연결이 즉시 거부돼서 502가 바로 나감

장점

- 정상 백엔드에 충분한 여유가 있음

단점

- 백엔드가 멈추면 작업자가 최대 10초 묶임
- 값은 M8 부하 테스트에서 조정할 수 있음

선택하지 않은 선택지

- 짧게: 죽은 백엔드에 오래 묶이지 않지만, 조금 느린 정상 응답까지 504로 실패시킬 수 있음
- 길게: 느린 백엔드도 기다려 주지만, 작업자 수가 고정인 스레드 풀에서 오래 묶이는 작업자가 생기면 전체가 느려짐

### M6 구현할 것 (결정 없이 정해진 항목)

중계 함수

- 순서: 요청 받기 → 대상 백엔드 정하기 → 백엔드 연결 → 요청 전달 → 응답 받기 → 손님에게 전달
- GET, POST 모두 중계
  - 백엔드에 보내는 것: 요청 줄 + M5가 보존한 원본 헤더 블록 + 본문
  - POST 본문은 M5에서 이미 읽어 둔 본문을 그대로 보냄
  - `Expect: 100-continue`는 우리 서버가 이미 손님에게 답했으므로 백엔드에는 빼고 보냄
  - 손님이 보낸 `Connection` 헤더는 빼고 `Connection: close`로 보냄
- 백엔드 연결은 요청마다 새로 맺음 (연결 재사용은 범위 밖)
- 백엔드 소켓에도 `FD_CLOEXEC`를 걸어 CGI 자식이 물려받지 않게 함 (M4 fd 상속 차단과 같은 규칙)

라우팅 표

- Host → 백엔드 목록 (`host:port` 여러 개)

Round-Robin

- 같은 도메인의 백엔드 여러 개에 요청을 번갈아 보냄 (8001 → 8002 → 8001 …)
- 여러 작업자가 같은 순서 번호를 올리므로 뮤텍스로 보호하고 `make tsan`으로 확인

502, 504 응답

- M5의 오류 응답 형식(Content-Length, Connection 포함)을 그대로 씀

라우팅 단위 테스트 (`tests/proxy_test.c`)

- Host로 백엔드 찾기, 포트 떼기와 대소문자 무시, Round-Robin 순서, 규칙에 없는 Host, `--route` 인자 해석

## 설계 선택: M7 안정성

### 이미 완료한 것

- SIGPIPE 무시 (Phase 1 안정성 수정)
- 큰 파일을 받다가 curl Ctrl+C → 서버 살아 있음
- 400 응답 (형식이 틀린 요청 줄·헤더, Host 없음, 잘못된 Content-Length 등)
- 413 큰 본문 (본문을 받기 전에 거절)
- 414 긴 URI (요청 줄이 MAXLINE 안에 끝나지 않으면 414, 400과 구분됨)
- 505 잘못된 HTTP 버전 (1.0, 1.1 외)
- 오류 응답 뒤 남은 데이터를 비우고 닫아, 응답이 RST로 사라지지 않게 함
- 포트, 정적 파일 폴더(`--root`), 작업자 수, 큐 크기, 타임아웃, 연결당 요청 수 상한을 실행 인자로 받음

### M7-1. 라우팅 규칙 받는 방법 (실행 인자 / 설정 파일 / 둘 다) → 실행 인자

동작

- 예: `--route api.local=127.0.0.1:8001,127.0.0.1:8002`
- 등호 왼쪽은 도메인(Host), 오른쪽은 쉼표로 구분한 백엔드 목록
- 도메인이 여러 개면 `--route`를 여러 번 줌
- 형식이 틀리면 시작할 때 사용법을 출력하고 종료함

선택 이유

- 지금의 `--root`, `--threads`와 같은 방식이라 인자 처리에 몇 줄만 더하면 됨
- 과제 조건도 "인자 또는 설정 파일"이라 인자만으로 충족함

장점

- 구현이 쉬움
- 테스트에서 규칙을 바꿔 서버를 띄우기 쉬움

단점

- 규칙이 많아지면 명령줄이 길어짐

선택하지 않은 선택지

- 설정 파일: 규칙이 많을 때는 읽기 쉽지만, 과제 범위의 규칙 몇 개를 위해 파일 형식과 파서, 형식 오류 처리를 새로 만드는 건 과함
- 둘 다: 두 방식을 모두 만들고 둘이 겹칠 때 우선순위까지 정해야 해서, 얻는 것에 비해 구현과 테스트가 두 배가 됨

### M7-2. 잘못된 형식의 메서드 판단 (영문자가 아니면 400 / RFC 토큰 규칙) → RFC 토큰 규칙

동작

- 메서드에 허용되지 않는 글자가 있으면 `400 Bad Request` (예: `G@T`, 제어 문자)
- 형식은 맞지만 지원하지 않는 메서드는 `501 Not Implemented` (예: `PUT`, `FOO`)
- 토큰 허용 글자: 영문 대소문자, 숫자, ``! # $ % & ' * + - . ^ _ ` | ~``
- 지금은 모르는 메서드를 형식과 상관없이 전부 501로 보냄 → 400과 501로 나눔

선택 이유

- 구현량은 단순 규칙과 거의 같은데(허용 글자 확인 함수 하나) 표준(RFC 9110)과 정확히 맞음
- 파서 안에서 끝나서 단위 테스트로 확인하기 쉬움

장점

- 표준을 근거로 설명할 수 있음

단점

- 허용 글자를 확인하는 함수가 필요함

선택하지 않은 선택지

- 영문자가 아니면 400: 규칙은 단순하지만, 표준상 허용되는 글자(`-`, `_` 등)가 들어간 정상 메서드 이름도 형식 오류로 잘못 판단함

### M7-3. 정적 파일 POST (405 + Allow 헤더 / 501 유지) → 405 + Allow: GET, HEAD (팀 합의 필요)

동작

- 정적 파일에 POST가 오면 `405 Method Not Allowed`와 함께 허용 메서드를 `Allow: GET, HEAD`로 알려 줌
- 지금은 501 → 405로 변경
- CGI와 프록시로 가는 POST는 그대로 정상 처리됨

선택 이유

- 501은 "서버가 모르는 메서드"라는 뜻인데, 우리 서버는 CGI와 프록시에서 POST를 처리함
- 405는 "알지만 이 대상에는 허용 안 함"이라 의미가 정확함

장점

- 상태 코드 의미가 정확함
- 손님이 허용 메서드를 알 수 있음

단점

- 기준선 테스트(`test_post_is_501`)와 기능 테스트를 고쳐야 함

선택하지 않은 선택지

- 501 유지: 바꿀 것은 없지만 상태 코드의 의미가 사실과 어긋남. 다만 테스트를 바꾸는 일이라 팀이 반대하면 501을 유지해도 과제 필수 항목에는 영향이 없음 (필수는 아님)

### M7-4. Slowloris 시간 제한 (5초 / 10초 / 20초 이상) → 요청 줄부터 헤더 끝까지 전체 10초

동작

- 요청 줄을 읽기 시작한 순간부터 헤더 끝의 빈 줄까지 전체 시간이 10초를 넘으면 응답 없이 연결을 닫음
- 지금은 읽을 때마다 5초 타이머가 다시 시작돼서, 한 글자씩 천천히 보내면 작업자를 계속 붙잡을 수 있음
- keep-alive의 다음 요청은 첫 바이트가 온 시점부터 잼 (요청을 기다리는 시간은 기존 5초 유휴 타임아웃이 담당)

선택 이유

- 정상 브라우저는 헤더를 한 번에 보내서 10초에 걸릴 일이 없음
- 리뷰에서 제안한 값이고, 다른 시간 제한(CGI 10초, 백엔드 응답 10초)과 같음

장점

- 정상 손님에게 넉넉함
- 구현이 작음

단점

- 공격 연결 하나가 작업자를 최대 10초 묶음

선택하지 않은 선택지

- 5초: 이미 줄마다 5초 읽기 타임아웃이 있어서, 전체도 5초로 하면 느린 네트워크의 정상 손님에게 너무 빡빡함
- 20초 이상: 아주 느린 손님도 안전하지만, 작업자가 16개뿐이라 공격 연결 몇 개만으로도 오래 막힘

### M7-5. 종료 시 응답 중인 손님 (끝까지 보내고 종료 / 바로 닫고 종료) → 끝까지 보내고 종료

동작

- Ctrl+C(SIGINT)나 종료 명령(SIGTERM)을 받아도 응답을 보내던 손님에게는 끝까지 보낸 뒤 종료함

선택 이유

- 종료 때문에 정상 손님이 피해를 보지 않음
- 늦어지는 시간에도 상한이 있음 (CGI 10초, 백엔드 응답 10초, 쓰기 타임아웃 10초)

장점

- 실제 서버들이 쓰는 graceful shutdown 방식

단점

- 큰 파일, CGI, 백엔드 응답이 끝날 때까지 종료가 늦어질 수 있음

선택하지 않은 선택지

- 바로 닫고 종료: 즉시 끝나고 구현이 단순하지만, 받던 손님이 깨진 응답을 받음. 카드의 "정리 후 종료"와도 맞지 않음

### M7-6. 종료 시 쉬는 keep-alive 연결 (바로 닫음 / 유휴 타임아웃으로 닫히게 둠) → 5초 유휴 타임아웃으로 닫히게 둠

동작

- 다음 요청을 기다리며 쉬는 연결은 기존 5초 읽기 타임아웃이 끝나면 닫힘
- 종료 중에는 응답 뒤 keep-alive를 하지 않고 `Connection: close`로 보내서, 쉬는 연결이 새로 생기지 않게 함

선택 이유

- 이미 있는 타임아웃이 처리해서 추가 코드가 거의 없음
- 늦어지는 시간이 최대 5초로 정해져 있음

장점

- 구현이 단순함

단점

- 종료가 최대 5초 늦어짐

선택하지 않은 선택지

- 바로 닫음: 종료는 빠르지만, 읽기에서 기다리는 작업자를 깨우려면 작업자마다 잡고 있는 연결을 기록하고 강제로 깨우는 장치가 필요함. 5초를 아끼려고 코드가 복잡해지고 동시성 버그 위험이 늘어남

### M7 구현할 것 (결정 없이 정해진 항목)

종료 처리 (SIGINT·SIGTERM)

- main이 작업자를 만들기 전에 SIGINT·SIGTERM을 막아 둠 (`pthread_sigmask`). 새로 만든 스레드는 이 설정을 물려받음
- 신호를 받는 전용 스레드 하나가 `sigwait`로 기다림
- 신호를 받으면
  1. 종료 플래그를 세움 (M7-6의 `Connection: close` 판단에 씀)
  2. 리스닝 소켓을 닫아 main의 accept를 멈추고 새 손님을 받지 않음
  3. `conn_queue_shutdown`으로 작업자를 깨움 (M4에서 만들어 둔 종료 플래그)
  4. 작업자가 처리 중이던 연결을 마치고 모두 끝날 때까지 `pthread_join`으로 기다림
  5. 큐와 작업자 목록, 라우팅 표 메모리 해제 → 종료 로그 출력 → 종료
- CGI 자식은 fork 전 막힌 신호를 물려받으므로, `execve` 전에 신호 막기를 풀어 줌

## 요청 흐름

```text
main
  신호 막기 → 신호 전용 스레드 → 리스닝 소켓 → 작업자 N개 → accept 반복

작업자: 연결 하나 처리 (keep-alive 반복)
  요청 줄 읽기 ─ 요청 줄~헤더 전체 10초 넘으면 닫음 (M7-4)
    메서드 형식 오류 → 400, 지원 안 함 → 501 (M7-2)
  헤더 읽기 → 헤더 검사 → (Expect) → 본문 읽기            (M5)
  Host가 라우팅 표에 있나? (M6-3)
    ├ 있음 → Round-Robin으로 백엔드 선택 → 연결 (3초, 거부 시 502)
    │        → 요청 줄 + 원본 헤더 + 본문 전달 → 응답 받기 (10초, 넘으면 504)
    │        → Content-Length만큼 손님에게 전달 (M6-5)
    └ 없음 → 지금처럼 직접 처리 (M6-4)
             정적 파일: GET·HEAD → 200, POST → 405 + Allow (M7-3)
             CGI: GET·POST → 실행
  keep-alive 판단 (종료 중이면 Connection: close) → 다음 요청 또는 닫기

신호 전용 스레드: SIGINT·SIGTERM → 리스닝 소켓 닫기 → 큐 종료 → join → 정리 → 종료 로그
```

예시

```bash
./build/tiny 8001 --root www-a &
./build/tiny 8002 --root www-b &
./build/tiny 8080 --route api.local=127.0.0.1:8001,127.0.0.1:8002
```

| 요청 (프록시 8080으로) | 결과 |
| --- | --- |
| `Host: api.local` GET /home.html | 8001로 전달 |
| `Host: api.local` GET /home.html (다시) | 8002로 전달 |
| `Host: api.local` POST /cgi-bin/adder (`a=1&b=2`) | 본문까지 백엔드에 전달, `1 + 2 = 3` |
| `Host: localhost` GET /home.html | 프록시가 직접 응답 |
| `Host: localhost` POST /home.html | 405, `Allow: GET, HEAD` |
| `Host: api.local`, 백엔드 둘 다 꺼짐 | 502 |
| `Host: api.local`, 백엔드가 10초 넘게 응답 없음 | 504 |
| `G@T / HTTP/1.1` | 400 |
| `PUT / HTTP/1.1` | 501 |
| 헤더를 한 글자씩 10초 넘게 보냄 | 연결 닫힘 |
| 서버 Ctrl+C | 처리 중 응답 마무리 → 종료 로그, 누수 보고 없음 |

## 검증 계획

준비

- `make` 후 백엔드 2개(8001, 8002)와 프록시(8080)를 위 예시처럼 띄움. 기능 테스트는 빈 포트를 골라 띄움
- 백엔드가 응답하지 않는 상황은 연결만 받고 아무것도 보내지 않는 테스트용 소켓으로 만듦

### M7

| 확인할 것 | 요청 / 방법 | 성공 기준 |
| --- | --- | --- |
| 메서드 형식 | `G@T / HTTP/1.1`, `PUT / HTTP/1.1` | 400, 501 |
| 정적 POST | `curl -i -d x localhost:8080/home.html` | 405, `Allow: GET, HEAD` |
| Slowloris | 헤더를 1초마다 한 글자씩 보냄 | 10초 안팎에 연결이 닫힘. 다른 손님은 정상 응답 |
| 종료 (응답 중) | 큰 파일을 천천히 받는 중 서버에 SIGTERM | 받던 파일을 끝까지 받고 서버 종료 |
| 종료 로그와 누수 | 개발 빌드(ASan)로 띄운 서버에 Ctrl+C | 종료 로그 출력, LeakSanitizer 보고 없음 |
| 기존 항목 | 긴 URI, 큰 Content-Length, 엉터리 요청 | 414, 413, 400 (이미 통과) |

단위 테스트

- 메서드 토큰 판단: 허용 글자, 허용되지 않는 글자, 빈 메서드
- `--route` 인자 해석: 정상, 백엔드 여러 개, 형식 오류(등호 없음, 포트 없음)
