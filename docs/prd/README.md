# PRD 작성 방법

PRD(Product Requirements Document)는 무엇을 왜 만들지, 어디까지 만들지를 적은 문서입니다. 이 폴더는 팀원 각자의 초안을 모아 최종본 하나로 합치는 곳입니다.

## 순서

```text
1. 각자 초안 작성      docs/prd/<이름>.md        (각자 작업 브랜치에서)
2. 팀 회의             초안을 같이 읽고 트레이드오프를 정함
3. 최종 PRD 작성       docs/prd/final.md
4. 구현 티켓으로 나눔  docs/prd/issues/<두 자리 번호>-<주제>.md
```

- **초안 파일:** `docs/prd/<이름>.md` 하나에 씁니다(예: `docs/prd/dabin.md`). 각자 자기 파일만 고치므로 브랜치를 합칠 때 충돌이 나지 않습니다. 길어지면 `docs/prd/<이름>/` 폴더로 나눠도 됩니다.
- **최종 PRD:** 회의에서 정한 답을 `docs/prd/final.md`에 씁니다. 최종 PRD가 나온 뒤에는 초안을 고치지 않습니다. 초안은 그 시점의 생각을 남긴 기록이기 때문입니다.
- **티켓:** 최종 PRD를 PR 하나 크기의 작업으로 나눠 `docs/prd/issues/`에 파일 하나씩 둡니다. 번호는 `01`부터 셉니다. 작업을 시작한 사람은 파일 맨 위에 `담당: <이름>`을 적습니다.

## 초안에 쓰는 것

LMS 문서(웹 서버 만들기)의 항목을 기준으로 씁니다. 필수 항목과 선택 항목, 팀이 따로 정한 범위를 구분합니다.

| 절 | 내용 |
| --- | --- |
| 목표 | 무엇을 만들고, 어떤 상태가 되면 끝인지 |
| 범위 | LMS 필수 / LMS 선택 / 하지 않는 것 |
| 결정할 것 | 동시성 모델, Proxy 방식 등 회의에서 정할 항목과 각 후보의 구현 난이도, 디버깅 난이도 |
| 요청 흐름 | 요청 하나가 연결 수락부터 응답까지 거치는 단계 |
| 테스트 | 각 기능을 curl, 로그, 단위 테스트로 어떻게 확인할지 |
