# Phase 2 PRD: M4 동시성과 M5 HTTP 완성 (yehoon)

> 개인 PRD 초안. 구현 계획 카드의 M4, M5 범위만 다룸.

## 목표와 범위

**M4 동시성**

- 손님을 한 명씩 받던 서버가 여러 명을 동시에 받게 바꿈
- 만들 것
  - 먼저: 가장 단순한 형태 (연결마다 스레드 하나)
  - 그다음: 스레드 풀 (작업 큐 + 작업자 스레드 묶음)
  - CI에 make tsan 추가
- 목표 달성 기준: 한 손님이 연결만 걸어 두고 있어도 다른 손님이 바로 응답을 받음

**M5 HTTP 완성**

- 건너뛰던 헤더와 본문을 읽고, POST와 연결 재사용(keep-alive)을 처리함
- 만들 것
  - 먼저: 헤더에서 Content-Length를 꺼내 그만큼 본문 읽기
  - 헤더 파싱 (Host, Content-Length, Connection)
  - CGI POST, keep-alive
  - MIME 추가 (CSS, JS), 500 응답
  - 파서 단위 테스트 (tests/http_test.c)
- 목표 달성 기준: POST 본문이 CGI 프로그램에 전달되고, 한 연결에서 요청 두 개가 처리되고(Re-using existing connection), CSS와 JS가 올바른 Content-Type으로 응답됨

## 설계 선택: M4 동시성

### M4-1. 동시성 모델: 스레드 (단순한 형태 → 스레드 풀)

단계

1. 연결마다 스레드 하나: accept한 연결마다 스레드를 만들어 처리하고, 끝나면 스레드가 스스로 끝남 (detach)
2. 스레드 풀: 1단계가 동작하는 것을 확인한 뒤, 미리 만든 작업자 스레드와 작업 큐로 바꿈

선택 이유

- 지금 코드 구조를 거의 그대로 쓸 수 있음. doit 하나가 연결 하나를 처음부터 끝까지 처리하므로, 스레드는 connfd로 doit을 부르고 닫기만 하면 됨
- doit 안의 변수가 모두 지역 변수라 스레드끼리 공유하는 데이터가 거의 없음. 락으로 보호할 대상이 작업 큐 하나뿐
- 블로킹 읽기·쓰기를 그대로 쓸 수 있음. 한 스레드가 기다리는 동안 다른 스레드가 다른 손님을 처리함. 이벤트 루프였다면 읽기·쓰기를 non-blocking으로 바꾸고 연결별 상태를 저장하도록 다시 짜야 함
- pthread는 POSIX 표준이라 리눅스와 macOS CI를 같은 코드로 통과함
- 단순한 형태를 먼저 만들면 동시 처리 자체를 먼저 확인할 수 있고, 스레드 풀로 바꾼 뒤 성능을 비교할 기준이 생김

장점

- 프로세스를 복제하는 fork보다 가볍고 빠름
- 스레드 풀은 스레드를 미리 만들어 두어 요청마다 생성 비용이 없고, 스레드 수가 정해져 있어 손님이 몰려도 자원 사용이 늘지 않음

단점

- 메모리를 공유해서 실수로 공유 변수를 만들면 데이터 경합이 생김 (make tsan으로 확인)
- 한 스레드가 잘못된 메모리 접근으로 죽으면 서버 전체가 죽음
- 연결마다 스레드 방식은 손님이 몰리면 스레드가 끝없이 늘어남 (스레드 풀로 해결)

다른 방식을 고르지 않은 이유

| 방식 | 고르지 않은 이유 |
| --- | --- |
| fork (연결마다 프로세스) | 요청마다 프로세스를 복제해서 비용이 크고, 끝난 자식 회수(SIGCHLD)를 새로 처리해야 함 |
| 이벤트 루프 (select, poll, epoll, kqueue) | 블로킹 읽기·쓰기와 CGI 대기 때문에 거의 다 다시 작성해야 함. epoll과 kqueue는 OS별로 달라 두 OS CI를 맞추기 어려움 |

### M4-2. 스레드 풀 구조: 원형 배열 작업 큐 + 작업자 스레드 N개

동작

- 서버 시작 시 작업자 스레드 N개와 작업 큐를 만듦
- 작업 큐는 고정 크기 원형 배열. 앞(꺼낼 위치), 뒤(넣을 위치), 개수를 저장하고, 배열 끝에 닿으면 처음 칸으로 돌아감
- 큐를 건드리는 동안은 락(mutex)으로 잠금
- 조건 변수 두 개
  - 큐가 비면 작업자가 "일감 있음" 신호를 기다림
  - 큐가 가득 차면 메인 스레드가 "빈자리 있음" 신호를 기다림

선택 이유

- 큐에 넣는 값이 connfd(정수) 하나뿐이라 배열로 충분함
- 넣고 뺄 때 메모리 할당이 없어 빠르고 메모리 누수가 없음

장점

- 구현이 단순함
- 큐가 가득 차면 메인 스레드가 기다리므로 연결이 끝없이 쌓이지 않음

단점

- 스레드 수와 큐 크기를 정해야 함. 처음에는 상수로 두고 부하 테스트로 조정
- 연결 하나가 작업자 하나를 계속 잡고 있으므로, keep-alive로 쉬는 연결이 많으면 작업자가 모자랄 수 있음 (M5-4의 유휴 타임아웃으로 해결)

구현 시 주의

- 스레드 풀에서 CGI를 실행하면, fork한 자식은 실행(execve) 전까지 메모리를 할당하는 함수를 쓰면 안 됨. setenv 대신 fork 전에 환경 변수 배열(QUERY_STRING 등)을 만들어 execve에 넘김
- CGI 자식 회수는 자기 자식만 기다리는 waitpid(pid)를 그대로 씀 (이미 반영됨)

## 설계 선택: M5 HTTP 완성

### M5-1. 헤더 파싱: 요청 구조체에 이름·값 쌍으로 저장

동작

- 요청 구조체에 메서드, URI, 버전, 헤더 목록, 본문, 본문 길이를 담음
- 헤더 한 줄을 콜론 기준으로 이름과 값으로 나누고, 값 앞뒤 공백을 지워 배열에 저장
- 찾을 때는 이름을 대소문자 구분 없이 비교 (Content-Length와 content-length를 같게 봄)
- Host, Content-Length, Connection을 꺼내 씀

선택 이유

- 지금은 메서드, URI, 버전을 변수로 따로 넘김. 헤더와 본문까지 늘어나면 구조체 하나로 넘기는 게 간단함
- 헤더 이름은 대소문자를 구분하지 않는 것이 HTTP 규칙임

장점

- 파서만 따로 단위 테스트하기 쉬움 (tests/http_test.c)
- 헤더를 전부 저장해 두어 나중에 다른 헤더가 필요해도 다시 읽을 필요가 없음

단점

- keep-alive로 요청을 반복 처리할 때 구조체를 매번 초기화해야 함
- 헤더 개수에 상한을 둬야 함

### M5-2. 본문 읽기: Content-Length만큼 정확히 읽기

동작

- 헤더가 끝난 빈 줄 바로 다음부터 Content-Length 값만큼 읽음
- 본문 크기만큼 malloc하고, 요청 처리가 끝나면 free
- Content-Length가 숫자가 아니거나 다 읽기 전에 연결이 끊기면 요청 종료

선택 이유

- 본문에는 끝 표시가 없어서 Content-Length로만 끝을 알 수 있음
- 정확히 그 길이만큼 읽어야 keep-alive에서 다음 요청과 경계가 섞이지 않음

장점

- 필요한 만큼만 메모리를 씀

단점

- malloc과 free 짝을 오류 경로에서도 맞춰야 함 (ASan으로 확인)
- Content-Length 없이 조각으로 보내는 방식(chunked)은 지원하지 않음

### M5-3. CGI POST: 파이프로 표준 입력에 전달

동작

- fork 전에 파이프를 만들고, 환경 변수 배열에 REQUEST_METHOD, CONTENT_LENGTH, QUERY_STRING을 넣음
- 자식: 파이프의 읽는 쪽을 표준 입력, 소켓을 표준 출력으로 연결한 뒤 CGI 실행
- 부모: 본문을 파이프에 쓰고 닫음 → 자식을 회수
- CGI 프로그램은 표준 입력에서 CONTENT_LENGTH만큼 읽음 (adder도 POST를 받도록 수정)

선택 이유

- CGI 표준이 POST 본문을 표준 입력으로 넘기는 방식임
- 임시 파일처럼 만들고 지우는 관리가 필요 없음

장점

- 표준 방식이라 다른 CGI 프로그램도 그대로 동작함

단점

- 부모가 파이프의 쓰는 쪽을 닫지 않으면 자식이 입력 끝을 기다리며 멈추므로 닫는 순서를 지켜야 함
- 확인 명령은 a=1&b=2 형식으로 보냄. 지금 adder는 1&2 형식만 읽으므로, 이름=값 형식을 읽도록 adder를 고치거나 확인용 CGI 프로그램을 하나 정해야 함

### M5-4. keep-alive: 연결 하나에서 요청 반복 처리

동작

- 작업자 스레드가 connfd를 받으면, 연결이 끝날 때까지 "요청 읽기 → 처리 → 응답"을 반복함
- 판단 규칙
  - HTTP/1.1: 기본 유지, Connection: close면 닫음
  - HTTP/1.0: 기본 닫음, Connection: keep-alive면 유지
  - CGI 응답 뒤에는 닫음 (CGI 프로그램이 Connection: close를 보냄)
- 모든 응답(오류 응답 포함)에 Content-Length와 Connection 헤더를 넣음
- 읽기 버퍼(rio)는 연결당 한 번만 준비함
- 소켓 읽기 타임아웃(SO_RCVTIMEO, 5초 정도)을 걸어 요청 없이 쉬는 연결을 닫음

선택 이유

- 브라우저는 HTML, CSS, 이미지를 같은 연결로 연속 요청하므로, 연결을 재사용하면 연결을 맺는 시간(3-way handshake)이 줄어듦
- 클라이언트는 Content-Length가 있어야 응답의 끝을 알 수 있음. 지금 오류 응답에는 Content-Length가 없음
- 스레드 풀에서는 쉬는 연결이 작업자를 계속 잡고 있으면 다른 손님이 처리되지 못하므로 타임아웃이 필요함

장점

- 연결을 맺고 끊는 비용과 서버의 TIME_WAIT 연결이 줄어듦

단점

- 요청마다 구조체 초기화와 본문 해제를 빠짐없이 해야 함
- 타임아웃이 짧으면 재사용 효과가 줄고, 길면 작업자가 오래 묶임. 스레드 수와 함께 조정

### M5-5. MIME 추가와 500 응답

동작

- MIME 표에 두 줄 추가: .css → text/css, .js → text/javascript
- 서버 내부 실패(파일 열기, mmap 실패 등)에는 500 Internal Server Error (안정성 수정 때 일부 반영됨. 새로 생기는 실패 경로에도 적용)

선택 이유

- 브라우저는 Content-Type을 보고 CSS와 JS를 적용함. text/plain으로 보내면 스타일과 스크립트가 적용되지 않음
- 서버 쪽 문제를 클라이언트 문제(4xx)와 구분해서 알려 줌

장점

- MIME은 표에 한 줄씩 넣으면 되어 변경이 작음

단점

- 지금 MIME 판단은 이름 어딘가에 확장자가 들어 있으면 그 타입으로 봄 (예: a.css.txt도 CSS). 카드 범위에서는 그대로 둠
