## 1. 목표와 범위

### M4 완료 기준

- 터미널 A에서 `nc localhost 8000`으로 연결만 걸어 둔 상태에서, 터미널 B의 `curl`이 바로 `200`을 받습니다.
- 정적 파일과 CGI를 섞은 동시 요청 50개가 모두 정상 응답을 받고, 좀비 프로세스가 남지 않습니다.
- 요청을 보내지 않는 연결은 읽기 타임아웃 뒤 서버가 닫습니다.
- `make tsan`이 경고 없이 통과하고 CI에서 돌아갑니다.
- 기존 기능 테스트(`make verify`)가 그대로 통과합니다.

### M5 완료 기준

- `curl -d "a=1&b=2" localhost:8000/cgi-bin/adder`의 본문 7바이트가 CGI에 전달되어 `1 + 2 = 3`을 받습니다.
- 한 연결에서 요청 두 개가 처리됩니다 (curl 로그에 `Re-using existing connection`).
- CSS, JS가 올바른 `Content-Type`으로 응답됩니다.
- CGI 실패는 `500`, 시간 초과는 `504`를 받습니다.
- 1 MiB를 넘는 본문은 본문을 받기 전에 `413`으로 거절됩니다.
- 파서 단위 테스트 `tests/http_test.c`가 통과합니다.

### 이번 범위 밖

| 항목                   | 처리          | 이유                                                                           |
| ---------------------- | ------------- | ------------------------------------------------------------------------------ |
| 이벤트 루프            | 하지 않음     | 지금 코드를 non-blocking 상태 머신으로 다시 짜야 함. 10장에서 재검토 조건 정리 |
| 큐가 가득 찼을 때 503  | 하지 않음     | 고정 동시 수 부하에서는 기다림이 낫음                                          |

## 2. M4 동시성

### 2.1 동시성 모델

|                       | 멀티프로세스 (`fork`)  | 스레드 풀 (`pthread`)                          | 이벤트 루프 (`poll`/`epoll`/`kqueue`) |
| --------------------- | ---------------------- | ---------------------------------------------- | ------------------------------------- |
| 방식                  | 연결마다 자식 프로세스 | 미리 만든 N개 스레드가 큐에서 연결을 꺼내 처리 | 스레드 하나가 준비된 연결만 골라 처리 |
| 메모리                | 가장 무거움            | 스레드마다 스택                                | 가장 가벼움                           |
| 격리                  | 한 요청이 죽어도 무사  | 서버 전체가 죽음                               | 서버 전체가 죽음                      |
| 공유 데이터           | 따로 씀                | 같이 씀 → 락 필요                              | 락이 거의 없음                        |
| 느린 연결, keep-alive | 프로세스 하나가 묶임   | **스레드 하나가 묶임**                         | 묶이지 않음                           |
| 동시 연결 한계        | 수백                   | 풀 크기                                        | 수만 (C10K)                           |
| 지금 코드에서 바꿀 양 | 작음                   | 작음                                           | **큼**                                |

**스레드 풀을 선택합니다.**

- 과제가 "요청 처리 스레드 풀 권장"이라고 적었습니다.
- `doit` 하나가 연결 하나를 처음부터 끝까지 처리하므로 blocking 코드(`rio_readlineb` 등)를 그대로 씁니다. 이벤트 루프는 연결마다 "어디까지 읽었는지"를 저장하도록 M2, M5 코드를 모두 다시 짜야 하고, CGI 대기도 이벤트로 바꿔야 합니다.
- pthread는 POSIX 표준이라 Linux와 macOS CI를 같은 코드로 통과합니다. epoll과 kqueue는 OS마다 다릅니다.
- 스레드 수가 N개로 고정되어, 손님이 몰려도 자원 사용이 늘지 않습니다.

**약점:** 놀고 있는 연결도 작업자 하나를 붙잡습니다. 읽기 타임아웃(2.4)과 연결당 요청 수 상한(5장)으로 버팁니다. 우리 테스트는 수십~수백 연결 수준이라 이것으로 충분하다고 봅니다.

**단계:** 연결당 스레드(`pthread_create` + `pthread_detach`)를 커밋 하나로 먼저 만들어 동시 처리를 확인하고, 바로 스레드 풀로 바꿉니다. 이 커밋은 M8에서 비교 기준으로 씁니다.

```c
/* M4-1: 연결당 스레드 (비교 기준용) */
while (1) {
    int *connfdp = malloc(sizeof(int));   /* &connfd를 넘기면 다음 accept가 덮어씀 */
    *connfdp = accept(listenfd, ...);
    pthread_create(&tid, NULL, conn_thread, connfdp);
}

void *conn_thread(void *arg) {
    int connfd = *(int *)arg;
    free(arg);
    pthread_detach(pthread_self());
    serve_connection(connfd);
    close(connfd);
    return NULL;
}
```

### 2.2 스레드 풀과 작업 큐

```
main 스레드:   accept → 소켓 옵션 설정 → 큐에 connfd 넣기 (가득 차면 not_full 대기) → 반복
작업자 N개:    큐에서 connfd 꺼내기 (비면 not_empty 대기) → serve_connection → close → 반복
```

- 큐는 `head`, `tail`, `count`를 가진 고정 크기 원형 배열입니다. 배열 끝에 닿으면 처음 칸으로 돌아갑니다.
- 넣기와 꺼내기를 모두 mutex로 감쌉니다. 락이 없으면 두 작업자가 같은 connfd를 꺼내거나 연결 하나가 사라질 수 있습니다.
- 조건 변수에서 깨어나면 `while`로 조건을 다시 확인합니다 (다른 작업자가 먼저 꺼냈거나 spurious wakeup).
- **락은 큐를 만지는 순간에만 잡습니다.** `serve_connection`을 락 안에서 부르면 한 번에 한 요청만 처리됩니다.
- 종료 처리(M7)를 위해 큐에 `shutdown` 플래그를 두고, 플래그가 서면 `pthread_cond_broadcast`로 작업자를 모두 깨웁니다.

**큐가 가득 차면 main이 기다립니다.**

|                | main 기다림 (선택)                             | 503 후 닫기                                          |
| -------------- | ---------------------------------------------- | ---------------------------------------------------- |
| 넘친 손님      | 커널 backlog에서 기다렸다가 늦게라도 응답 받음 | 바로 실패                                            |
| 잠깐 몰린 경우 | 모두 처리됨                                    | 조금만 기다리면 처리될 손님도 거절됨                 |
| 계속 과부하    | 줄이 길어져 결국 타임아웃                      | 받은 손님의 응답 시간을 지킴                         |
| 구현           | `pthread_cond_wait` 하나                       | 503 작성, 읽지 않은 요청 때문에 RST가 나지 않게 처리 |

main이 기다리는 동안 멈추는 것은 새 연결을 꺼내는 일(accept)뿐이고, 작업자는 계속 처리합니다. 처리량은 작업자 수가 정하므로 503이 더 효율적이지는 않습니다.

### 2.3 작업자 수와 큐 크기

| 값                    | 기본값              | 근거                                                                                                                                                                          |
| --------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 작업자 수             | 16                  | CPU 계산보다 네트워크, 디스크, CGI를 기다리는 시간이 길어 코어 수보다 많아도 됨. keep-alive로 쉬는 연결이 작업자를 붙잡으므로 여유를 둠. M8에서 1, 4, 8, 16, 32를 측정해 확정 |
| 큐 크기               | 64                  | 처리 대기 중인 연결의 한도. 넘치면 커널 backlog로 넘어감                                                                                                                      |
| 본문 버퍼 최대 메모리 | 1 MiB × 16 = 16 MiB | 본문 상한(3.3) × 작업자 수. CGI 출력 버퍼까지 합치면 최대 32 MiB                                                                                                              |

### 2.4 타임아웃

accept 직후 `setsockopt`로 `SO_RCVTIMEO`, `SO_SNDTIMEO`를 겁니다.

| 기다리는 곳 | 제한              | 막는 상황                                  | 났을 때                   |
| ----------- | ----------------- | ------------------------------------------ | ------------------------- |
| 요청 읽기   | 5초 (`--timeout`) | 접속만 함, keep-alive 대기, 아주 느린 요청 | 응답 없이 닫음            |
| 응답 쓰기   | 10초              | 응답을 아주 느리게 받아 감                 | 닫음                      |
| CGI 실행    | 10초              | 끝나지 않는 CGI                            | CGI를 `kill`, `504` (4.4) |

다빈의 WSL 실험(작업자 16개를 모두 채운 뒤 새 정적 GET 전송) 결과, 제한이 없을 때는 응답이 오지 않았고 제한을 적용하면 작업자가 돌아와 `200`을 받았습니다.

| 작업자를 채운 상황        | 제한 없음        | 제한 적용       |
| ------------------------- | ---------------- | --------------- |
| 아무것도 보내지 않는 연결 | 9초간 응답 없음  | 4.89초 뒤 `200` |
| 다운로드를 멈춘 연결      | 45초간 응답 없음 | 29.5초 뒤 `200` |
| 끝나지 않는 CGI           | 45초간 응답 없음 | 9초 뒤 `200`    |

지금 코드에서 타임아웃이 나면 `read`가 -1(`EAGAIN`)을 돌려주고, `rio_readlineb`도 -1을 돌려줘 요청이 응답 없이 끝납니다. 그래서 `setsockopt`만 추가하면 됩니다.

**한계:** `SO_RCVTIMEO`는 `read` 한 번 기준이라, 4초마다 한 글자씩 보내면 작업자를 오래 붙잡을 수 있습니다(Slowloris). 10장에서 다룹니다.

### 2.5 스레드 안전성

| 코드                                 | 위치      | 판단                                                  |
| ------------------------------------ | --------- | ----------------------------------------------------- |
| `doit`의 `buf`, `rio`, `filename` 등 | 스택      | 안전. 스레드마다 따로 있음                            |
| `FILE_TYPES` 표                      | 전역      | 안전. 읽기만 함                                       |
| 요청 본문, CGI 출력 버퍼             | 힙        | 안전. 그 요청을 맡은 스레드만 포인터를 가짐           |
| **작업 큐**                          | 힙        | **mutex 필요.** 실제로 공유해서 바꾸는 것은 이것 하나 |
| **CGI 자식의 `setenv`**              | 환경 변수 | **수정 필요.** 아래                                   |
| `printf` 로그                        | stdout    | 줄이 섞일 수 있지만 동작에는 문제없음                 |

**fork 후 `setenv` 문제 (지금 코드의 버그):** 멀티스레드 프로세스에서 fork하면 자식에는 fork를 부른 스레드 하나만 복사됩니다. 그 순간 다른 스레드가 malloc 내부 락을 잡고 있었다면, 자식에서 그 락은 영원히 잠긴 채 남습니다. `setenv`는 내부에서 malloc을 쓰므로 자식이 멈출 수 있습니다.

- **수정:** 부모가 fork 전에 `char *envp[]`(`QUERY_STRING`, `REQUEST_METHOD`, `CONTENT_LENGTH`, `CONTENT_TYPE` 등)를 만들어 둡니다. 자식은 async-signal-safe 함수(`dup2`, `close`, `execve`, `_exit`)만 씁니다.
- **`waitpid(pid)`는 유지합니다.** `wait(NULL)`은 다른 스레드의 CGI 자식을 대신 회수합니다.

### 2.6 fd 상속 차단

CGI를 `execve`하면 자식은 부모의 fd를 모두 물려받습니다. 스레드 풀에서는 그 순간 다른 작업자가 맡고 있던 **다른 손님의 소켓**과 **리스닝 소켓**도 넘어갑니다.

- 다른 손님 소켓: 서버가 `close`해도 CGI가 같은 소켓을 들고 있어서 FIN이 나가지 않습니다. 클라이언트는 연결이 끝났는지 모릅니다.
- 리스닝 소켓: 서버를 재시작해도 아직 실행 중인 CGI가 포트를 잡고 있어 `bind`가 실패할 수 있습니다.

**두 겹으로 막습니다.**

1. **`FD_CLOEXEC` [다빈]:** 리스닝 소켓은 만들 때, 접속 소켓은 accept 직후에 설정합니다. Linux에서는 `accept4(..., SOCK_CLOEXEC)`로 원자적으로 설정하고, macOS에서는 `accept` 후 `fcntl`을 씁니다 (`#ifdef`로 분기).
2. **자식에서 fd 3 이상 모두 닫기 [신규]:** macOS의 `accept` → `fcntl` 사이에 다른 작업자가 fork하는 틈이 남습니다. 자식이 `dup2`로 stdin/stdout을 연결한 뒤 `execve` 전에 3번부터 끝까지 `close`합니다. `close`는 async-signal-safe 함수입니다. 최댓값(`sysconf(_SC_OPEN_MAX)`)은 fork 전에 부모가 계산해 둡니다.

### 2.7 종료 처리 (M7)

SIGINT, SIGTERM의 기본 동작은 즉시 종료라 처리 중인 응답이 잘립니다. 스레드가 있으면 시그널이 아무 스레드에나 전달될 수 있고, 핸들러 안에서는 mutex를 쓸 수 없습니다.

1. 다른 스레드를 만들기 전에 main에서 `pthread_sigmask`로 SIGINT, SIGTERM을 막습니다. 이후 스레드는 이 설정을 물려받습니다.
2. 시그널 전용 스레드 하나가 `sigwait`로 기다립니다.
3. 시그널이 오면: 종료 플래그 → main의 accept 중단 → 큐의 작업자 모두 깨움 → 작업자는 큐에 남은 연결까지 처리하고 끝남 → main이 `pthread_join` → 큐 해제 → 종료.

- **accept에서 멈춘 main을 깨우는 방법은 OS마다 다릅니다.** Linux는 `shutdown(listenfd)`로 깨어나지만 macOS에서는 보장되지 않습니다. main이 `poll`로 리스닝 소켓과 종료 알림용 pipe를 같이 기다리게 합니다.
- 작업자가 놀고 있는 연결을 읽는 중이어도 읽기 타임아웃(5초) 안에 끝나므로, 종료가 무한히 늦어지지 않습니다.
- `SIGPIPE`는 지금처럼 무시합니다 (쓰기 도중 클라이언트 끊김 대응).

## 3. M5 헤더 파싱과 본문

### 3.1 요청 구조체

파서는 소켓을 모르고 문자열만 받아 구조체를 채웁니다. 그래서 단위 테스트에서 소켓 없이 검증할 수 있습니다.

```c
#define HDR_RAW_MAX  8192          /* 헤더 전체 상한 */
#define BODY_MAX     (1 << 20)     /* 1 MiB */

struct http_request {
    char method[16], uri[MAXLINE], version[16];

    /* 서버가 쓰는 필드 */
    char host[256];
    char content_type[256];
    long content_length;           /* has_content_length가 0이면 의미 없음 */
    int  has_content_length;
    int  has_transfer_encoding;
    int  expect;                   /* 없음 / 100-continue / 그 외 */
    int  keep_alive;               /* 버전과 Connection 헤더로 결정 */

    /* 원본 헤더 블록: M6 프록시가 백엔드로 그대로 전달 */
    char   raw_headers[HDR_RAW_MAX];
    size_t raw_len;

    char *body;                    /* malloc. 요청이 끝나면 free */
};
```

- **원본 헤더 블록 [예훈 아이디어]:** 헤더 줄을 읽으면서 `raw_headers`에 이어 붙입니다. 버퍼가 차면 그 자체가 "헤더 전체 8 KiB 상한"이 되어 `400`을 보냅니다. 예훈 안처럼 이름·값 배열을 만들지 않아도 프록시가 헤더를 잃지 않습니다.
- keep-alive로 요청을 반복할 때는 요청마다 구조체를 초기화하고 `body`를 해제합니다.

### 3.2 헤더 규칙

| 헤더                | 저장할 값                     | 쓰는 곳                                                                        |
| ------------------- | ----------------------------- | ------------------------------------------------------------------------------ |
| `Host`              | 문자열                        | HTTP/1.1인데 없거나 중복되면 `400`. HTTP/1.0은 없어도 허용. M6에서 라우팅에 씀 |
| `Content-Length`    | 0 이상 정수, 있었는지 여부    | 본문 바이트 수                                                                 |
| `Connection`        | `close` / `keep-alive` / 없음 | 응답 후 연결을 닫을지                                                          |
| `Content-Type`      | 문자열                        | 해석하지 않고 CGI에 `CONTENT_TYPE`으로 넘김                                    |
| `Transfer-Encoding` | 있었는지 여부                 | 있으면 거절                                                                    |
| `Expect`            | `100-continue` / 그 외 / 없음 | 본문을 받기 전에 답할지                                                        |

- 헤더 이름은 `strcasecmp`로 비교하고, 값 앞뒤 공백은 잘라냅니다.
- 모르는 헤더는 읽고 무시합니다 (원본 블록에는 남음).
- `:`가 없는 헤더 줄, `MAXLINE`보다 긴 헤더 줄, 헤더 전체 8 KiB 초과는 `400`입니다.

### 3.3 요청 줄 규칙 [신규]

| 상황                                                 | 응답                                    |
| ---------------------------------------------------- | --------------------------------------- |
| 요청 줄이 `MAXLINE` 안에 끝나지 않음 (줄바꿈 없음)   | `414 URI Too Long` + 닫기               |
| 요청 줄이 세 부분(메서드, URI, 버전)으로 나뉘지 않음 | `400` + 닫기                            |
| 버전이 `HTTP/x.y` 형식이 아님                        | `400` + 닫기                            |
| `HTTP/1.0`, `HTTP/1.1`이 아닌 버전                   | `505 HTTP Version Not Supported` + 닫기 |
| GET, POST, HEAD가 아닌 메서드                        | `501`                                   |

### 3.4 본문의 끝

TCP는 바이트가 이어지는 흐름이라, 본문이 어디서 끝나는지를 HTTP가 따로 알려 줘야 합니다.

| 방식                                             | 결정                         |
| ------------------------------------------------ | ---------------------------- |
| `Content-Length: n`                              | **지원**                     |
| `Transfer-Encoding: chunked`                     | `501` + 닫기 (범위 제한)     |
| CL과 TE가 같이 옴                                | `400` + 닫기                 |
| CL과 TE가 모두 없음                              | 본문 0바이트 (RFC 9112 §6.3) |
| CL이 숫자가 아님, 음수, 서로 다른 값으로 여러 번 | `400` + 닫기                 |

**CL과 TE가 같이 오면 거절하는 이유:** 서버마다 다른 쪽을 믿으면 본문이 끝나는 위치를 서로 다르게 판단합니다. 그러면 남은 바이트가 같은 연결의 다음 요청으로 처리되는 request smuggling이 생깁니다. 서버 한 대일 때는 요청이 꼬이는 버그 수준이지만, M6 Reverse Proxy와 keep-alive를 같이 쓰면 보안 문제가 됩니다.

**CL이 없는 POST:** 본문 0바이트로 처리합니다. adder는 빈 입력에 안내 메시지를 출력합니다. (bloro 초안은 `411`이었지만, RFC 규칙을 따르는 쪽이 분기가 적습니다.)

### 3.5 본문 버퍼링 + 상한

|         | 버퍼링 (선택)                   | 스트리밍                                  |
| ------- | ------------------------------- | ----------------------------------------- |
| 방식    | CL만큼 malloc해 다 읽은 뒤 처리 | 조금 읽을 때마다 바로 넘김                |
| 메모리  | 본문 크기만큼 (상한 있음)       | 작은 고정 버퍼                            |
| 구현    | 단순, 파서와 처리부 분리        | 읽기와 쓰기가 섞이고 실패 처리 복잡       |
| 큰 본문 | 상한으로 거절                   | 받는 동안 작업자가 묶임. 결국 상한이 필요 |

"매우 큰 요청 본문"을 막는 것은 스트리밍이 아니라 **상한**입니다. 헤더에서 CL을 먼저 보고 `BODY_MAX`(1 MiB)를 넘으면 **malloc 전에** `413`을 보냅니다.

- **본문은 반드시 헤더를 읽은 같은 `rio`로 읽습니다** (`rio_readnb`). `rio_readlineb`가 미리 읽어 둔 본문 앞부분이 rio 버퍼에 있을 수 있습니다.
- 본문 도중 연결이 끊기거나 읽기 타임아웃이 나면 `free` 후 응답 없이 닫습니다.
- **GET에 본문이 붙어 와도 읽어서 버립니다** (상한 적용). 읽지 않으면 keep-alive에서 그 본문이 다음 요청으로 읽힙니다.
- 본문 버퍼는 응답 후와 모든 실패 경로에서 `free`합니다. ASan으로 확인합니다.

### 3.6 `Expect: 100-continue`

curl은 POST 본문이 일정 크기를 넘으면 `Expect: 100-continue`를 붙이고, 서버가 답할 때까지 본문을 미룹니다. 무시하면 curl이 약 1초 기다린 뒤 그냥 보냅니다. 다빈의 실험에서도 약 1초 지연이 확인되었습니다.

| 조건                                             | 처리                                                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| HTTP/1.1, `100-continue`, 본문 검사 통과, CL > 0 | `HTTP/1.1 100 Continue\r\n\r\n` 전송 후 본문 읽기                                    |
| `100-continue`, 본문 검사 실패 (413 등)          | `100` 없이 오류 응답 후 **닫기** (클라이언트가 본문을 보내면 다음 요청으로 읽히므로) |
| `100-continue`가 아닌 값                         | `417 Expectation Failed` + 닫기                                                      |
| HTTP/1.0 요청                                    | Expect 무시                                                                          |

### 3.7 MIME [다빈]

- 파일 이름의 **마지막 `.` 뒤**를 비교합니다. `.json`과 `.js`, `a.css.txt`를 올바르게 구분합니다.

| 확장자          | Content-Type                  |
| --------------- | ----------------------------- |
| `.html`         | `text/html`                   |
| `.css`          | `text/css`                    |
| `.js`           | `text/javascript`             |
| `.png`          | `image/png`                   |
| `.jpg`, `.jpeg` | `image/jpeg`                  |
| `.gif`          | `image/gif`                   |
| 그 외           | `text/plain` (현재 동작 유지) |

### 3.8 HEAD [bloro]

정적 파일에만 지원합니다. GET과 같은 헤더(`Content-Length` 포함)를 보내고 본문만 뺍니다. CGI에 대한 HEAD는 `501`입니다. 4장의 구조에서는 본문만 빼면 되므로 나중에 쉽게 추가할 수 있습니다.

## 4. M5 CGI 실행과 응답 구조

### 4.1 지금 구조의 문제

```
서버 → 소켓: "HTTP/1.0 200 OK ..."      ← fork 전에 먼저 보냄
fork → 자식: dup2(소켓 → stdout) → execve(adder)
adder → 소켓: 나머지 헤더와 본문을 직접 씀
```

- **500을 못 보냅니다.** 200을 먼저 보내서 CGI가 실패해도 클라이언트는 200 + 빈 본문을 받습니다.
- **keep-alive를 못 합니다.** CGI가 소켓에 직접 써서 서버는 응답 끝을 모릅니다.
- **끝나지 않는 CGI를 막지 못합니다.** 작업자가 `waitpid`에서 무한정 기다립니다.

### 4.2 세 초안의 방식과 통합안

| 방식       | 입력          | 출력              | 500/504  | CGI keep-alive | 교착                                   | 출력 상한          |
| ---------- | ------------- | ----------------- | -------- | -------------- | -------------------------------------- | ------------------ |
| 예훈       | 파이프        | 소켓 직접         | 불가     | 불가           | 본문 64 KB 초과 + CGI가 안 읽으면 있음 | 없음               |
| bloro      | 파이프        | 파이프로 모음     | 가능     | 가능           | 입출력이 모두 크면 있음                | 1 MiB              |
| 다빈       | 임시 파일     | 임시 파일         | 가능     | 안 함          | 없음                                   | 없음 (디스크 사용) |
| **통합안** | **임시 파일** | **파이프로 모음** | **가능** | **가능**       | **없음**                               | **1 MiB**          |

**입력은 임시 파일, 출력은 파이프로 받습니다.** 부모는 파이프에 쓰지 않고 출력만 읽으므로, "부모는 쓰기에서, CGI는 출력에서 서로 기다리는" 교착이 생기지 않습니다. 출력은 메모리에 모으므로 상한을 걸 수 있습니다. 다빈의 WSL 1 MiB 입력 실험에서 임시 파일(중간값 1.9 ms)은 파이프(2.1~2.7 ms)보다 느리지 않았습니다.

### 4.3 실행 순서

```
fork 전 (부모):
  envp 준비 (REQUEST_METHOD, QUERY_STRING, CONTENT_LENGTH, CONTENT_TYPE)
  입력 준비:
    POST → mkstemp로 임시 파일 생성 → 바로 unlink → 본문 쓰기 → lseek(0)
    GET  → open("/dev/null")
  출력 파이프 생성 (pipe)
  fd 최댓값 계산 (sysconf)

자식:
  dup2(입력 fd → stdin), dup2(출력 파이프 쓰기 쪽 → stdout)
  fd 3 이상 모두 close
  execve(filename, argv, envp)
  실패하면 _exit(127)

부모:
  입력 fd, 출력 파이프 쓰기 쪽 close
  출력 파이프를 poll로 남은 시간만큼 기다리며 EOF까지 버퍼에 모음
    - 1 MiB 초과 → kill, waitpid → 500
    - 10초 초과 → kill, waitpid → 504
  EOF 이후: waitpid(pid, WNOHANG)를 마감 시간까지 짧게 반복
    - 마감까지 안 끝나면 kill → waitpid → 504
  종료 상태와 출력을 확인해 응답 생성
```

- **`mkstemp` 직후 `unlink`:** 이름은 사라지고 fd만 남으므로, 서버가 중간에 죽어도 임시 파일이 디스크에 남지 않습니다.
- **EOF 뒤에도 마감 시간을 지킵니다.** CGI가 stdout을 닫고 계속 돌면 blocking `waitpid`에서 작업자가 묶이기 때문입니다.

### 4.4 CGI 출력 해석과 응답 생성

CGI는 상태 줄 없이 `헤더 몇 줄 + 빈 줄 + 본문`을 출력합니다 (CGI 표준). 서버는 빈 줄에서 나눠 응답을 만듭니다.

| 항목                       | 처리                                                                 |
| -------------------------- | -------------------------------------------------------------------- |
| 상태 줄                    | CGI가 `Status: 404 Not Found`를 주면 그 값, 없으면 `HTTP/1.1 200 OK` |
| `Content-Type` 등 CGI 헤더 | 그대로 전달                                                          |
| `Content-Length`           | 서버가 센 본문 길이로 직접 씀 (CGI 값 무시)                          |
| `Connection`               | 서버가 5장 규칙으로 직접 씀 (CGI 값 무시)                            |

| 상황                                              | 응답                              |
| ------------------------------------------------- | --------------------------------- |
| fork, pipe, 임시 파일 실패                        | `500`                             |
| `execve` 실패, 0이 아닌 종료, 시그널로 죽음       | `500`                             |
| 출력이 비었거나 헤더와 본문을 나누는 빈 줄이 없음 | `500`                             |
| 출력이 1 MiB 초과                                 | CGI `kill`, `500`                 |
| 10초 안에 끝나지 않음                             | CGI `kill`, `504 Gateway Timeout` |

실패(`500`)와 시간 초과(`504`)를 나눠 원인을 구분합니다. 이 "모아서 확인한 뒤 보내기" 구조는 M6 Reverse Proxy에서 백엔드 응답을 다룰 때도 재사용할 수 있습니다.

### 4.5 adder 수정

- `REQUEST_METHOD`가 POST이면 stdin에서 `CONTENT_LENGTH`만큼 읽어 쿼리 문자열 대신 씁니다.
- GET `?1&2` 형식과 POST `a=1&b=2` 형식을 모두 받습니다.
- 숫자 형식 오류, 범위 초과에는 안내 메시지를 출력합니다 [다빈].
- 출력에서 `Connection`, `Content-length`를 뺍니다 (서버가 정함). `Content-type`과 본문만 출력합니다.

### 4.6 테스트용 CGI

`tests/fixtures/www/cgi-bin/`에 둡니다.

| 이름    | 동작                            | 기대 응답                              |
| ------- | ------------------------------- | -------------------------------------- |
| `fail`  | 아무것도 출력하지 않고 1로 종료 | `500`                                  |
| `nohdr` | 빈 줄 없이 본문만 출력          | `500`                                  |
| `slow`  | `sleep 30`                      | 약 10초 뒤 `504`, 프로세스가 남지 않음 |
| `big`   | 2 MiB 출력                      | `500`                                  |

## 5. M5 keep-alive

### 5.1 연결 처리 루프

```c
rio_readinitb(&rio, connfd);            /* 연결당 한 번만 */
for (n = 1; ; n++) {
    keep = handle_request(connfd, &rio, n < keepalive_max);
    if (!keep) break;
}
close(connfd);
```

- **`rio`는 연결당 한 번만 초기화합니다.** 파이프라이닝으로 다음 요청 앞부분이 이미 rio 버퍼에 있을 수 있습니다. 지금은 `doit` 안에서 rio를 만들므로 바깥으로 옮깁니다.
- 요청 줄, 헤더, 빈 줄, 본문(정확히 CL 바이트)을 다 읽으면 그다음 바이트가 다음 요청입니다.

### 5.2 판단 규칙

**한 줄 규칙: 요청을 끝까지 읽었고 응답 길이를 알면 유지, 아니면 닫습니다.** 단, 클라이언트가 닫기를 원하거나 요청 수 상한에 닿으면 닫습니다.

| 조건                                                               | 결정                                   |
| ------------------------------------------------------------------ | -------------------------------------- |
| HTTP/1.1, Connection 없음 또는 `keep-alive`                        | 유지                                   |
| HTTP/1.1, `Connection: close`                                      | 닫음                                   |
| HTTP/1.0, Connection 없음                                          | 닫음                                   |
| HTTP/1.0, `Connection: keep-alive`                                 | 유지 (응답에 `Connection: keep-alive`) |
| 본문 경계를 모르는 오류 (`400`, `413`, `414`, `417`, `501`, `505`) | 닫음                                   |
| 요청을 다 읽은 뒤의 오류 (`403`, `404`)                            | 유지                                   |
| 정적 파일 `200`, HEAD                                              | 유지                                   |
| CGI 응답 (`200`, `500`, `504`)                                     | 유지 (서버가 길이를 셈)                |
| 응답을 보내다 실패                                                 | 바로 닫음                              |
| 이 연결의 요청 수가 `--keepalive-max`에 도달                       | 응답에 `Connection: close`, 닫음       |
| 다음 요청 줄을 읽었는데 0 (클라이언트가 끊음)                      | 조용히 닫음                            |
| 다음 요청이 읽기 타임아웃(5초) 안에 안 옴                          | 조용히 닫음                            |

닫기로 했으면 응답에 `Connection: close`를 넣습니다.

### 5.3 단계적 적용 [다빈 → bloro]

| 단계  | 유지하는 응답                | 조건                                         |
| ----- | ---------------------------- | -------------------------------------------- |
| M5-4a | 본문 없는 정적 GET의 `200`만 | 먼저 머지. 루프, rio 이동, 요청 수 상한 검증 |
| M5-4b | 5.2 규칙 전체                | 4장 CGI 구조 변경이 머지된 뒤                |

### 5.4 연결을 끊는 장치

| 방식                | 막는 문제                               | 결정                                |
| ------------------- | --------------------------------------- | ----------------------------------- |
| idle 타임아웃       | 놀고 있는 연결이 작업자를 붙잡음        | **사용** (읽기 타임아웃 5초 그대로) |
| 연결당 요청 수 상한 | 쉬지 않고 요청하는 손님이 작업자를 독점 | **사용** (100)                      |
| 연결 수명 상한      | 가끔 요청하는 연결                      | 요청 수 상한과 효과가 겹쳐 생략     |
| 바쁠 때 닫기        | 큐에 손님이 기다리면 keep-alive 포기    | 여유 있으면 확장                    |

요청 수 상한으로 닫히면 클라이언트가 다시 연결하면서 큐 뒤에 서므로 다른 손님에게도 차례가 갑니다.

## 6. 오류 응답

Phase 1에 이미 있는 것: `404`(파일 없음), `403`(권한 없음, 폴더 요청, `..` 경로), `500`(정적 파일 열기 실패).
모든 오류 응답에 `Content-Length`와 `Connection`을 넣습니다.

| 상황                                                             | 응답                                   | 연결 | 과제 항목                |
| ---------------------------------------------------------------- | -------------------------------------- | ---- | ------------------------ |
| 요청 줄이 `MAXLINE` 초과                                         | `414`                                  | 닫음 | 매우 긴 URI              |
| 요청 줄 형식 오류, 버전 형식 오류                                | `400`                                  | 닫음 | 잘못된 HTTP 요청         |
| 지원하지 않는 버전                                               | `505`                                  | 닫음 | 잘못된 버전              |
| GET, POST, HEAD 외 메서드                                        | `501`                                  | 닫음 | 비정상 메서드            |
| 정적 파일에 POST                                                 | `501` (Phase 1 유지, 기존 테스트 있음) | 유지 |                          |
| CGI에 HEAD                                                       | `501`                                  | 유지 |                          |
| 헤더 줄에 `:` 없음, 헤더 줄 `MAXLINE` 초과, 헤더 전체 8 KiB 초과 | `400`                                  | 닫음 | 불완전한 헤더            |
| HTTP/1.1인데 Host 없음 또는 중복                                 | `400`                                  | 닫음 | RFC 9112 Host 필수       |
| CL이 숫자 아님, 음수, 서로 다른 값 반복                          | `400`                                  | 닫음 | 본문 길이를 믿을 수 없음 |
| CL과 TE가 같이 옴                                                | `400`                                  | 닫음 | request smuggling        |
| TE만 옴                                                          | `501`                                  | 닫음 | chunked 미지원           |
| CL > 1 MiB                                                       | `413`                                  | 닫음 | 매우 큰 요청 본문        |
| Expect가 `100-continue`가 아님                                   | `417`                                  | 닫음 |                          |
| 본문 도중 끊김, 읽기 타임아웃                                    | 없음                                   | 닫음 | 갑작스러운 연결 종료     |
| CGI 실패 (exec 실패, 비정상 종료, 출력 깨짐, 출력 상한 초과)     | `500`                                  | 유지 | 기본 오류 500            |
| CGI 10초 초과                                                    | `504`                                  | 유지 | 응답 없는 동적 처리      |

## 7. 요청 흐름

`curl -d "a=1&b=2" http://127.0.0.1:8000/cgi-bin/adder` 예시입니다.

```
[main]       accept → FD_CLOEXEC, 타임아웃 설정 → 큐에 넣기
[작업자]     큐에서 꺼내기 → rio 초기화 → 요청 반복 처리

요청 줄 읽기       "POST /cgi-bin/adder HTTP/1.1"
  → 요청 줄 검사    길이 414 / 형식 400 / 버전 505 / 메서드 501
  → 헤더 파싱       빈 줄까지 "이름: 값" → 구조체 + 원본 블록
                    Host=127.0.0.1:8000, Content-Length=7,
                    Content-Type=application/x-www-form-urlencoded
  → 헤더 검사       Host(1.1) 400 / CL+TE 400 / TE 501 / CL 오류 400
                    CL > 1 MiB 413 / 이상한 Expect 417
  → Expect 처리     100-continue였으면 "HTTP/1.1 100 Continue"
  → 본문 읽기       같은 rio로 7바이트. 모자라면 free 후 닫기
  → URI 해석, 파일 확인, 권한 확인 (지금과 같음)
  → CGI 실행        임시 파일에 본문 → 출력 파이프 → envp → fork
                    자식: dup2, fd 3 이상 close, execve
                    부모: 출력을 poll로 모음 (1 MiB, 10초) → waitpid
  → 응답            "HTTP/1.1 200 OK" + Content-type
                    + Content-Length(서버가 셈) + Connection → 본문
  → 정리            body, 출력 버퍼 free, 임시 파일 fd close
  → keep-alive 판단 → 다음 요청 또는 close
```

| M5-2  | 본문 읽기, 상한, 413, Expect, adder POST                                                                           | M5-1        |
| M5-3  | CGI 구조 변경 (임시 파일 입력, 파이프 출력, 500/504, 테스트용 CGI)                                                 | M5-2        |
| M5-4a | keep-alive: 정적 GET만, 요청 수 상한                                                                               | M5-1        |
| M5-4b | keep-alive 규칙 전체                                                                                               | M5-3, M5-4a |
| M7    | 시그널 전용 스레드, 안전한 종료                                                                                    | M4-2        |
| M8    | 부하 측정, 기본값 확정                                                                                             | 전부        |

M5-3(CGI)과 M5-4a(keep-alive 정적)는 병렬로 진행할 수 있습니다.

## 10. 한계와 다시 검토할 조건

| 한계                             | 영향                                                                                 | 재검토 조건                                                                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 놀고 있는 연결이 작업자를 붙잡음 | 동시 연결이 작업자 수를 넘으면 대기                                                  | 응답 시간이 타임아웃 수준까지 늘면 **이벤트 루프**로 전환. 시간 여유가 있으면 이벤트 루프 버전을 만들어 M8에서 숫자로 비교 (코치 권장) |
| `SO_RCVTIMEO`는 read 한 번 기준  | 한 글자씩 보내는 Slowloris가 작업자를 오래 붙잡음                                    | 문제가 되면 "요청 시작부터 N초 안에 헤더 끝" 전체 데드라인 추가                                                                        |
| chunked 미지원                   | RFC 7230/9112는 HTTP/1.1 수신자의 chunked 해석을 MUST로 정함. 이번 `501`은 범위 제한 | chunked 클라이언트를 지원해야 하면 디코딩 추가. 조각을 모아 버퍼에 붙이면 버퍼링 구조에 그대로 들어감                                  |
| 본문·CGI 출력 1 MiB 상한         | 파일 업로드, 큰 CGI 출력 불가                                                        | 정상 요청으로 받아야 하면 스트리밍 검토                                                                                                |
| 큐가 가득 차면 대기만 함         | 지속 과부하에서 응답 시간이 길어짐                                                   | 외부 트래픽처럼 손님이 끊임없이 오면 503 부하 차단으로 전환                                                                            |
| CGI `kill`은 CGI 프로세스 하나만 | CGI가 만든 자식은 남을 수 있음                                                       | 필요하면 프로세스 그룹(`setpgid` + `kill(-pgid)`) 사용                                                                                 |
| 스레드 격리 없음                 | 한 스레드의 메모리 오류가 서버 전체를 죽임                                           | ASan, TSan으로 예방                                                                                                                    |
