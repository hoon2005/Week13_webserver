# PRD 작성 방법

PRD(Product Requirements Document)는 무엇을 왜 만들지, 어디까지 만들지를 적은 문서입니다. 이 폴더는 팀원 각자의 초안을 모아 최종본 하나로 합치는 곳입니다.

## 순서

```text
1. 각자 초안 작성   docs/prd/<이름>.md   (각자 작업 브랜치에서)
2. 팀 회의          초안을 같이 읽고 후보 중 하나를 고름
3. 최종 PRD 작성    docs/prd/<마일스톤>.md   (정한 내용, 이유, 작업 체크리스트)
```

- **초안 파일:** `docs/prd/<이름>.md` 하나에 씁니다(예: `docs/prd/dabin.md`). 각자 자기 파일만 고치므로 같은 파일을 동시에 편집할 일이 없습니다.
- **최종 PRD:** 회의에서 정한 내용과 그 이유를 `docs/prd/<마일스톤>.md`에 모읍니다. 지금은 [phase1.md](phase1.md), [m4m5.md](m4m5.md), [m6m7.md](m6m7.md)가 있고, 이를 최종 코드 기준으로 합친 문서가 [final.md](final.md)입니다. 최종 PRD가 나온 뒤에는 초안을 고치지 않습니다. 초안은 그 시점의 생각을 남긴 기록이기 때문입니다.
- **작업 분배:** 최종 PRD의 작업 체크리스트에 담당자 이름을 적는 것으로 시작합니다. 티켓 파일이나 별도 결정 기록은 필요해지면 그때 만듭니다.

LMS 「웹 서버 만들기」의 필수 항목은 팀 최종본의 마일스톤별 완료 조건에 연결합니다. 구현 중 결정이 바뀌면 어떤 조건이나 관찰 결과 때문에 바뀌었는지 남깁니다.

## 개인 PRD 작성 가이드

회의에서 함께 정할 질문과 제안 이유를 먼저 적습니다. 안건이 여러 개라면 문서 앞에 짧게 요약해도 좋습니다. 아래 항목은 안건에 필요한 만큼 작성합니다. 네 항목을 모두 채운 예시는 [example.md](example.md)에 있습니다.

### 목표와 범위

풀려는 문제와 어떤 요청에 어떤 응답이 오면 목표를 달성한 것인지 적습니다. 예를 들어 API 요청과 정적 파일 요청을 각각 담당 백엔드에 전달하고 그 응답을 돌려주는 것이 목표가 될 수 있습니다. 포함하거나 미룰 선택 기능이 있으면 함께 적습니다.

### 설계 선택

후보에 따라 구현과 디버깅에서 무엇이 달라지는지 설명합니다. 한두 문장으로 충분하면 글로 쓰고, 여러 후보를 나란히 비교할 때는 표를 써도 됩니다. 추천에 영향을 준 제약이나 실험 결과, 선택을 다시 검토할 조건이 있으면 함께 남깁니다.

### 요청 흐름

예시 요청 하나가 어디까지 처리되고 어떤 응답을 받는지 적습니다. 여러 사람이 함께 구현하는 경계가 있다면 어느 모듈이 무엇을 받아서 넘기는지도 설명합니다.

### 검증 계획

다른 팀원이 확인할 수 있도록 **무엇을 준비하고, 어떤 요청을 보내고, 무엇이 보이면 성공인지** 적습니다. 상태 코드, 응답 본문, 로그, 테스트 결과 중 판단에 필요한 것만 고릅니다.

예를 들어 Reverse Proxy가 `/api/` 요청을 API 백엔드로 보내는지 확인한다면 이렇게 적을 수 있습니다.

1. **준비** 프록시를 `8080`, API 백엔드를 `8001`에 띄웁니다. 백엔드는 `/api/health`에 `200`과 `api-ok`를 응답합니다.
2. **요청** `curl -i http://127.0.0.1:8080/api/health`를 실행합니다.
3. **확인** 응답에 `200`과 `api-ok`가 나오고, 프록시 로그에 `/api/` 규칙과 백엔드 주소 `127.0.0.1:8001`이 찍힙니다. 로그를 보면 요청이 의도한 백엔드로 갔는지도 확인할 수 있습니다.

아직 구현 전이라면 확인할 상황과 기대 동작만 적어도 됩니다. 실험을 했다면 실제로 관찰한 결과를 덧붙입니다.
