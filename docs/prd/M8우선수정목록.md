## 1. 진행 방식

항목 하나마다 회귀 테스트를 함께 만들고, 고친 뒤 통과하는지 확인함. 회귀 테스트는 이미 있는 테스트가 아니라, 지금 코드에서는 실패하고 고친 뒤에는 통과하는 새 테스트를 말함.

```text
수정 항목 하나
  ① 재현 명령을 기능 테스트로 옮김 → 지금 코드에서 실패하는지 확인
  ② 코드 수정 → 이 테스트가 통과하는지 확인
  ③ make verify → 기존 테스트 92개가 모두 통과하는지 확인
  ④ 테스트와 수정을 커밋 하나로
```

- ①에서 실패를 먼저 확인하는 이유는, 고치기 전부터 통과하는 테스트는 아무것도 검증하지 못하기 때문임.
- 테스트와 수정을 커밋 하나로 묶으면 검증 보고서의 "수정 내용"에 그대로 쓸 수 있음.
- F12(포맷)는 줄 번호를 밀어내므로 다른 항목이 모두 끝난 뒤 마지막 커밋으로 둠.

재현 명령은 아래처럼 서버를 띄운 상태에서 실행함. F2와 F6은 서버를 따로 띄움.

```bash
make && rm -rf /tmp/www && cp -r tests/fixtures/www /tmp/www && cp build/adder /tmp/www/cgi-bin/ && chmod +x /tmp/www/cgi-bin/*
./build/tiny 8000 --root /tmp/www --route /api=127.0.0.1:8001 &
```

## 3. 일괄 동의 항목 (F1\~F7)

### F1. 같은 연결의 작은 응답이 약 44ms 늦어짐

#### 어떤 문제인가?

클라이언트가 연결을 재사용해 `home.html`을 받으면 두 번째 요청부터 응답이 약 44ms 걸렸어. `home.html`은 120바이트야. 응답은 정상인데 전송 대기가 요청 시간에 더해져.

#### 왜 발생하는가?

서버는 HTTP 헤더와 본문을 따로 써. TCP에서 ACK는 받은 데이터를 확인했다는 신호야. 헤더를 먼저 보낸 TCP는 ACK가 아직 오지 않았고 다음에 보낼 데이터가 작은 조각이면 Nagle 규칙에 따라 잠시 모아 둘 수 있어. 클라이언트 쪽 TCP는 Delayed ACK 규칙에 따라 다음 데이터가 곧 오기를 잠깐 기다렸다가 ACK를 보낼 수 있어.

```text
서버 TCP                                 클라이언트 TCP
헤더 전송 ─────────────────────────────→ 헤더 수신
작은 본문을 보류 (헤더 ACK 대기)             ACK를 잠시 보류
          ←───────────────────────────── 지연 뒤 ACK
본문 전송 ─────────────────────────────→ 응답 수신 완료
```

큰 본문은 전송 가능한 TCP 세그먼트 한 개 분량이 모이면 앞 데이터의 ACK가 오기 전에도 보낼 수 있어. `TCP_NODELAY`는 Nagle 때문에 작은 조각을 모으는 대기를 없애. ACK, 흐름 제어, 혼잡 제어는 계속 작동해. [RFC 1122 §4.2.3.2](https://www.rfc-editor.org/rfc/rfc1122.html#section-4.2.3.2), [§4.2.3.4](https://www.rfc-editor.org/rfc/rfc1122.html#section-4.2.3.4)

#### 어떤 영향이 있는가?

부하 측정 도구는 이 대기까지 응답 시간에 포함해. 부하 측정용 파일이 영향을 받으므로, F1은 M8 측정 전에 처리하는 항목이야.

| 실측 (두 번째 요청부터)    | 값                                            |
| -------------------------- | --------------------------------------------- |
| 정적 100바이트, 10KB, 60KB | 44.0ms, 44.0ms, 42.0ms                        |
| 404 응답, CGI(`adder`)     | 41.8ms, 54.8ms (CGI 실행 시간 포함)           |
| 중계한 5바이트             | 44.0ms                                        |
| 정적 100KB, 200KB, 1MB     | 0.1ms, 0.1ms, 0.2ms                           |
| HEAD, 빈 파일, 중계한 204  | 0.2ms 이하                                    |
| release 빌드 `wrk -c10`    | 초당 230건 → `TCP_NODELAY`를 켜 사본 70,452건 |

60KB와 100KB 사이의 경계는 같은 컴퓨터 안에서 잰 값임. 실제 네트워크에서는 달라질 수 있음.

#### 어떻게 수정할 것인가?

| 선택지                                          | 장점                                               | 단점                                                                                        |
| ----------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **A. `conn_socket_setup`에 `TCP_NODELAY` 설정** | 한 곳만 고치면 정적, 오류, CGI, 중계가 모두 해결됨 | 작은 패킷이 늘 수 있음. 이 서버는 응답마다 쓰기가 몇 번뿐이라 영향이 작음                   |
| B. 헤더와 본문을 `writev` 한 번으로 보냄        | 패킷 수가 줄어듦                                   | 정적·오류·CGI·중계를 각각 고쳐야 함. 중계 본문은 여러 번에 나눠 쓰므로 완전히 해결되지 않음 |

- **권장안: A.** B는 버그 수정이 아니라 성능 개선 후보로, M8에서 측정해 보고 결정함.

#### 기술 근거 및 코드 위치

|                  |                                                                                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 언제             | 연결을 유지하고, 본문이 있는 작은 응답을 두 번째 요청부터 받을 때. 정적 파일, 오류, CGI, 중계 모두                                                                                                                 |
| 원인과 코드 위치 | 헤더와 본문을 `write` 두 번에 나눠 보냄. 헤더 `tiny.c:603`, 본문 `tiny.c:635`(오류)·`1060`(정적)·`1342`(CGI), 중계는 `proxy.c:826`과 `body_relay`. 그리고 `conn_socket_setup`(`tiny.c:428`)에 `TCP_NODELAY`가 없음 |

| 영향             | 응답 내용은 맞고 느리기만 함. 부하 측정에 쓸 `home.html`(120바이트)이 여기에 걸림                                                                                                                                  |

- 참고 커밋: `b2924bf` (테스트 포함)

#### 정확성 확인

44ms는 원본에서 관찰한 지연이야. 60KB와 100KB 사이에서 측정 결과가 바뀐 것도 같은 컴퓨터에서 얻은 관찰이야. 실제 경계와 지연은 TCP 동작과 환경에 따라 달라져. 코드의 두 `write` 호출이 실제로 항상 두 TCP 패킷이 되는지도 패킷 기록이 있어야 확인할 수 있어.

#### 어떻게 검증할 것인가?

- 회귀 테스트는 절대 시간 대신 "같은 연결의 두 번째 요청이 새 연결의 첫 요청보다 느리지 않다"로 비교해야 컴퓨터마다 흔들리지 않음.

```bash
for i in $(seq 10); do echo "url=http://localhost:8000/home.html"; echo "output=/dev/null"; done > /tmp/urls
curl -s -w "%{time_total}\n" -K /tmp/urls
```

기대: 지금은 두 번째 줄부터 약 0.044, 고치면 0.001 아래.

### F2. 응답 전송에 실패해도 최대 1초를 더 기다림 (PRD와 다름)

#### 어떤 문제인가?

클라이언트가 큰 파일을 받다 멈췄는데 연결은 열어 둔 경우야. 서버가 응답 전송 실패를 감지한 뒤에도 닫기 전에 최대 1초를 더 쓰고, 그동안 작업 스레드는 다음 요청을 처리할 수 없어.

#### 왜 발생하는가?

응답을 다 보낸 뒤에는 서버가 보내는 방향을 먼저 닫아 더 보낼 데이터가 없다고 알려. 이때 보내는 신호가 FIN이야. 받는 방향은 잠깐 열어 두고 남은 데이터를 읽어. 연결이 갑자기 리셋(RST)돼 이미 보낸 응답이 사라지는 상황을 줄이기 위한 절차야.

지금 정적·오류·CGI 경로는 전송 실패 때도 `keep`을 0으로 설정하고, 요청 처리는 그 값만 보고 정상 전송 완료와 실패를 같은 종료 상태로 처리해.

```text
정상 전송 + 연결 종료 필요 → CONN_CLOSE_REPLIED → 잠시 수신 비우기
전송 실패 (현재)          → CONN_CLOSE_REPLIED → 잠시 수신 비우기
전송 실패 (A안·기존 중계) → CONN_CLOSE_SILENT  → 바로 닫기
```

#### 어떤 영향이 있는가?

원본 실측은 다음 요청이 얼마나 기다렸는지를 쟀어. 연결을 닫는 경로에서 생긴 시간 차이를 읽으려면 전송 실패까지 걸린 시간도 함께 봐야 해.

| 실측 (작업 스레드 1개, `--timeout 1`, 50MB 파일을 받다 멈춘 뒤 다음 요청의 대기, 3회) | 값                 |
| ------------------------------------------------------------------------------------- | ------------------ |
| 지금 코드                                                                             | 6.85, 6.86, 6.86초 |
| 정적 파일 경로만 고친 사본                                                            | 5.85, 5.84, 5.84초 |

정확히 1초 차이가 남. 나머지 약 5.8초는 쓰기 제한 시간(`SO_SNDTIMEO`)을 기다린 시간이라 이 수정과 상관없음.

#### 어떻게 수정할 것인가?

| 선택지                                                    | 장점                                      | 단점                                             |
| --------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| **A. 전송 실패를 따로 표시해 `CONN_CLOSE_SILENT`로 닫음** | PRD와 일치하고 중계 경로와 같은 규칙이 됨 | 정적·오류·CGI 세 경로를 모두 고쳐야 함           |
| B. 코드는 두고 PRD를 고침                                 | 코드 변경이 없음                          | 지킬 응답이 없는데 작업 스레드가 최대 1초 기다림 |

- **권장안: A.**

#### 기술 근거 및 코드 위치

|                  |                                                                                                                                                                                                                                                |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 언제             | 클라이언트가 응답을 받다가 멈춘 채 연결을 끊지 않을 때. 이미 끊었으면 바로 끝남                                                                                                                                                                |
| 원인과 코드 위치 | 전송에 실패하면 `*keep = 0`으로 바꿈(정적 `tiny.c:1061`, 오류 `636`, CGI `1343`). `request_handle`은 `keep`이 0이면 다 보낸 경우와 구분하지 못하고 `CONN_CLOSE_REPLIED`를 돌려줌(`879`). 그래서 `connection_close_lingering`(`731`)으로 들어감 |
| 비교             | 중계 응답은 쓰기에 실패하면 이미 바로 닫음(`proxy.c:826`\~`829` → `CONN_CLOSE_SILENT`)                                                                                                                                                         |
| PRD              | `m4m5.md` 496행 "응답을 보내다 실패 → 바로 닫음"                                                                                                                                                                                               |
| 영향             | 작업 스레드가 최대 1초 더 묶임. 1초 비우기는 보낸 응답이 RST로 사라지지 않게 하는 장치라, 실패했으면 지킬 응답이 없음                                                                                                                          |

- 참고 커밋: `2649f3d`

#### 정확성 확인

원본은 “정확히 1초”라고 적었어. 표에서 같은 순번의 값을 빼면 1.00초, 1.02초, 1.02초라 표의 정밀도에서는 약 1초로 읽혀. 원본이 약 5.8초를 `SO_SNDTIMEO` 대기 시간으로 설명한 부분은, 이 표로는 대기 시간의 구성까지 분리할 수 없어. 실패 전에 일부 바이트가 이미 전달됐을 수 있고, A안의 판단 기준은 완전한 응답 전송에 실패했다는 점이야.

참고본에서 추가로 언급한 수신 데이터 1 MiB 상한과 종료 순서는 기준 코드의 `connection_close_lingering`에서 확인할 사항이야.

#### 어떻게 검증할 것인가?

원본의 재현 명령은 아래 회귀 기준으로 바꿨어.

방어용 회귀 기준으로 전송 함수를 대역으로 바꿔 쓰기 실패를 반환해. 정적·오류·CGI 세 경로 모두 `CONN_CLOSE_SILENT`로 끝나고 `connection_close_lingering`을 호출하지 않는지 확인해. 정상 전송 뒤 연결을 닫는 경우에는 기존 `CONN_CLOSE_REPLIED` 경로를 확인해.

기대: 고치면 같은 명령에서 약 1초 줄어듦. `nc`가 받아 두는 양에 따라 절댓값은 위 표와 다를 수 있음.

### F3. 오류 페이지가 요청에서 온 HTML을 그대로 출력함

#### 어떤 문제인가?

서버가 404나 403 오류 페이지에 요청 경로를 보여줄 때, 경로에 섞인 HTML 특수문자가 그대로 출력돼. 브라우저가 그 내용을 페이지의 마크업으로 해석하면 스크립트 실행으로 이어질 수 있어.

#### 왜 발생하는가?

`error_reply_extra`는 오류를 일으킨 입력 일부를 `cause`로 받아 HTML에 붙여. HTML 이스케이프는 예를 들어 `<`를 `&lt;`로 바꿔 브라우저가 태그의 시작 기호를 화면에 표시할 글자로 읽게 하는 일이야.

```text
요청에서 온 cause → 오류 페이지 HTML 생성
                     ├─ 현재  → 특수문자가 HTML 문법으로 해석될 수 있음
                     └─ A안   → 특수문자를 이스케이프 → 화면에 글자로 표시
```

#### 어떤 영향이 있는가?

입력이 오류 HTML에 되돌아가 스크립트로 실행되는 경우를 반사형 XSS라고 해. 원본이 확인한 관찰은 서버가 입력을 변환하지 않고 내보낸다는 점이야.

#### 어떻게 수정할 것인가?

| 선택지                                             | 장점                                  | 단점                                        |
| -------------------------------------------------- | ------------------------------------- | ------------------------------------------- |
| **A. `< > & "`를 `&lt; &gt; &amp; &quot;`로 변환** | 오류 페이지에 요청 정보가 그대로 남음 | 변환 함수를 추가해야 함                     |
| B. 오류 페이지에 `cause`를 넣지 않음               | 가장 단순하고 안전함                  | 어떤 경로가 문제였는지 페이지에 나오지 않음 |

- **권장안: A.**

#### 기술 근거 및 코드 위치

|                  |                                                                                                                                                                                                                                                    |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 언제             | 404나 403이 나는 URL에 HTML 태그를 넣었을 때                                                                                                                                                                                                       |
| 원인과 코드 위치 | `error_reply_extra`가 요청에서 온 글자(`cause`)를 변환하지 않고 HTML에 넣음(`tiny.c:623`\~`629`)                                                                                                                                                   |
| 영향             | 공격자가 만든 링크를 누르면 그 스크립트가 우리 서버 주소에서 실행될 수 있음(반사형 XSS). 브라우저는 주소의 `<`를 보통 `%3C`로 바꿔 보내고 서버는 `%`를 해석하지 않아서, 실제 브라우저에서는 막히는 경우가 많음. curl로는 그대로 나가는 것을 확인함 |

- 참고 커밋: `f0d0765`

#### 정확성 확인

원본의 curl 확인은 응답에 태그가 반영됐다는 관찰이야. 일반 브라우저에서 링크를 열어 실제로 스크립트가 실행되는지는 주소 인코딩, 서버의 디코딩 처리, 브라우저 동작 등을 따로 확인해야 해. 브라우저에서 막히는 빈도도 원본에 측정값이 없어.

#### 어떻게 검증할 것인가?

원본의 재현 명령은 아래 회귀 기준으로 바꿨어.

오류 HTML 생성 테스트에 `<`, `>`, `&`, `"`가 포함된 일반 문자열을 넣어. A안을 적용하면 네 문자가 각각 HTML 엔티티로 출력되는지 확인해. 404·403 상태와 화면에 표시되는 오류 정보도 유지되는지 확인해.

기대: 지금은 `<script>`가 그대로. 고치면 `&lt;script&gt;`.

### F4. HEAD 요청의 204 중계 응답에 Content-Length가 남음 (PRD 규칙이 겹침)

#### 어떤 문제인가?

클라이언트의 HEAD 요청에 백엔드가 `204 No Content`로 응답했어. HEAD 응답과 204 응답은 각각 본문을 보낼 수 없어. 이 조합에서는 `Content-Length`도 없어야 하는데 현재 중계 응답에는 값 5가 남아.

#### 왜 발생하는가?

HEAD는 “같은 GET 요청이라면 어떤 헤더를 받을까”를 물어보는 요청 메서드야. 204는 서버가 보낼 본문이 없다는 응답 상태야. `proxy_response_parse`가 HEAD를 먼저 처리하면 백엔드의 길이 값이 전달돼. A안은 204를 먼저 검사해 두 조건이 겹칠 때도 204 규칙을 적용해.

| 요청과 응답 상태    | 본문         | Content-Length                                                     |
| ------------------- | ------------ | ------------------------------------------------------------------ |
| GET + 200           | 보낼 수 있음 | 길이를 미리 알고 전송 인코딩을 쓰지 않으면 보내는 것을 권장        |
| HEAD + 200          | 없음         | 선택 사항. 보낸다면 같은 요청을 GET으로 보냈을 때의 본문 바이트 수 |
| GET 또는 HEAD + 204 | 없음         | 금지. 값이 0이어도 헤더를 보내면 안 됨                             |

[RFC 9110 §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6), [§9.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2), [§15.3.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.5)

#### 어떤 영향이 있는가?

원본 실측에서 GET + 204에는 이 헤더가 없었고 HEAD + 204에만 남았어. 두 경우에 본문이 전송되지는 않았어.

#### 어떻게 수정할 것인가?

| 선택지                                                              | 장점                        | 단점            |
| ------------------------------------------------------------------- | --------------------------- | --------------- |
| **A. 204를 HEAD보다 먼저 검사하고, PRD 표에도 "204가 우선"을 적음** | RFC에 맞고 검사 순서만 바뀜 | 없음            |
| B. 그대로 둠                                                        | 변경 없음                   | RFC 위반이 남음 |

- **권장안: A.**

#### 기술 근거 및 코드 위치

|                  |                                                                                              |
| ---------------- | -------------------------------------------------------------------------------------------- |
| 언제             | HEAD 요청에 백엔드가 204와 `Content-Length`를 함께 보낼 때                                   |
| 원인과 코드 위치 | `proxy_response_parse`가 HEAD를 204보다 먼저 검사함(`proxy.c:499`\~`503`)                    |
| PRD              | `m6m7.md` 502행 "HEAD: 백엔드 값"과 503행 "204: 없음"이 겹침. 어느 쪽이 먼저인지 정하지 않음 |
| 근거             | RFC 9110 8.6 "204에 `Content-Length`를 보내면 안 됨(MUST NOT)"                               |
| 영향             | 본문은 안 나가서 다음 응답에 영향이 없음                                                     |
| 실측             | GET + 204는 길이 없음, HEAD + 204는 `Content-Length: 5`                                      |

#### 어떻게 검증할 것인가?

```bash
(printf 'HTTP/1.0 204 No Content\r\nContent-Length: 5\r\n\r\n' | nc -lN 8001 >/dev/null) & sleep 0.5
curl -s -I localhost:8000/api/x
```

기대: 지금은 `Content-Length: 5`, 고치면 그 줄이 없음.

### F5. HEAD 요청 줄 검사에 실패하면 오류 본문을 보냄

#### 어떤 문제인가?

클라이언트가 `HEAD / HTTP/2.0`이라는 요청 줄을 보내면 서버가 505 오류를 응답해. 오류 페이지 본문이 함께 나가는데, HEAD에 대한 응답은 오류여도 본문을 보내면 안 돼.

#### 왜 발생하는가?

클라이언트에게서 요청을 받을 때 어떤 HTTP 버전을 받아들이는지와 서버가 백엔드에 보낼 요청의 버전을 HTTP/1.0으로 정하는 것은 각각의 연결에서 적용되는 규칙이야. 이 사례에서는 수신 요청 줄의 버전 검사에서 오류가 나. 백엔드로 전달하기 전에 우리 서버가 처음 요청한 클라이언트에게 505를 응답해.

```text
클라이언트 → 우리 서버 → 백엔드 (실제로 중계하는 경우, HTTP/1.0)
             │
             └─ 수신 버전 검사 실패 → 최초 클라이언트에 505
현재: 버전·URI 검사 실패 → HEAD 미저장 → 오류 헤더와 본문 전송
A안:  HEAD 저장 후 검사 → 검사 실패  → 오류 헤더만 전송
```

A안은 파서가 알아낼 수 있는 요청 메서드를 먼저 저장하는 방식이야. 여기서 `HEAD / HTTP/2.0`은 HTTP/1.x 형식의 텍스트 요청 줄에 지원하지 않는 버전을 적은 사례야. [RFC 9110 §9.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2), [§15.6.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.6)

#### 어떤 영향이 있는가?

요청 줄 검사를 통과한 HEAD 요청에서 파일을 못 찾아 404를 내는 경우에는 이미 메서드가 저장돼 있어. 오류 응답을 만드는 코드는 이때 HEAD를 알아보고 본문을 빼. F5는 그보다 앞선 검사에서 실패하는 경우에도 같은 판단이 가능하도록 하는 수정이야.

원본의 505 사례에서는 오류 응답 뒤 연결을 닫아. 클라이언트가 받는 505 상태는 그대로 두고, 불필요한 본문을 빼는 변경이야.

#### 어떻게 수정할 것인가?

| 선택지                                              | 장점                                                             | 단점                                      |
| --------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------- |
| **A. 파서가 메서드를 먼저 저장한 뒤 나머지를 검사** | 저장 순서만 바뀌고, 모든 오류 응답이 같은 방식으로 HEAD를 판단함 | 파서 단위 테스트를 함께 고쳐야 할 수 있음 |
| B. 오류 응답에서 요청 줄을 다시 읽어 HEAD인지 판단  | 파서를 건드리지 않음                                             | 메서드를 두 곳에서 해석하게 됨            |

- **권장안: A.**

#### 기술 근거 및 코드 위치

|                  |                                                                                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 언제             | HEAD 요청의 버전이나 URI가 틀렸을 때                                                                                                            |
| 원인과 코드 위치 | 본문을 뺄지는 `req->method`를 보고 정하는데(`tiny.c:621`), 파서가 버전과 URI를 먼저 검사해 실패하면 메서드를 저장하지 않음(저장은 `http.c:165`) |
| 근거             | RFC 9110 9.3.2 "HEAD 응답에 본문을 보내면 안 됨(MUST NOT)"                                                                                      |
| 영향             | 응답 뒤 연결을 닫으므로 다음 요청에는 영향이 없음                                                                                               |

#### 어떻게 검증할 것인가?

```bash
(printf 'HEAD / HTTP/2.0\r\nHost: x\r\n\r\n'; sleep 1) | nc localhost 8000
```

기대: 지금은 505 뒤에 HTML 본문, 고치면 헤더만.

### F6. 긴 PATH를 CGI에 넘길 때 뒤쪽 경로가 잘림

#### 어떤 문제인가?

CGI는 웹 서버가 실행하는 외부 프로그램이야. CGI가 프로그램 이름만으로 다른 명령을 실행하면 `PATH`에 나열된 폴더를 순서대로 찾아. 끝쪽 폴더가 잘리면 거기에만 있는 명령을 찾지 못할 수 있어.

#### 왜 발생하는가?

서버는 CGI에 넘기는 환경 변수 문자열을 고정 배열에 만들어. 1,024바이트에서 앞의 `PATH=` 5바이트와 문자열 끝을 표시하는 NUL 1바이트를 빼면 값에 1,018바이트가 남아. WSL에서는 Windows 경로가 뒤에 더해져 길어지기 쉬워.

```text
서버 PATH → [PATH= 5바이트 | 값 최대 1,018바이트 | NUL 1바이트] → CGI
            고정 버퍼에 들어가지 않은 값의 뒤쪽은 전달되지 않음
```

#### 어떤 영향이 있는가?

뒤쪽 경로에만 있는 명령이 있거나 한 경로의 중간이 잘린 경우, CGI의 명령 탐색에 문제가 생길 수 있어.

#### 어떻게 수정할 것인가?

| 선택지                         | 장점                                                                                       | 단점                  |
| ------------------------------ | ------------------------------------------------------------------------------------------ | --------------------- |
| **A. 시작할 때 길이만큼 할당** | 길이 상한이 없어짐. `fork` 전에 한 번만 만들어 두므로 자식에서 할당하지 않는 규칙도 지켜짐 | 종료할 때 해제해야 함 |
| B. 버퍼를 크게(예: 8 KiB) 늘림 | 한 줄 수정                                                                                 | 상한이 남음           |

- **권장안: A.**

#### 기술 근거 및 코드 위치

|                  |                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------- |
| 언제             | 서버의 `PATH`가 1,018자를 넘을 때. WSL은 Windows 경로가 붙어 길어지기 쉬움         |
| 원인과 코드 위치 | `path_env[1024]`(`tiny.c:59`)에 `PATH=`(5자)와 함께 담음(`194`)                    |
| PRD              | CGI에 `PATH`를 넘기는 것 자체가 초안 PRD에 없던 구현. `final.md` 5.4에는 적혀 있음 |
| 영향             | 뒤쪽 폴더의 프로그램을 CGI 스크립트가 못 찾음                                      |
| 실측             | 3,014자를 주면 CGI는 1,018자만 받음                                                |

- 참고 커밋: `f0d0765`

#### 정확성 확인

배열 한계의 단위는 바이트야. 원본의 재현은 ASCII 문자열을 써서 문자 수와 바이트 수가 같아. 실측 표의 입력 3,014자와 재현 명령의 입력 2,015자는 별도 사례야.

#### 어떻게 검증할 것인가?

```bash
printf '#!/bin/sh\nprintf "Content-type: text/plain\\r\\n\\r\\n%%s\\n" "${#PATH}"\n' > /tmp/www/cgi-bin/pathlen && chmod +x /tmp/www/cgi-bin/pathlen
PATH="/usr/bin:/bin:/$(printf 'a%.0s' $(seq 2000))" ./build/tiny 8011 --root /tmp/www & T=$!; sleep 0.5
curl -s localhost:8011/cgi-bin/pathlen; kill $T
```

기대: 지금은 1018, 고치면 2015.

### F7. adder가 계산 가능한 합도 입력 상한 때문에 거절함

#### 어떤 문제인가?

`2,000,000,000 + 1`은 32비트 `int` 범위 안의 결과야. 그런데 현재 `adder`는 첫 번째 숫자가 1,073,741,823을 넘는다는 이유로 계산 전에 거절해.

#### 왜 발생하는가?

큰 수 두 개를 더했을 때 `int` 범위를 벗어나는 일을 막기 위해 현재는 입력 하나하나의 상한을 낮게 잡아. A안은 입력을 읽은 뒤 덧셈 전에 `long long`으로 넓혀 계산하고, 얻은 합이 결과에 쓰는 `int` 범위에 드는지 확인해.

```text
2,000,000,000과 1
  현재 → 입력 하나씩 상한 검사 → 첫 숫자에서 거절
  A안  → 넓은 타입으로 덧셈 → 합 2,000,000,001의 범위 검사 → 표시
```

#### 어떤 영향이 있는가?

변경 효과는 CGI 예제 `adder`에 있어. 입력 문자열이 유효한 숫자인지 확인하는 검사도 계속 필요해.

#### 어떻게 수정할 것인가?

| 선택지                                 | 장점                             | 단점                            |
| -------------------------------------- | -------------------------------- | ------------------------------- |
| **A. `long long`으로 더해 합을 검사**  | `int` 범위 안의 합은 모두 계산함 | 없음                            |
| B. 그대로 두고 안내 문구만 범위를 명시 | 코드 변경이 거의 없음            | 계산할 수 있는 수를 계속 거절함 |

- **권장안: A.**

#### 기술 근거 및 코드 위치

|                  |                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------- |
| 언제             | 입력 하나가 1,073,741,823을 넘을 때                                                |
| 원인과 코드 위치 | 덧셈이 넘치지 않게 입력을 `int` 범위의 절반으로 제한함(`adder.c:27`)               |
| PRD              | `m4m5.md` 450행 "범위 초과에는 안내 메시지". 입력 기준인지 합 기준인지 정하지 않음 |
| 영향             | CGI 예제에만 영향                                                                  |

- 참고 커밋: `61cdc59`

#### 정확성 확인

원본 PRD는 “범위 초과”의 대상이 입력인지 합인지 정하지 않았어. 허용할 입력의 범위는 구현에서 확인해야 해. 두 입력을 원래 `int` 범위로 받는 경우에는 덧셈 전에 `long long`으로 변환하면 32비트 `int` 덧셈의 오버플로를 피할 수 있어.

#### 어떻게 검증할 것인가?

```bash
curl -s 'localhost:8000/cgi-bin/adder?2000000000&1' | grep -E 'answer|Invalid'
```

기대: 지금은 `Invalid number`, 고치면 `2000000001`.

## 4. 논의 항목 (F8\~F11)

### F8. CGI 출력에서 HTTP 응답 규칙 검사가 빠져 응답 경계가 어긋남

#### 어떤 문제인가?

CGI가 본문이 없어야 하는 응답 상태에 본문을 붙여도 현재 서버는 그대로 내보낼 수 있어. 연결을 재사용하면 클라이언트가 그 바이트를 다음 응답의 첫 부분으로 읽을 수 있어.

#### 왜 발생하는가?

모든 응답은 클라이언트에 나갈 때 HTTP 규칙을 지켜야 해. 정적 파일이나 오류 응답은 우리 서버가 헤더와 본문을 만들어. CGI와 중계는 다른 프로그램의 출력을 받아 HTTP 응답에 반영하므로 입력을 확인하는 단계가 중요해.

```text
정적·오류  서버가 HTTP 응답을 생성 ──────────────────→ 클라이언트
중계       백엔드 응답 → proxy_response_parse 검사 ─→ 클라이언트
CGI        CGI 출력   → cgi_reply의 제한된 검사 ────→ 클라이언트
```

프록시는 이미 `proxy_response_parse`에서 백엔드 응답을 검사해. CGI 경로의 `cgi_reply`는 CGI 출력을 빈 줄에서 헤더와 본문으로 나눠. `Status`는 HTTP 상태 줄에 옮기고, `Content-Length`와 `Connection`은 서버에서 정해. 나머지 헤더는 제한된 검사 뒤 응답에 붙여.

CGI는 PRD에서 헤더를 그대로 전달하기로 했고, 예외적인 CGI 출력을 어떻게 다룰지는 정하지 않았어. `adder`의 정상 출력에서는 아래 예외가 나타나지 않아.

#### 어떤 영향이 있는가?

204는 헤더가 끝나는 빈 줄에서 응답이 끝나. 그 뒤에 본문이 나가면 연결에서 다음 HTTP 응답이 시작하는 위치가 어긋나. 1xx는 중간 응답이고, 헤더 이름과 값, 전송 길이 역시 각각 검사할 규칙이 있어. 구체적인 사례는 아래 기술 근거 표에 있어. [RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)

#### 어떻게 수정할 것인가?

| 선택지                                                                                                                                              | 장점                                                           | 단점                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **A. 백엔드 응답 검사(`proxy_response_parse`)와 같은 규칙. 204·304는 본문과 길이를 빼고, 1xx·`Transfer-Encoding`·잘못된 헤더 이름·제어 문자는 500** | 중계와 CGI가 같은 규칙을 씁. 위 표의 모든 경우가 RFC에 맞게 됨 | 수정량이 가장 큼. 지금 통과하던 CGI 출력 일부가 500이 됨                             |
| B. 204·304만 본문과 길이를 뺄                                                                                                                       | 가장 큰 문제인 응답 섞임을 작은 수정으로 막음                  | `Transfer-Encoding`과 `Content-Length`가 함께 나가는 문제, 잘못된 헤더가 그대로 남음 |
| C. 204·304·1xx를 모두 500으로 거절                                                                                                                  | 규칙이 단순함                                                  | 204를 정상적으로 쓰는 CGI도 실패함                                                   |

- **권장안: A.** 중계에 이미 같은 규칙이 있어서 "서버가 내보내는 응답의 규칙"을 하나로 설명할 수 있음.
- 정할 것: 검사 범위(A, B, C 중 어느 것).

#### 기술 근거 및 코드 위치

|                  |                                                                                                                                                                                                                            |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 언제             | CGI가 아래 표처럼 출력할 때. `adder`는 이렇게 출력하지 않음                                                                                                                                                                |
| 원인과 코드 위치 | `cgi_reply`(`tiny.c:1247`)는 `:`이 없는 줄(`1288`)과 잘못된 `Status`만 막고, `Content-Length`와 `Connection` 외의 헤더를 그대로 붙임(`1325`\~`1333`). 상태는 100\~599를 모두 받고(`1307`) 본문을 항상 보냄(`1339`\~`1342`) |
| PRD              | `m4m5.md` 432행 "CGI 헤더: 그대로 전달". 코드가 PRD를 어긴 게 아니라 PRD가 예상하지 못함                                                                                                                                   |
| 영향             | 연결을 유지하면 남은 본문을 클라이언트가 다음 응답의 시작으로 읽음                                                                                                                                                         |

| CGI 출력                     | 지금 나가는 것                   | 근거                                                                                                                     |
| ---------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `Status: 204` + 본문 `BODY`  | 204, `Content-Length: 4`, `BODY` | 9110 15.3.5 "204는 헤더에서 끝나고 본문을 가질 수 없음", 8.6 "204에 `Content-Length`를 보내면 안 됨(MUST NOT)", 9112 6.3 |
| `Status: 100`                | 100을 최종 응답으로              | 9110 15.2 "1xx는 헤더에서 끝남". 최종 응답은 따로 와야 함                                                                |
| `Transfer-Encoding: chunked` | 서버의 `Content-Length`와 함께   | 9112 6.2 "`Transfer-Encoding`이 있으면 `Content-Length`를 보내면 안 됨(MUST NOT)"                                        |
| `Bad Name: x`, `: x`         | 그대로                           | 9110 5.1, 3875 6.3 "헤더 이름은 token"                                                                                   |
| `X: a\rb`                    | 그대로                           | 9110 5.5 "CR·LF·NUL이 든 값은 거절하거나 공백으로 바꿔야 함(MUST)"                                                       |

- 참고 커밋: `45ec2a7`(204·304, 1xx, `Transfer-Encoding`), `7383e40`(헤더 이름, 제어 문자)

#### 정확성 확인

304에서는 본문을 보낼 수 없어. 조건부 GET의 304 응답에는 같은 요청에 200을 보냈을 때의 본문 바이트 수와 일치하는 `Content-Length`를 선택적으로 보낼 수 있어. 원본 A·B안이 304의 길이도 빼는 것은 이 서버에서 택하려는 처리 규칙이야. 204에서는 `Content-Length` 금지가 HTTP 규칙이야. [RFC 9110 §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6), [§15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5)

#### 어떻게 검증할 것인가?

원본의 재현 명령은 아래 회귀 기준으로 바꿨어.

방어용 응답 생성 테스트에서 A·B안의 204와 304가 헤더에서 끝나고 `Content-Length`가 없는지 확인해. 응답을 연속으로 읽는 테스트는 다음 상태 줄이 바로 시작하는지 검사해. A안을 택하면 1xx 상태, `Transfer-Encoding` 헤더, 잘못된 헤더 이름, 제어 문자가 들면 각각 500으로 처리되는지도 확인해.

기대: 지금은 `BODYHTTP/1.1 200 OK`로 붙어 나옴. 고치면 204 헤더 바로 뒤에 200.

### F9. 정적 파일 경로에 쿼리가 섞이고 CGI 판단 범위도 넓음 (동작 변경)

#### 어떤 문제인가?

두 군데를 고치는 항목이야. 하나는 디스크에서 어떤 파일을 찾을지, 다른 하나는 파일을 읽을지 CGI 프로그램을 실행할지 정하는 부분이야.

#### 왜 발생하는가?

쿼리는 URL에서 `?` 뒤에 붙는 부가 정보야. 예를 들어 `/style.css?v=1`에서 파일 경로는 `/style.css`이고 쿼리는 `v=1`이야.

| 판단                 | 현재                                     | A안                                               |
| -------------------- | ---------------------------------------- | ------------------------------------------------- |
| 디스크에서 찾을 경로 | `/style.css?v=1` 전체를 파일 경로로 사용 | `?` 앞의 `/style.css`로 파일을 찾음               |
| CGI 여부             | URI 전체에서 `cgi-bin`을 찾음            | `?` 앞 경로의 첫 조각이 `cgi-bin`일 때 CGI로 판단 |

라우팅과 경로 검사는 이미 `?` 앞을 본다고 원본에 적혀 있어. 파일 경로와 CGI 판단에서도 경로와 쿼리를 먼저 구분하는 게 A안이야.

#### 어떤 영향이 있는가?

예를 들어 CSS를 수정한 뒤 `v=1`을 `v=2`로 바꾸면 브라우저가 새 URL로 요청해. 두 요청에서 서버가 찾아야 할 파일은 모두 `/style.css`야. 지금은 쿼리까지 파일 이름으로 써서 이런 요청이 실패해.

A안에서는 경로 첫 조각을 기준으로 삼으므로 `/a/cgi-bin/x`는 기존 CGI 처리에서 정적 파일 처리로 바뀌어. 팀에서는 이 동작 변경을 받아들일지 결정해야 해.

#### 어떻게 수정할 것인가?

| 선택지                                                                      | 장점                                                                                      | 단점                                                                     |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **A. `?`에서 자른 경로로 파일을 찾고, 첫 경로 조각이 `cgi-bin`일 때만 CGI** | 라우팅·경로 검사와 같은 기준(`?` 앞)을 씁. 파일 이름에 `cgi-bin`이 들어가도 오판하지 않음 | `/a/cgi-bin/x`가 CGI에서 정적 파일로 바뀜                                |
| B. `?`만 자르고, CGI 판정은 `?` 앞 경로에 `cgi-bin`이 들어 있으면 CGI       | 지금 CGI로 처리되는 경로가 그대로 유지됨                                                  | `/docs/cgi-bin-notes.html`처럼 이름에 `cgi-bin`이 든 파일이 CGI로 판단됨 |

- **권장안: A.**
- 정할 것: `/a/cgi-bin/x`가 정적 파일로 바뀌는 동작 변경을 받아들일지.

#### 기술 근거 및 코드 위치

|                  |                                                                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 언제             | 정적 파일 URL에 쿼리가 있을 때                                                                                                                                        |
| 원인과 코드 위치 | `uri_parse`가 정적 파일이면 쿼리를 떼지 않고 파일 이름으로 씀(`tiny.c:1013`). CGI인지는 URI 전체에서 `cgi-bin`을 찾아 정함(`tiny.c:1011`). Phase 1 규칙이 그대로 남음 |
| PRD              | 정적 파일의 쿼리 규칙은 없음. 라우팅은 `?` 앞만 봄(`m6m7.md` 198행), 경로 검사도 `?` 앞만 봄(327행)                                                                   |
| 영향             | `?v=1`처럼 흔한 주소가 실패하고, 쿼리 글자 때문에 CGI로 잘못 판단함                                                                                                   |

- 참고 커밋: `230ab53`

#### 정확성 확인

원본은 첫 경로 조각 비교를 제안하고, 대화에서는 이를 `/cgi-bin/`으로 시작하는 경우로 풀어 설명했어. `/cgi-bin`처럼 뒤에 슬래시나 스크립트 이름이 없는 경계에서 두 표현의 동작이 같은지는 기준 코드와 합의된 테스트로 확인해야 해.

#### 어떻게 검증할 것인가?

원본의 CGI 오분류 재현 명령은 파서 회귀 기준으로 바꿨어.

아래 명령은 정적 파일 경로에서 쿼리를 분리하는 동작을 확인해. CGI 분류는 파서 단위 테스트에서 경로와 쿼리를 따로 비교해. 정적 경로의 쿼리 내용이 정적·CGI 분류에 영향을 주지 않는지 확인해.

### F10. 경로로 라우팅하지만 잘못된 Host는 별도로 걸러야 함

#### 어떤 문제인가?

`/api/` 같은 경로 접두사로 백엔드를 고르는 현재 방식은 그대로야. 별도로 HTTP/1.1 요청의 `Host`가 올바른 형태인지 확인해서 값이 잘못되면 400으로 응답하는 항목이야.

#### 왜 발생하는가?

`Host`는 요청 대상의 호스트 이름과 필요하면 포트를 담는 헤더야. 경로 접두사 검사는 어느 백엔드로 보낼지 결정하고, `Host` 검사는 요청을 받을 수 있는 형식인지 확인해.

```text
HTTP/1.1 요청
  → Host 필드 검사  → 형식 오류면 400
  → 유효한 요청의 경로 접두사로 처리 경로 선택
  → /api/는 설정된 백엔드로 중계
```

이 도식은 제안된 판단 흐름을 보여줘. 원본에서 확인 가능한 것은 현재 검사 범위가 개수와 길이라는 점이야. [RFC 9110 §7.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.2), [RFC 9112 §3.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2)

#### 어떤 영향이 있는가?

형식 검사가 빠지면 우리 서버가 잘못된 값을 받아들이고, 중계 요청에서는 그 값이 백엔드 요청에 다시 쓰일 수 있어.

#### 어떻게 수정할 것인가?

| 선택지                                                  | 장점                                              | 단점                                              |
| ------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------- |
| **A. 이름, 포트, IPv6, `%` 인코딩 형식까지 검사해 400** | RFC 규칙에 가장 가까움. 참고 구현과 테스트가 있음 | 수정량이 늘고 규칙이 복잡해짐                     |
| B. 허용 문자와 포트가 숫자인지만 검사                   | 짧고, `a/b` 같은 명백한 오류는 거절함             | `[`의 짝이 안 맞는 것처럼 일부 틀린 형식은 통과함 |

- **권장안: A.** 참고 구현과 테스트가 있어서 수정 부담이 생각보다 작음.
- 정할 것: 검사 범위(A 또는 B).

#### 기술 근거 및 코드 위치

|                  |                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------- |
| 언제             | `Host: a/b`처럼 틀린 값을 보냈을 때                                                |
| 원인과 코드 위치 | Host는 개수(`http.c:328`)와 길이(`286`)만 검사함                                   |
| 근거             | RFC 9112 3.2 "형식이 틀린 Host에는 400으로 응답해야 함(MUST)"                      |
| PRD              | `m4m5.md` 286·537행은 없음과 중복만 400                                            |
| 영향             | 중계하면 틀린 값이 백엔드에 그대로 감(`proxy.c`의 `proxy_request_build`가 다시 씀) |

- 참고 커밋: `a26984e`(처음 검사), `7383e40`(IPv6와 `%` 보완)

#### 어떻게 검증할 것인가?

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H 'Host: a/b' localhost:8000/home.html
```

기대: 지금은 200, 고치면 400.

### F11. 긴 Connection 값의 뒤쪽에 있는 close를 놓침 (PRD와 다름)

#### 어떤 문제인가?

응. `Connection` 값이 서버가 허용하는 길이 안에 있고 문법도 맞으면, 맨 끝의 `close`도 처리해야 해. `Connection`은 쉼표로 옵션을 구분하는 목록이라 `close`가 앞에 올 필요는 없어. 길이가 너무 긴 요청을 거절하는 방식도 가능해.

#### 왜 발생하는가?

현재 헤더 한 줄은 8,191바이트까지 받을 수 있어. 그런데 `connection_parse`는 값을 256바이트 버퍼에 옮기면서 앞의 최대 255바이트만 봐서, 뒤쪽 `close`를 제대로 읽지 못할 수 있어.

```text
수신: 헤더 한 줄 최대 8,191바이트
검사: Connection 값 중 앞 255바이트만 확인 → 뒤쪽 close를 놓칠 수 있음
A안: 받은 값 전체를 검사                         → close면 응답 후 닫기
B안: Connection 값에 명시적 상한 적용              → 초과하면 400
```

8,191바이트는 헤더 이름 등을 포함하는 줄의 수신 한계야. 255바이트는 값의 검사 한계야. 서버가 받아들인 값은 전부 해석하고, 처리할 상한을 넘긴 요청은 적절한 4xx 응답으로 거절하는 규칙이 적용돼. 원본의 B안은 400을 제안해. [RFC 9110 §5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.4), [§7.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.6.1), [RFC 9112 §9.6](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6)

#### 어떤 영향이 있는가?

원본 명령은 `close`가 마지막에 있는 값에서 255자와 256자를 비교해. 현재는 경계를 하나 넘기면 연결이 유지돼. A안이라면 두 경우 모두 응답을 보낸 뒤 닫혀야 해.

#### 어떻게 수정할 것인가?

| 선택지                              | 장점                                               | 단점                                                    |
| ----------------------------------- | -------------------------------------------------- | ------------------------------------------------------- |
| **A. 복사하지 않고 값 전체를 훑음** | 길이와 상관없이 `close`를 인식함. PRD와 RFC에 맞음 | `connection_parse`를 고쳐야 함                          |
| B. 값이 너무 길면 400으로 거절      | 구현이 간단함                                      | 정상 요청까지 막을 수 있음                              |
| C. 버퍼만 키움                      | 한 줄 수정                                         | 헤더 한 줄이 8,191바이트까지라 같은 문제가 남을 수 있음 |

- **권장안: A.**
- 정할 것: A와 B 중 어느 쪽으로 할지.

#### 기술 근거 및 코드 위치

|                  |                                                                                                                                  |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 언제             | `Connection` 값이 256자 이상이고 `close`가 뒤에 있을 때                                                                          |
| 원인과 코드 위치 | `connection_parse`가 값을 256바이트 버퍼에 복사하며 앞 255자만 봄(`http.c:203`, `209`\~`210`). 헤더 한 줄은 8,191바이트까지 받음 |
| PRD              | `m4m5.md` 489행 "HTTP/1.1, `Connection: close` → 닫음"                                                                           |
| 근거             | RFC 9112 9.6 "`close`를 받은 서버는 응답 뒤 연결을 닫아야 함(MUST)"                                                              |
| 영향             | 정상 클라이언트는 이렇게 보내지 않아 영향이 작음                                                                                 |
| 실측             | 값 255자는 `close`, 256자부터 `keep-alive`                                                                                       |

#### 정확성 확인

실측의 “256자부터”는 원본 재현처럼 단일 `close`가 값의 맨 끝에 있는 테스트를 설명해. 값 전체가 길어도 `close`가 잘리지 않고 검사 범위 앞쪽에 있으면 현재 코드가 인식할 수 있어.

#### 어떻게 검증할 것인가?

```bash
for n in 248 249; do curl -s -D - -o /dev/null -H "Connection: $(printf 'a%.0s' $(seq $n)), close" localhost:8000/home.html | grep -i ^connection; done
```

기대: 지금은 `close`, `keep-alive`. 고치면 둘 다 `close`.

## 5. 마지막 커밋 (F12)

### F12. tiny.c와 adder.c를 코드 포맷 검사에 다시 포함함

#### 어떤 문제인가?

`.clang-format-ignore`에 있는 `tiny.c`와 `adder.c` 제외 항목 두 줄을 제거해. 팀이 작성하고 관리하는 코드라 두 파일에도 팀의 코드 포맷 규칙을 적용하자는 작업이야.

#### 왜 발생하는가?

`.clang-format`은 팀의 포맷 규칙을 담아. 두 파일이 `.clang-format-ignore`에 남아 있어서 `make lint`의 포맷 검사에서 건너뛰어. 원본 문서에 따르면 Phase 1에서 팀 코드로 교체됐고 이후에도 크게 수정된 파일들이야.

#### 어떤 영향이 있는가?

제외를 없앴을 때의 원본 수치는 `tiny.c` 경고 19건, `adder.c` 경고 0건이야. `tiny.c`의 줄 번호가 바뀔 수 있어서 F1~F11을 마친 뒤 마지막에 따로 커밋해.

#### 어떻게 수정할 것인가?

| 선택지                            | 장점                                 | 단점                      |
| --------------------------------- | ------------------------------------ | ------------------------- |
| **A. 두 줄을 빼고 `make format`** | 팀 코드 전체가 같은 모양 규칙을 따름 | `tiny.c`의 줄 번호가 밀림 |
| B. 그대로 둠                      | 변경 없음                            | 팀 코드가 규칙 밖에 남음  |

- **권장안: A.** 줄 번호가 밀려 이 문서의 코드 위치가 맞지 않게 되므로, F1\~F11을 모두 고친 뒤 마지막에 따로 커밋함.

#### 기술 근거 및 코드 위치

|      |                                                                                           |
| ---- | ----------------------------------------------------------------------------------------- |
| 현재 | `.clang-format-ignore` 1, 5, 6행이 "우리가 쓰지 않은 코드"로 `tiny.c`, `adder.c`를 제외함 |
| 실제 | 원본 Tiny에서 시작했지만 Phase 1에서 팀 코드로 모두 교체했고 이후 크게 고침               |
| 빼면 | `tiny.c` 경고 19건, `adder.c` 0건                                                         |

#### 어떻게 검증할 것인가?

A안의 `make format`을 실행한 뒤 두 파일이 포맷 검사 대상에 포함되는지 확인해. 제외 항목 두 줄 제거와 포맷 변경을 마지막 커밋에서 확인하면 돼.
