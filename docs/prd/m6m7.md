### 실행 방법

```text
./build/tiny <port> [--root DIR] [--threads N] [--queue N] [--timeout 초] [--keepalive-max N]
                    [--route 접두사=이름:포트,이름:포트]... [--proxy-timeout 초]
```

| 인자 | 기본값 | 적용 범위 |
| --- | --- | --- |
| `--route` | 없음 | 라우팅 규칙 하나. 여러 번 지정할 수 있고 규칙은 최대 16개, 규칙당 백엔드는 최대 8개 |
| `--proxy-timeout` | 10 | 백엔드 연결부터 최종 응답 헤더까지의 합계 시간, 그리고 본문을 읽을 때 새 데이터를 기다리는 시간 |
| `--timeout` | 5 | 클라이언트 읽기 타임아웃. 요청 줄·헤더 마감은 2배, 본문 마감은 6배 |

나머지 인자는 [m4m5.md의 실행 방법](m4m5.md#실행-방법)을 따릅니다.

## 1. 목표와 범위

### 완료 기준

**M6**

- `--route /api=127.0.0.1:8001,127.0.0.1:8002`로 켠 서버에 `GET /api/users`를 반복하면 두 백엔드가 번갈아 응답합니다.
- `/api` 규칙에 걸리지 않는 요청(`/home.html`, `/cgi-bin/adder?1&2`)은 서버가 직접 응답합니다.
- GET, POST, HEAD가 백엔드까지 전달됩니다.
- 백엔드 하나가 꺼져도 남은 백엔드가 응답합니다. 모두 꺼지면 `502`, 응답하지 않으면 `504`를 받습니다.
- 응답 길이를 아는 프록시 응답 뒤에는 클라이언트 연결이 유지됩니다.

**M7**

- SIGINT나 SIGTERM을 받으면 처리 중인 요청을 마치고 종료 로그를 남긴 뒤 종료 코드 0으로 끝나며, 누수 보고가 없습니다.
- 종료 중에 SIGINT나 SIGTERM이 한 번 더 오면 즉시 종료합니다.
- 요청을 한 바이트씩 느리게 보내는 연결은 마감 시간에 닫힙니다.
- 큰 파일을 받던 클라이언트가 연결을 끊어도 서버가 다음 요청에 응답합니다.
- 긴 URI는 `414`, 큰 `Content-Length`는 `413`, 잘못된 요청은 `400`을 받습니다.

### LMS 요구사항 연결

| LMS 항목 | 구분 | 이 문서 |
| --- | --- | --- |
| R11 Forward 또는 Reverse 중 하나 이상 | 필수 | M6-1 |

### 범위 밖

| 항목 | 이유 |
| --- | --- |
| Forward Proxy, 캐싱 | Reverse Proxy 하나로 R11을 충족함 (M6-1) |
| Host 기준 라우팅 | R14는 경로와 Host 중 하나만 요구함 (M6-3) |
| 설정 파일 | CLI 인자로 C4를 충족함 (M6-5) |
| Least Connections | R15는 단순 로드 밸런싱을 권장함 (M6-17) |

| 부하에 따른 keep-alive 종료 | M8 부하 측정값에 직접 영향을 줌 (M7-4) |

## 2. M6 설계 결정

### M6-1. 프록시 종류 → Reverse Proxy

**결정할 것:** 클라이언트를 대신할지(Forward), 서버를 대신할지(Reverse)

**선택지**

| 방식 | 누구를 대신하나 | 목적지 | 로드 밸런싱 |
| --- | --- | --- | --- |
| Forward | 클라이언트 | 요청마다 다름 | 거의 없음 |
| Reverse | 서버 | 설정한 백엔드 목록 | Reverse의 역할 |
| 둘 다 | 양쪽 | 양쪽 | Reverse 쪽에서 함 |

**선택:** Reverse Proxy를 사용합니다. 클라이언트는 이 서버에만 접속하고, 서버가 규칙에 따라 백엔드를 고릅니다.

**출처:** [공통]. bloro 초안은 시간이 남으면 Forward를 더하는 안이었고, 범위는 [다빈] [예훈]과 같이 Reverse로 한정합니다.

**이유와 근거**

- R11은 둘 중 하나 이상을 요구하고, R14와 R15로 라우팅과 로드 밸런싱을 구체적으로 요구합니다.
- 백엔드를 로컬에 두 개 띄우면 되므로 외부 사이트 없이 확인할 수 있습니다.
- K4 설명: 백엔드를 외부에 드러내지 않고(보안), 요청을 여러 백엔드에 나눕니다(로드 밸런싱).

**선택하지 않은 이유**

- **Forward:** HTTPS에 필요한 `CONNECT`가 없으면 실제 사이트 대부분에 쓸 수 없고, 내부망 주소로 가는 요청(SSRF)을 따로 막아야 합니다.
- **둘 다:** 절대 URI 해석과 이름 찾기까지 설계와 확인 범위가 커집니다.

**알려진 한계:** 프록시가 단일 장애점이 되고, 모든 프록시 요청이 한 구간을 더 거칩니다.

### M6-2. 프록시 위치 → 웹 서버 안의 라우팅 단계

**결정할 것:** 프록시를 기존 서버에 넣을지, 별도 프로그램으로 나눌지

**선택지**

- 기존 서버에 라우팅 단계를 추가 [공통]
- 프록시 전용 실행 파일
- 실행 파일은 하나로 두고 인자로 역할을 전환

**선택:** 요청을 다 읽고 검사한 뒤 라우팅 단계를 거칩니다. 규칙에 걸리면 백엔드로 보내고, 걸리지 않으면 서버가 직접 처리합니다. `--route`가 없으면 모든 요청을 직접 처리합니다.

**출처:** [공통]

**이유와 근거**

- M4·M5의 스레드 풀, 요청 파서, keep-alive, 오류 응답을 그대로 씁니다.
- 정적 요청이 프록시를 한 번 더 거치지 않으므로 연결과 복사가 늘지 않습니다.
- 같은 서버를 백엔드로 여러 개 띄우면 프록시와 백엔드의 역할을 나눠 보여 줄 수 있습니다.

**선택하지 않은 이유**

- **전용 실행 파일:** 스레드 풀과 연결 루프를 공유 모듈로 옮겨야 하고, 정적 요청도 한 구간을 더 거칩니다.
- **인자로 역할 전환:** 선택한 방식과 구조가 거의 같은데 모드 분기만 늘어납니다.

### M6-3. 라우팅 기준 → 경로 접두사

**결정할 것:** 요청의 무엇을 보고 백엔드를 고를지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 경로 접두사 [다빈] [bloro] | curl과 브라우저로 바로 확인할 수 있음 | 한 도메인 안에서만 나눔 |
| Host 헤더 [예훈] | 도메인별로 서비스를 나눔 | 포트·대소문자 처리와 Host 지정이 필요함. HTTP/1.0 요청에는 Host가 없을 수 있음 |
| 둘 다 | 가장 유연함 | 우선순위 규칙이 필요함 |

**선택:** `?` 앞의 경로를 접두사와 비교합니다. 쿼리는 보지 않습니다. 경로는 바꾸지 않고 백엔드에 그대로 보냅니다.

**출처:** [다빈] [bloro]. 경로를 그대로 보내는 것은 [공통]입니다.

**이유와 근거**

- R14는 경로와 Host 중 하나를 요구하므로 경로만으로 충족합니다.
- 코치님 조언: URI를 자원 단위로 설계하면(`/api/users/3`, `/api/orders/5`) 접두사 규칙 하나로 라우팅할 수 있습니다.
- 경로를 고쳐 쓰지 않으므로 `/api`를 `/`로 바꾸는 것 같은 예외가 없습니다.

**선택하지 않은 이유**

- **Host:** 도메인별 분배라는 장점이 요구사항을 더 채우지 않고, 확인할 때마다 Host를 지정해야 합니다.
- **둘 다:** 우선순위와 확인할 조합이 늘어납니다.

### M6-4. 접두사 비교와 시작 검사 → 경로 경계와 가장 긴 접두사

**결정할 것:** 어떤 경로를 규칙에 걸린 것으로 볼지, 잘못된 규칙을 언제 거절할지

**선택지**

| 방식 | `/api` 요청 | `/apiary` 요청 |
| --- | --- | --- |
| 단순 문자열 비교 | 걸림 | 걸림 (잘못 걸림) |
| 규칙 끝에 `/` 필수 (`/api/`) [다빈] | 걸리지 않음 | 걸리지 않음 |
| `/` 경계 비교 (`/api`) [bloro] | 걸림 | 걸리지 않음 |

**선택:** 접두사 다음 글자가 `/`이거나 경로의 끝이면 걸립니다. 여러 규칙에 걸리면 가장 긴 접두사를 고릅니다.

| 규칙과 경로 | 결과 |
| --- | --- |
| `/api`에 `/api`, `/api/users/3`, `/api?x=1` | 걸림 |
| `/api`에 `/apiary`, `/a?/api` | 걸리지 않음 |
| `/api`와 `/api/admin`이 있을 때 `/api/admin/x` | `/api/admin` 규칙 |
| `/api/`로 적은 규칙 | 끝의 `/`를 떼고 `/api`로 다룸 |
| `/` 규칙 | 모든 경로에 걸림. 더 긴 규칙이 있으면 그쪽이 우선 |

규칙은 시작할 때 검사하고, 아래에 해당하면 이유를 출력하고 시작하지 않습니다.

| 시작 오류 | 이유 |
| --- | --- |
| `접두사=백엔드` 형식이 아님, 접두사가 `/`로 시작하지 않음, 포트가 1~65535가 아님 | 실행 중에 잘못된 규칙을 발견하지 않게 함 |
| 같은 접두사가 두 번 나옴 (`/api`와 `/api/` 포함) | 어느 규칙을 쓸지 알 수 없음 |
| 백엔드 이름을 주소로 바꾸지 못함 | 첫 요청이 아니라 시작할 때 알 수 있음 |
| 백엔드가 프록시 자신 (이 컴퓨터의 주소이고 수신 포트가 같음) | 요청 하나가 계속 되돌아와 작업 스레드를 모두 차지함 |
| 규칙 16개 또는 규칙당 백엔드 8개 초과 | 고정 크기 표를 씀 |

**출처:** 비교 규칙은 [bloro], 중복·자기 자신 검사는 [다빈], 고정 크기 표와 주소 검사는 [다빈] [bloro], 끝 슬래시와 `/` 규칙은 [합의]

**이유와 근거**

- `/api` 요청이 정적 파일의 `404`로 이어지면 원인을 찾기 어렵습니다.
- RFC 9110 7.6은 무한 루프를 막는 장치 없이 메시지를 자기 자신에게 전달하지 못하게 합니다(MUST NOT).
- 표 크기가 고정이므로 규칙을 위한 동적 할당과 해제가 없습니다.

**선택하지 않은 이유**

- **단순 문자열 비교:** `/apiary`가 `/api` 백엔드로 갑니다.
- **규칙 끝에 `/` 필수:** `/api`가 규칙에 걸리지 않아 예상과 다릅니다.

**알려진 한계:** 다른 프록시를 거쳐 되돌아오는 간접 루프는 시작할 때 알 수 없습니다. `/` 규칙을 주면 정적 파일과 CGI의 직접 처리가 모두 가려집니다.

### M6-5. 규칙을 받는 방법 → CLI 인자 --route

**선택지**

- 설정 파일
- 둘 다

**선택:** `--route /api=127.0.0.1:8001,127.0.0.1:8002` 형식으로 받습니다. 백엔드는 `이름:포트`로 적고 IPv4 주소를 시작할 때 한 번 찾습니다.

**출처:** CLI는 [공통], 옵션 이름은 [예훈] [bloro], 주소를 시작할 때 찾는 방식은 [다빈] [bloro]

**이유와 근거**

- 옵션이 하는 일이 라우팅 규칙 등록이라 `--route`가 의미에 맞습니다.
- 요청마다 이름을 찾지 않으므로 DNS 지연이 요청 처리에 섞이지 않습니다.

**선택하지 않은 이유**

- **설정 파일:** 규칙 몇 개를 위해 파일 형식, 파서, 줄 번호 오류 처리가 필요합니다.
- **둘 다:** 두 설정이 겹칠 때의 우선순위까지 정해야 합니다.

**알려진 한계:** 백엔드 주소의 DNS가 바뀌면 서버를 다시 시작해야 반영됩니다.

### M6-7. 라우팅 전 경로 검사 → 403으로 거절

**결정할 것:** `/static/../api/admin`처럼 규칙을 벗어나려는 경로를 어떻게 할지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 검사하지 않음 | 추가 규칙 없음 | 접두사 규칙을 우회할 수 있음 |
| 경로를 정리한 뒤 계속 진행 | 특이한 경로도 받음 | 정리한 경로와 백엔드로 보낸 경로가 다를 수 있음 |
| `..`만 라우팅 전에 거절 [다빈] | 백엔드 경로를 덜 제한함 | 라우팅과 직접 처리의 규칙이 달라짐 |
| `..`, `.`, 빈 조각을 모두 라우팅 전에 거절 | 모든 요청에 같은 규칙을 씀 | `//style.css` 같은 경로도 거절함 |

**선택:** 쿼리를 뗀 경로에 `..` 조각, `.` 조각(`/./`), 중간의 빈 조각(`//`)이 있으면 라우팅 전에 `403`으로 응답합니다. 경로 끝의 `/`는 허용합니다.

**출처:** 거절하는 방식과 세 가지 조각은 [다빈], 셋 다 라우팅 전에 검사하는 것은 [합의]

**이유와 근거**

- 라우팅과 직접 처리가 같은 경로를 보므로 규칙을 우회할 수 없습니다.
- `//cgi-bin/adder`를 허용하면 CGI 프로그램 파일이 정적 파일로 내려갈 수 있습니다.
- 정상 클라이언트는 이런 경로를 거의 보내지 않아, 정리해서 계속 진행하는 것보다 거절이 단순합니다.

**선택하지 않은 이유**

- **검사하지 않음:** `/static/../api/admin`이 `/static` 규칙으로 전달되고 백엔드에서 다른 경로로 해석될 수 있습니다.
- **경로 정리:** 경로를 그대로 전달한다는 M6-3과 맞지 않습니다.
- **`..`만 거절:** `/api//x`는 백엔드로 가고 `//style.css`는 거절되어 규칙을 한 줄로 설명할 수 없습니다.

**알려진 한계:** URL 표기만 검사합니다. `%2e%2e`는 해석하지 않고, 루트 안의 심볼릭 링크가 가리키는 곳은 보지 않습니다.

### M6-9. 백엔드 요청의 HTTP 버전 → HTTP/1.0

**결정할 것:** 백엔드로 보내는 요청 줄의 버전과 연결 방식

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 클라이언트 버전 그대로 [예훈] | 요청 줄을 고치지 않음 | 요청마다 백엔드 동작이 달라짐 |
| HTTP/1.1 고정 [bloro] | 최신 버전 | 백엔드가 chunked로 응답할 수 있음 |
| HTTP/1.0 고정 [다빈] | 백엔드가 chunked를 쓰지 않음 | 낮은 버전으로 보냄 |

**선택:** 요청 줄은 `HTTP/1.0`으로 고정하고, 요청마다 새 연결을 맺어 `Connection: close`를 보냅니다. 백엔드 소켓에는 `FD_CLOEXEC`를 걸어 CGI 자식이 물려받지 않게 합니다.

**출처:** 버전은 [다빈], 요청마다 새 연결은 [공통], `FD_CLOEXEC`는 [예훈]

**이유와 근거**

- 요청마다 연결을 닫으므로 HTTP/1.1의 연결 재사용을 쓰지 않습니다.
- RFC 9112 6.1은 HTTP/1.1 이상이 아닌 요청에 `Transfer-Encoding`으로 응답하지 못하게 하므로(MUST NOT), chunked 해석이 필요 없습니다.
- CSAPP Proxy Lab도 HTTP/1.0으로 요청합니다.

**선택하지 않은 이유**

- **클라이언트 버전 그대로:** HTTP/1.1 요청에서는 chunked 응답이 올 수 있습니다.
- **HTTP/1.1 고정:** chunked 응답을 그대로 전달하면 HTTP/1.0 클라이언트가 해석하지 못합니다.
- **연결 재사용:** 연결 풀과 락, 끊긴 연결의 처리가 필요합니다.

**알려진 한계:** 요청마다 새 연결을 쓰므로 `TIME_WAIT` 상태의 연결이 쌓입니다.

### M6-10. 백엔드로 보낼 헤더 → 원본을 걸러 전달하고 필요한 헤더 추가

**결정할 것:** 클라이언트 헤더 중 무엇을 빼고 무엇을 더할지

**선택지**

| 항목 | 예훈 | bloro | 다빈 |
| --- | --- | --- | --- |
| 빼는 홉 단위 헤더 | `Connection`만 | 목록 전체 + `Connection`에 적힌 이름 | 목록 대부분 + `Connection`에 적힌 이름 |
| `X-Forwarded-For` | 없음 | 클라이언트 IP로 덮어씀 | 없음 |
| `Via` | 없음 | 없음 | 추가 |

**선택:** m4m5.md에서 보존한 원본 헤더를 줄 단위로 걸러서 보냅니다.

| 처리 | 헤더 |
| --- | --- |
| 뺌 (홉 단위) | `Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Transfer-Encoding`, `Upgrade`, `Proxy-Authorization`, `Trailer`, 그리고 `Connection` 값에 적힌 헤더 |
| 뺌 (서버가 처리) | `Expect`, 클라이언트가 보낸 `X-Forwarded-For` |
| 다시 씀 | `Host`는 검사한 클라이언트 값 그대로, `Content-Length`는 검사한 본문 길이로 하나만 |
| 추가 | `Connection: close`, `X-Forwarded-For: <클라이언트 IP>`, `Via: <클라이언트 요청의 HTTP 버전> tiny` |
| 그대로 | `Content-Type`, `Cookie`, `Authorization` 등 나머지 |

Host가 없는 HTTP/1.0 요청에는 Host를 만들어 넣지 않습니다. `Expect: 100-continue`는 m4m5.md 3.6대로 서버가 답하고 본문을 모두 받은 뒤 백엔드에 연결합니다.

```text
클라이언트가 보낸 요청              백엔드로 보내는 요청
GET /api/users?id=1 HTTP/1.1        GET /api/users?id=1 HTTP/1.0
Host: example.com                   X-End: 1
Connection: keep-alive, X-Hop       Host: example.com
X-Hop: 1                            X-Forwarded-For: 203.0.113.7
X-End: 1                            Via: 1.1 tiny
X-Forwarded-For: 1.2.3.4            Connection: close
```

**출처:** 홉 단위 목록과 `X-Forwarded-For`는 [bloro], `Via`와 헤더 다시 쓰기는 [다빈], `Expect` 처리와 `Connection: close`는 [공통], Host를 만들지 않는 것은 [합의]

**이유와 근거**

- **홉 단위 헤더:** 프록시와 클라이언트 사이에서만 쓰는 헤더라 백엔드로 넘기지 않습니다. RFC 9110 7.6.1과 RFC 2616 13.5.1을 기준으로 정했습니다.
- **`X-Forwarded-For`:** 백엔드에는 모든 요청이 프록시 IP에서 온 것으로 보이므로 원래 클라이언트 IP를 알려 줍니다. K4의 "누가 누구를 대신하나"와 이어집니다. 클라이언트가 미리 넣은 값은 가짜일 수 있어 덮어씁니다.
- **`Via`:** RFC 9110 7.6.3이 프록시와 게이트웨이에 요구합니다(MUST).
- **`Expect`:** 백엔드의 `100 Continue`를 최종 응답과 혼동하지 않게 합니다.
- **Host:** HTTP/1.0에서는 필수가 아니므로 클라이언트가 보내지 않은 값을 만들지 않습니다.

**선택하지 않은 이유**

- **`Connection`만 빼기:** `Keep-Alive`, `Upgrade` 등이 백엔드로 넘어갑니다.
- **파싱한 필드로 헤더를 새로 만들기:** `Cookie`, `Authorization`처럼 저장하지 않은 헤더가 사라집니다.
- **`X-Forwarded-For`에 덧붙이기:** 클라이언트가 넣은 가짜 IP가 남습니다.
- **Host를 백엔드 주소로 바꾸기:** 백엔드가 만든 링크가 내부 주소를 가리킬 수 있습니다.

**알려진 한계:** 이 서버 앞에 다른 프록시가 있으면 그 프록시가 넣은 `X-Forwarded-For`도 덮어씁니다.

### M6-11. 응답 전달 → 헤더는 모아서 확인, 본문은 받는 대로 전달

**결정할 것:** 백엔드 응답을 언제 클라이언트에 보낼지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 전부 모은 뒤 전달 | 실패하면 항상 오류 응답을 보낼 수 있음 | 응답 크기만큼 메모리가 필요하고 크기 상한이 생김 |
| 바로 전달 | 메모리가 고정됨 | 잘못된 응답 헤더도 그대로 나감 |
| 헤더만 모아 확인하고 본문은 바로 전달 [다빈] [bloro] | 헤더 단계의 실패는 오류 응답으로 알리고, 본문 메모리는 고정됨 | 본문 도중의 실패는 오류 응답으로 바꿀 수 없음 |

**선택:** 응답 헤더를 최대 8 KiB까지 모아 확인하고, 정상이면 홉 단위 헤더를 빼고 상태 줄의 버전을 `HTTP/1.1`로, `Connection`을 클라이언트 연결에 맞게 다시 써서 보냅니다. 본문은 받는 대로 전달합니다.

**출처:** [다빈] [bloro]

**이유와 근거**

- 백엔드가 꺼짐, 무응답, 잘못된 응답은 헤더 단계에서 드러나므로 `502`나 `504`로 알릴 수 있습니다.
- 본문 크기와 상관없이 메모리 사용량이 일정합니다.
- 헤더 상한은 요청 헤더의 상한(8 KiB)과 같습니다.

**선택하지 않은 이유**

- **전부 모으기:** 상한을 1 MiB로 두면 그보다 큰 정상 파일도 `502`가 됩니다.
- **바로 전달:** 형식이 잘못된 응답을 걸러 낼 수 없습니다.

### M6-12. 응답의 끝 → Content-Length, 없으면 백엔드가 닫을 때

**결정할 것:** 백엔드 응답이 어디서 끝나는지, 클라이언트 연결을 유지할지

**선택지**

- 백엔드가 닫을 때까지 읽기(EOF) [bloro]

**선택**

| 백엔드 응답 | 클라이언트에 보내는 `Content-Length` | 본문 | 클라이언트 연결 |
| --- | --- | --- | --- |

| 길이 없음 | 없음 | 백엔드가 닫을 때까지 | 닫음 |
| HEAD 요청의 응답, `304` | 백엔드 값만. 없으면 만들지 않음 | 없음 | 유지 |
| `204` | 없음 (RFC 9110 8.6) | 없음 | 유지 |
| `100`, `103` | 전달하지 않고 다음 응답을 읽음 | | |
| `Transfer-Encoding` 있음, `101`, 형식 오류, 서로 다른 길이, 헤더 8 KiB 초과 | `502` 응답으로 바꿈 | | 유지 |

여기서 **유지**는 m4m5.md 5.2의 keep-alive 조건을 만족할 때 유지한다는 뜻입니다.

**출처:** [다빈]. 길이를 우선하는 규칙은 [예훈]과 같습니다.

**이유와 근거**

- 응답 길이를 알면 연결을 유지한다는 m4m5.md의 규칙을 프록시 응답에도 적용합니다.
- HEAD 응답의 `Content-Length`는 실제로 오는 본문 길이가 아닙니다. 그 길이만큼 읽으면 정상 응답을 본문이 덜 온 실패로 처리하게 됩니다.
- HTTP/1.0 요청에는 `Transfer-Encoding` 응답이 올 수 없으므로 잘못된 응답으로 봅니다.

**선택하지 않은 이유**

- **EOF까지 읽기:** 길이를 알리고도 일찍 닫힌 응답을 정상으로 볼 수 있고, 연결 유지를 판단하려면 결국 길이를 해석해야 합니다.
- **길이 규칙만 적용:** HEAD, `204`, `304`에서 오지 않을 본문을 기다립니다.

**알려진 한계:** 길이가 없는 응답에서 백엔드 프로세스가 죽으면 운영체제가 정상 종료(FIN)를 보내므로, 잘린 응답과 완성된 응답을 구분할 수 없습니다.

### M6-13. 본문 전달 중 실패 → 길이를 알면 닫고, 모르면 RST

**결정할 것:** 상태 줄을 이미 보낸 뒤 백엔드가 실패하면 클라이언트에 어떻게 알릴지

**선택지**

- 클라이언트 연결 닫기 [bloro]
- 길이를 알면 닫고, 모르면 RST로 닫기 [다빈]

**선택**

| 상황 | 처리 |
| --- | --- |
| 길이를 아는 본문이 덜 오거나 시간 초과 | 응답 없이 바로 닫음 |
| 길이를 모르는 본문에서 백엔드 오류나 시간 초과 | RST로 닫음. 남은 데이터를 비우지 않음 |
| 클라이언트가 연결을 끊음 | 백엔드 소켓과 클라이언트 소켓을 바로 닫음 |

**출처:** [다빈]

**이유와 근거**

길이가 없는 응답은 FIN을 받으면 끝난 것으로 봅니다. 중간에 실패한 응답을 FIN으로 닫으면 클라이언트가 성공으로 처리합니다. 아래는 curl의 종료 코드로 확인한 결과입니다.

| 응답 | FIN | RST | `shutdown(SHUT_WR)` 뒤 RST |
| --- | --- | --- | --- |
| `Content-Length` 있음, 중간에 끊김 | 오류 18 | 오류 56 | |
| 길이 없음, 중간에 끊김 | **성공(0)** | 오류 56 | **성공(0)** |

**선택하지 않은 이유**

- **항상 그냥 닫기:** 길이가 없는 응답이 잘려도 클라이언트가 알 수 없습니다.

### M6-14. 백엔드 시간 제한 → 연결 3초, 응답 헤더까지 합계 10초

**결정할 것:** 백엔드를 얼마나, 어떤 방식으로 기다릴지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 연결 3초 + 응답 10초 [예훈] | 값이 명확함 | 시간을 재는 방법이 정해지지 않음 |
| `SO_RCVTIMEO`, `SO_SNDTIMEO` [bloro] | 클라이언트 소켓과 같은 방식 | `read` 한 번 기준이고, 연결에 적용되는지 운영체제마다 다를 수 있음 |
| 논블로킹 `connect` + `poll`, 합계 10초 [다빈] | Linux와 macOS에서 같은 방식으로 전체 시간을 지킴 | 남은 시간을 계산해야 함 |

**선택:** 논블로킹 `connect`와 `poll`을 씁니다.

| 구간 | 제한 |
| --- | --- |
| 백엔드 하나에 연결 | 3초와 남은 합계 시간 중 짧은 쪽 |
| 첫 연결 시도 → 요청 전송 → 최종 응답 헤더 | 합계 10초 (`--proxy-timeout`) |
| 응답 본문 | 새 데이터가 10초(`--proxy-timeout`) 동안 오지 않으면 중단 |

다음 백엔드로 넘어가거나 `100`, `103`을 버리고 다시 읽어도 합계 마감은 처음 값을 그대로 씁니다. 클라이언트에 쓰는 시간은 이 제한에 넣지 않습니다.

**출처:** 방식과 합계 10초, `--proxy-timeout`은 [다빈], 연결 3초는 [예훈] [bloro], 둘의 조합은 [합의]

**이유와 근거**

- blocking `connect`는 응답 없는 주소에서 1분 넘게 작업 스레드를 붙잡을 수 있습니다.
- 연결에만 3초 상한을 두면 응답 없는 백엔드를 만나도 다음 백엔드를 시도할 시간이 남습니다(M6-15).
- 합계 10초는 CGI 시간 제한(m4m5.md 2.4)과 같은 값입니다.
- CI가 Linux와 macOS에서 실행되므로 두 환경에서 같은 방식이 필요합니다.
- `--proxy-timeout`으로 시간을 줄여 `504`를 짧은 시간에 확인할 수 있습니다.

**선택하지 않은 이유**

- **연결 3초와 응답 10초를 따로 적용:** 시도할 백엔드가 늘수록 전체 시간도 늘어납니다.
- **`SO_RCVTIMEO`:** 조금씩 계속 보내는 백엔드는 전체 시간을 제한할 수 없습니다.
- **`alarm`:** 시그널을 어느 스레드가 받을지 정할 수 없고 M7-5의 `sigwait`와 충돌합니다.

### M6-15. 재시도 → 연결 실패만 다음 백엔드로

**결정할 것:** 백엔드 하나가 실패했을 때 같은 요청을 다른 백엔드로 보낼지

**선택지**

- 재시도 없음 [예훈]
- 연결 거부·도달 불가만 다음 백엔드로, 시간 초과는 바로 `504` [다빈]
- 연결 단계의 거부와 시간 초과를 다음 백엔드로 [bloro]
- 응답 단계의 실패도 멱등 메서드는 재시도

**선택:** 연결 단계의 거부, 도달 불가, 시간 초과는 다음 백엔드로 넘어갑니다. 백엔드마다 한 번씩만 시도합니다.

| 상황 | 처리 |
| --- | --- |
| 연결 거부, 도달 불가, 연결 3초 초과 | 다음 백엔드 시도 |
| 모든 백엔드 연결 실패 | 시간 초과가 한 번이라도 있으면 `504`, 없으면 `502` |
| 합계 10초가 지남 | 남은 백엔드를 시도하지 않고 `504` |
| 소켓을 열지 못함 (fd 부족) | 다음 백엔드를 시도하지 않고 바로 `502` |
| 연결된 뒤의 실패 | 재시도하지 않음 (M6-16) |

**출처:** 연결 단계만 재시도하는 것은 [다빈] [bloro], 시간 초과도 넘어가는 것은 [bloro], fd 부족 처리는 [다빈], 응답 코드 규칙은 [합의]

**이유와 근거**

- 연결 단계에서는 요청을 보내지 않았으므로 POST도 두 번 처리되지 않습니다.
- 백엔드 2대 중 1대가 꺼져도 살아 있는 백엔드가 응답합니다.
- 응답 코드를 시도 순서와 상관없이 정하므로, Round-Robin의 시작 위치에 따라 `502`와 `504`가 바뀌지 않습니다.

**선택하지 않은 이유**

- **재시도 없음:** 2대 중 1대가 꺼지면 요청 절반이 실패합니다.
- **연결 시간 초과는 바로 `504`:** 연결 3초 상한을 둬도 다음 후보를 시도하지 못합니다.
- **응답 단계 재시도:** 규칙이 복잡해지고, 백엔드가 같은 요청을 두 번 처리할 수 있습니다.
- **백엔드 상태 확인:** 확인 스레드와 공유 상태가 필요합니다.

**알려진 한계:** 꺼진 백엔드에도 차례가 오면 매번 연결을 시도합니다. 응답 없는 백엔드를 만날 때마다 최대 3초가 늘어납니다.

### M6-16. 실패 응답 → 502와 504

**결정할 것:** 백엔드 실패를 어떤 상태 코드로 알릴지

**선택지**

- `502`와 `504`로 구분 [공통]
- 모든 백엔드가 꺼진 경우 `503`도 사용

**선택**

| 시점 | 실패 | 응답 | 클라이언트 연결 |
| --- | --- | --- | --- |
| 연결 | 모든 백엔드 실패 | `502` 또는 `504` (M6-15) | 유지 |
| 최종 응답 전송 전 | 시간 초과 | `504` | 유지 |
| 최종 응답 전송 전 | 연결이 끊김, 응답 형식 오류 | `502` | 유지 |
| 본문 전달 중 | 백엔드 실패, 클라이언트 끊김 | 없음 | 닫음 (M6-13) |

**출처:** [공통]. `503`을 쓰지 않는 이유는 [bloro]입니다.

**이유와 근거**

- `502`는 연결하지 못했거나 잘못된 응답, `504`는 제한 시간 안에 응답하지 않음을 뜻하므로 원인을 구분할 수 있습니다.
- 요청을 끝까지 읽은 뒤의 오류이므로 m4m5.md 5.2에 따라 연결을 유지합니다.

**선택하지 않은 이유**

- **`503`:** 백엔드 상태를 미리 확인하지 않으므로 요청 전에 모두 꺼졌는지 알 수 없습니다.

**알려진 한계:** 백엔드가 요청을 다 받기 전에 먼저 응답하고 연결을 끊으면, 요청 전송 실패로 보고 `502`를 보낼 수 있습니다.

### M6-17. 로드 밸런싱 → Round-Robin

**결정할 것:** 같은 규칙의 백엔드 중 어디로 보낼지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| Round-Robin [다빈] [예훈] | 단순하고 상태가 카운터 하나뿐임 | 느린 백엔드에도 차례가 오면 보냄 |
| Round-Robin + Least Connections [bloro] | 느린 백엔드를 피함 | 모든 종료 경로에서 처리 중 개수의 +1과 −1을 맞춰야 함 |

**선택:** 규칙마다 카운터를 두고 요청마다 다음 백엔드부터 시도합니다. 카운터는 C11 atomic으로 올립니다.

**출처:** Round-Robin은 [공통], Round-Robin만 쓰는 것은 [다빈] [예훈], atomic 카운터는 [bloro]

**이유와 근거**

- R15가 Round-Robin을 권장합니다.
- 여러 작업 스레드가 바꾸는 값이 카운터 하나라 mutex보다 atomic이 단순하고, C11은 프로젝트의 표준입니다(C1).

**선택하지 않은 이유**

- **Least Connections:** `502`, `504`, 끊김, 본문 전달 실패 등 모든 경로에서 개수를 맞춰야 합니다. 하나라도 빠지면 그 백엔드가 계속 바쁜 것으로 보여 요청을 받지 못합니다.
- **mutex 카운터 [예훈]:** 값 하나를 올리는 데 요청마다 락이 필요합니다.

**알려진 한계:** 느린 백엔드에도 같은 비율로 요청을 보냅니다.

## 3. M7 설계 결정

### M7-1. 잘못된 요청 검사 → 400

**결정할 것:** 프록시와 백엔드가 다르게 해석할 수 있는 요청을 어디까지 거절할지

**선택지**

- m4m5.md의 형식 검사만 유지
- URI, 제어 문자, 헤더 이름 검사를 추가 [다빈]

**선택:** 아래에 해당하면 `400`으로 응답하고 연결을 닫습니다.

| 검사 | 예시 |
| --- | --- |
| URI가 `/`로 시작하지 않음 | `GET ./secret HTTP/1.1`, `GET http://example.com/ HTTP/1.1` |
| 요청 줄이나 헤더 줄에 탭이 아닌 ASCII 제어 문자가 있음 (줄 끝의 CRLF 제외) | NUL, 줄 중간의 CR |
| 헤더 이름이 HTTP 토큰이 아님 | `Connection : close` (이름 뒤의 공백) |

**출처:** [다빈]

**이유와 근거**

- **URI:** 정적 파일 경로는 URI 앞에 `.`을 붙여 만들므로 `./secret`은 `../secret`이 되어 루트 밖을 가리킵니다. 라우팅 규칙도 모두 `/`로 시작합니다.
- **제어 문자:** 프록시는 한 줄로 본 헤더를 백엔드가 두 줄로 나누면 숨겨진 헤더가 전달됩니다. m4m5.md 3.4가 request smuggling을 막는 것과 목적이 같습니다.
- **헤더 이름:** RFC 9112 5.1은 이름과 `:` 사이에 공백이 있는 요청을 `400`으로 거절하도록 합니다(MUST). 토큰만 받으면 이름으로 홉 단위 헤더를 거르는 M6-10을 우회할 수 없습니다.

**선택하지 않은 이유**

- **기존 검사만 유지:** 원본 헤더를 백엔드로 전달하므로 잘못된 헤더가 백엔드까지 갑니다.

**알려진 한계:** 절대 URI(`GET http://...`)를 받지 않습니다. RFC 9112 3.2.2는 일반 서버도 절대 URI를 받도록 합니다.

### M7-2. 메서드 형식 → 토큰이 아니면 400, 모르는 메서드는 501

**결정할 것:** 잘못된 메서드와 지원하지 않는 메서드를 어떻게 구분할지

**선택지**

- 모두 `501` (m4m5.md 3.3)
- 영문자가 아니면 `400`
- RFC 토큰이 아니면 `400`, 형식이 맞으면 `501` [예훈] [다빈]

**선택:** `G@T`처럼 토큰에 허용되지 않는 글자가 있으면 `400`, `PUT`이나 `FOO`처럼 형식은 맞지만 지원하지 않으면 `501`로 응답합니다. 둘 다 연결을 닫습니다.

**출처:** [예훈] [다빈]

**이유와 근거**

- RFC 9110 5.6.2의 토큰 규칙을 그대로 적용합니다. 허용 글자는 영문자, 숫자, ``! # $ % & ' * + - . ^ _ ` | ~``입니다.
- M7-1의 헤더 이름 검사와 같은 규칙을 씁니다.

**선택하지 않은 이유**

- **모두 `501`:** 형식 오류와 지원 여부를 구분할 수 없습니다.
- **영문자 검사:** `-`나 `_`처럼 표준이 허용하는 글자도 형식 오류가 됩니다.

### M7-3. 대상에 허용하지 않는 메서드 → 405와 Allow

**결정할 것:** 서버는 알지만 요청한 대상에는 허용하지 않는 메서드를 어떻게 알릴지

**선택지**

- `501` 유지 [다빈] (m4m5.md 6장)
- `405` + `Allow` [예훈] (bloro는 시간이 남으면 추가하는 안)

**선택**

| 요청 | 응답 | 연결 |
| --- | --- | --- |
| 정적 파일에 POST | `405`, `Allow: GET, HEAD` | 유지 |
| CGI에 HEAD | `405`, `Allow: GET, POST`, 본문 없음 | 유지 |

기준선 테스트와 구현 계획의 확인 명령도 정적 파일 POST의 응답을 `405`로 둡니다. 프록시 경로의 POST와 HEAD에는 적용하지 않습니다.

**출처:** 정적 파일 POST는 [예훈], CGI HEAD는 [합의]

**이유와 근거**

- `501`은 서버가 지원하지 않는 메서드라는 뜻인데, 서버는 POST와 HEAD를 지원합니다. `405`는 이 대상에 허용하지 않는다는 뜻입니다.
- RFC 9110 15.5.6은 `405` 응답에 `Allow`를 넣도록 합니다(MUST).
- Phase 1에서 `501`을 유지한 것은 동작을 바꾸지 않는 교체 단계였기 때문이고, Phase 2는 동작을 늘리는 단계입니다.

**선택하지 않은 이유**

- **`501` 유지:** 상태 코드의 의미가 실제 동작과 다릅니다.
- **정적 파일 POST만 변경:** 같은 상황에서 CGI HEAD만 `501`이 됩니다.

### M7-4. 클라이언트 요청 수신 마감 → 첫 바이트 5초, 헤더 10초, 본문 30초

**결정할 것:** 요청을 아주 느리게 보내는 연결(Slowloris)을 언제 끊을지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 읽기 타임아웃만 사용 (m4m5.md 2.4) | 추가 규칙 없음 | 조금씩 계속 보내면 작업 스레드를 붙잡음 |
| 요청 줄부터 헤더 끝까지 10초 [예훈] | 헤더 단계를 제한함 | 본문을 느리게 보내는 것은 막지 못함 |
| 헤더와 본문에 각각 마감 [다빈] | 두 단계를 모두 제한함 | 읽기마다 남은 시간을 계산해야 함 |

bloro 초안은 시간이 남으면 헤더 마감을 더하는 안입니다.

**선택**

| 구간 | 제한 | `--timeout` 기준 |
| --- | --- | --- |
| 첫 바이트 대기 (keep-alive의 다음 요청 포함) | 5초 | 1배 |
| 요청을 읽는 중 새 바이트가 오지 않음 | 5초 | 1배 |
| 첫 바이트부터 헤더 끝까지 전체 | 10초 | 2배 |
| 본문 전체 | 30초 | 6배 |

- 전체 마감은 바이트가 더 와도 연장하지 않습니다. 마감이 지나면 응답 없이 연결을 닫습니다.
- 본문 마감은 헤더 검사를 마치고, 필요하면 `100 Continue`를 보낸 뒤부터 셉니다.
- `poll`로 전체 마감까지 남은 시간과 읽기 타임아웃 중 짧은 쪽만큼 기다립니다.
- 클라이언트가 다음 요청을 미리 보냈으면(파이프라이닝) 소켓을 기다리기 전에 버퍼의 데이터를 먼저 봅니다.

**출처:** [다빈]. 부하에 따른 keep-alive 종료를 제외한 것은 [합의]입니다.

**이유와 근거**

- 읽기 타임아웃은 `read` 한 번 기준이라, 4초마다 한 바이트씩 보내면 작업 스레드를 계속 붙잡을 수 있습니다.
- 헤더만 제한하면 같은 공격을 POST 본문으로 옮길 수 있습니다.
- 읽기를 `poll`로 기다리므로 종료 파이프(M7-6)를 함께 기다릴 수 있습니다.

**선택하지 않은 이유**

- **읽기 타임아웃만 사용:** 전체 시간을 제한하지 못합니다.
- **헤더 마감만 사용:** 본문 단계의 느린 전송이 남습니다.
- **감시 스레드:** 연결 목록, 락, fd 재사용 문제가 생깁니다.
- **부하에 따른 keep-alive 종료** (큐에 쌓인 연결이 쉬는 작업 스레드보다 많으면 응답 뒤 닫기): M8 부하 측정의 처리량과 keep-alive 재사용률에 직접 영향을 줍니다.

**알려진 한계:** 본문을 30초 안에 보내지 못하는 느린 정상 업로드도 끊깁니다. 요청을 계속 보내는 keep-alive 연결은 `--keepalive-max`(기본 100건)까지 작업 스레드를 차지할 수 있습니다.

### M7-5. 종료 신호 받기 → sigwait 전용 스레드

**결정할 것:** 어떤 시그널을 어느 스레드에서 받을지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 핸들러 + 플래그 | 짧음 | 아무 스레드에서나 실행되고 mutex를 쓸 수 없음 |
| `sigwait` 전용 스레드 [공통] | 보통 스레드처럼 mutex와 로그를 쓸 수 있음 | 스레드가 하나 늘어남 |
| `signalfd` / `kqueue` | 시그널을 fd로 받음 | 운영체제마다 다름 |

**선택:** 다른 스레드를 만들기 전에 SIGINT와 SIGTERM을 막고, 시그널 전용 스레드가 `sigwait`로 받습니다. SIGHUP은 종료 신호로 받지 않습니다. SIGPIPE는 무시합니다.

**출처:** `sigwait`는 [공통], SIGINT와 SIGTERM만 받는 것은 [예훈] [bloro] + [합의]

**이유와 근거**

- m4m5.md 2.7에서 정한 방식입니다.
- K6가 요구하는 신호는 SIGINT와 SIGTERM입니다.
- 쓰기 도중 클라이언트가 끊어도 SIGPIPE로 서버가 죽지 않습니다.

**선택하지 않은 이유**

- **핸들러:** 스레드 풀의 조건 변수를 안전하게 깨울 수 없습니다.
- **`signalfd`, `kqueue`:** Linux용과 macOS용을 따로 둬야 합니다.
- **SIGHUP도 받기 [다빈]:** 과제가 요구하는 신호가 아니고 규칙이 늘어납니다.

**알려진 한계:** 터미널을 닫아 SIGHUP을 받으면 정리 없이 끝납니다. `nohup`으로 실행하면 SIGHUP을 무시합니다.

### M7-6. 대기 중인 스레드 깨우기 → poll과 종료 파이프

**결정할 것:** 기다리는 스레드를 어떻게 깨우고, 누가 자원을 정리할지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 시그널 스레드가 리스닝 소켓을 닫고 정리 [예훈] | 단순해 보임 | 다른 스레드의 `close`로 `accept`가 깨어난다는 보장이 없고, 닫힌 fd 번호가 재사용될 수 있음 |
| main이 `poll`로 리스닝 소켓과 종료 파이프를 기다림, 쉬는 연결은 5초 타임아웃 [bloro] | 두 운영체제에서 main이 바로 깨어남 | 쉬는 연결 때문에 최대 5초 늦어짐 |
| 쉬는 keep-alive 연결도 종료 파이프를 함께 기다림 [다빈] | 쉬는 연결도 바로 끝남 | 읽기 대기에서 fd 두 개를 봐야 함 |

**선택**

| 대기 위치 | 깨우는 방법 |
| --- | --- |
| main이 새 연결을 기다림, 작업 스레드가 keep-alive의 다음 요청을 기다림 | 종료 파이프에 1바이트를 쓰고 `poll`이 깨어남 |
| main이 가득 찬 큐에서 기다림, 작업 스레드가 빈 큐에서 기다림 | `conn_queue_shutdown`이 조건 변수를 깨움 |

| 규칙 | 이유 |
| --- | --- |
| 종료 파이프의 바이트는 읽지 않음 | 기다리는 모든 스레드가 같은 알림을 봄 |
| 리스닝 소켓은 논블로킹, 접속 소켓은 블로킹 | `poll`과 `accept` 사이에 클라이언트가 끊어도 main이 멈추지 않음 |
| 소켓과 알림이 함께 준비되면 소켓을 먼저 처리 | 이미 도착한 요청을 두고 닫으면 RST가 나갈 수 있음 |
| 종료 알림은 연결의 두 번째 요청을 기다릴 때부터 봄 | 큐에 있던 연결의 첫 요청을 처리함 (M7-7) |
| main이 작업 스레드와 시그널 스레드를 모두 join한 뒤 자원을 해제 | 해제된 자원에 다른 스레드가 접근하지 않음 |

시그널 스레드는 알리기만 합니다. 작업 스레드가 모두 끝나면 main이 정리 완료 플래그를 세우고 `pthread_kill`로 시그널 스레드를 깨워 join합니다. 이 플래그가 서 있으면 깨운 시그널을 두 번째 종료 신호로 세지 않습니다.

**출처:** [다빈]. `poll`과 종료 파이프, main의 정리, 시그널 스레드 join은 [다빈] [bloro]입니다.

**이유와 근거**

- m4m5.md 2.7은 `shutdown(listenfd)`가 macOS에서 보장되지 않아 `poll`과 파이프를 쓰기로 했습니다.
- M7-4에서 이미 `poll`로 읽기를 기다리므로 종료 파이프를 함께 보는 비용이 작습니다.

**선택하지 않은 이유**

- **리스닝 소켓 닫기:** `accept`가 깨어나지 않거나 다른 파일을 잘못 다룰 수 있습니다.
- **5초 타임아웃에 맡기기:** main과 같은 파이프를 쓰면 기다릴 필요가 없습니다.

### M7-7. 이미 받은 연결 → 큐에 남은 연결까지 처리

**결정할 것:** 종료 신호가 왔을 때 진행 중인 요청과 큐의 연결을 어떻게 할지

**선택지**

- 바로 닫기
- 진행 중인 요청만 끝내기
- 진행 중인 요청과 큐에 남은 연결까지 처리 [다빈] [bloro]

**선택:** 새 연결은 받지 않습니다. 진행 중인 요청과 큐에 남은 연결의 첫 요청을 처리합니다. 응답 헤더를 쓰기 전에 종료가 시작됐으면 `Connection: close`를 붙이고 응답 뒤 닫습니다. 진행 중인 프록시 요청도 끝까지 처리하고 백엔드 소켓을 닫습니다.

**출처:** [다빈] [bloro]. 진행 중인 응답을 끝까지 보내고 `Connection: close`를 붙이는 것은 [공통]입니다.

**이유와 근거**

- 이미 `accept`한 클라이언트가 응답 없이 끊기지 않습니다.
- `Connection: close`가 없으면 요청을 계속 보내는 연결이 `--keepalive-max`까지 종료를 늦춥니다.

**선택하지 않은 이유**

- **바로 닫기:** 클라이언트가 잘린 응답을 받습니다.
- **진행 중인 요청만:** 큐에서 기다리던 연결이 응답 없이 끊깁니다.

**알려진 한계:** 정상 종료에는 전체 시간 상한이 없습니다. 큐의 연결이 많거나 클라이언트가 응답을 천천히 읽으면 종료가 늦어지며, 이때 M7-8로 즉시 끝낼 수 있습니다. 운영체제의 연결 대기열(backlog)에만 있던 연결은 응답 없이 끊깁니다.

### M7-8. 두 번째 종료 신호 → 즉시 종료

**결정할 것:** 정상 종료가 오래 걸릴 때 어떻게 바로 끝낼지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 끝날 때까지 기다림 [예훈] | 단순함 | 느린 클라이언트가 종료를 붙잡음 |
| 두 번째 신호면 종류와 상관없이 즉시 종료 [bloro] | 규칙이 하나임 | SIGINT와 SIGTERM이 겹쳐도 강제 종료됨 |
| 추가 SIGINT만 즉시 종료 [다빈] | 다른 신호가 겹쳐도 응답을 마침 | 신호마다 규칙이 다름 |

**선택:** 첫 번째 SIGINT 또는 SIGTERM은 정상 종료, 두 번째는 종류와 상관없이 `_exit(1)`로 즉시 종료합니다.

**출처:** [bloro]

**이유와 근거**

- "두 번째는 즉시 종료" 하나로 설명하고 확인할 수 있습니다.
- `kill` 명령으로도 강제 종료할 수 있습니다.

**선택하지 않은 이유**

- **끝날 때까지 기다림:** 강제로 끝내려면 `kill -9`만 남습니다.
- **추가 SIGINT만:** 신호 종류를 나눠 설명해야 하고, 과제 환경에서 다른 신호가 겹치는 경우는 드뭅니다.
- **종료 시간 상한:** 타이머나 `sigtimedwait`가 필요한데 macOS에는 `sigtimedwait`가 없습니다.

**알려진 한계:** 실행 도구가 SIGINT와 SIGTERM을 연달아 보내면 처리 중인 응답이 잘립니다. `_exit`에서는 LeakSanitizer 검사가 실행되지 않습니다.

### M7-9. CGI 자식 → 프로세스 그룹을 나누고 시그널 설정을 되돌림

**결정할 것:** 종료 신호가 실행 중인 CGI에 어떤 영향을 줄지

**선택지**

| 항목 | 예훈 | bloro | 다빈 |
| --- | --- | --- | --- |
| 시그널 막기 해제 | 함 | 함 | 함 |
| SIGPIPE 기본값 복원 | 없음 | 함 | 함 |
| 별도 프로세스 그룹 (`setpgid`) | 없음 | 없음 | 함 |
| 실행 중인 pid 목록을 강제 종료 때 정리 | 없음 | 없음 | 함 |

**선택**

- CGI를 별도 프로세스 그룹에서 실행합니다.
- `execve` 전에 시그널 막기를 풀고 SIGPIPE 처리를 기본값으로 되돌립니다.
- 서버가 CGI를 중단할 때(시간 초과, 출력 1 MiB 초과, 읽기 오류)는 프로세스 그룹과 CGI 자신에게 모두 SIGKILL을 보냅니다.
- 실행 중인 pid 목록은 두지 않습니다.

**출처:** [다빈]. pid 목록을 제외한 것은 [합의]입니다.

**이유와 근거**

- 터미널의 Ctrl+C는 서버와 같은 프로세스 그룹 전체에 전달됩니다. 그룹을 나누지 않으면 CGI가 함께 죽어 처리 중이던 요청이 `500`을 받으므로, 진행 중인 요청을 끝내는 M7-7이 깨집니다.
- 막은 시그널과 무시한 SIGPIPE는 `execve` 뒤에도 남으므로 되돌려야 CGI가 일반 프로그램처럼 동작합니다.
- CGI가 다른 그룹으로 옮겨 가면 그룹에 보낸 시그널이 닿지 않으므로 CGI 자신에게도 보냅니다.

**선택하지 않은 이유**

- **프로세스 그룹을 나누지 않음:** CGI 요청에서 정상 종료가 지켜지지 않습니다.
- **pid 목록:** `fork`와 목록 기록, `waitpid`와 목록 삭제를 각각 한 락 안에서 처리해야 합니다.
- **`PR_SET_PDEATHSIG`:** Linux에만 있습니다.

**알려진 한계:** 강제 종료하거나 서버가 갑자기 죽으면 실행 중인 CGI가 남을 수 있습니다. CGI의 10초 제한도 서버가 감시하므로, 스스로 끝나지 않는 CGI는 계속 실행됩니다. 스스로 끝난 CGI가 남긴 자식도 정리하지 않습니다.

### M7-10. 자원 회수 확인 → sanitizer, fd 수, 좀비

**결정할 것:** 끊김과 종료 뒤에 메모리, fd, 자식 프로세스가 회수됐는지 무엇으로 확인할지

**선택지**

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| LeakSanitizer (Linux) [bloro] [다빈] | 개발 빌드에 포함되고 종료 코드로 판정함 | macOS에서는 누수를 판정하지 않음. fd와 자식은 보지 않음 |
| valgrind | 과제가 예로 듦 | ASan과 함께 쓸 수 없고 느림 |
| 열린 fd 수와 좀비 확인 [bloro] | 메모리 검사가 보지 않는 자원을 확인함 | 운영체제마다 세는 방법이 다름 |

**선택**

- **메모리:** 정상·오류 요청을 섞어 보낸 뒤 SIGTERM을 한 번 보내고, Linux에서 종료 코드 0과 누수 보고 없음을 확인합니다.
- **fd:** 강제 끊김을 여러 번 일으킨 전후로 서버의 열린 fd 수를 비교합니다(Linux).
- **자식 프로세스:** CGI 도중 끊김 뒤 `ps`에 좀비가 없는지 봅니다.

| 상황 | 회수할 자원 |
| --- | --- |
| 클라이언트가 응답 도중 끊김 | 클라이언트 소켓, 프록시면 백엔드 소켓 |
| 백엔드가 본문 도중 끊김 | 백엔드 소켓, 클라이언트 소켓 |
| 요청 본문 도중 끊김 | 본문 버퍼, 클라이언트 소켓 |
| CGI 실행 중 끊김 | 자식 프로세스, 파이프, 클라이언트 소켓 |

**출처:** 종료 코드로 판정하는 것은 [bloro] [다빈], fd 수와 좀비 확인, 회수할 자원 정리는 [bloro]

**이유와 근거**

- K5가 끊김 시 자원 회수를, Q4가 메모리 검사를 요구합니다.
- 메모리 누수 검사는 fd와 자식 프로세스를 보지 않으므로 함께 확인합니다.
- 두 번째 신호의 `_exit`에서는 누수 검사가 실행되지 않으므로(M7-8) 신호를 한 번만 보냅니다.

**선택하지 않은 이유**

- **valgrind:** 별도 빌드가 필요하고, 스레드가 많은 서버에서 매우 느립니다.
- **코드 리뷰만:** 오류 경로 하나를 빠뜨리기 쉽습니다.

## 4. 요청과 종료 흐름

### 요청 하나의 흐름

```text
./build/tiny 8000 --route /api=127.0.0.1:8001,127.0.0.1:8002

[main]        poll(리스닝 소켓, 종료 파이프) → accept → 큐에 넣기
[작업 스레드] 큐에서 연결을 꺼내 요청을 반복 처리
  요청 줄·헤더 읽기         마감 10초 (M7-4)
  → 요청 검사               400, 414, 501, 505 (M7-1, M7-2)
  → Expect 처리, 본문 읽기  413, 417, 마감 30초 (M7-4)
  → 경로 검사               403 (M6-7)
  → 라우팅 (M6-4)
      ├ 걸리지 않음 → 정적 파일 / CGI 직접 처리     405 (M7-3)
      └ 걸림 → Round-Robin으로 시작 백엔드 선택 (M6-17)
               → 연결, 실패하면 다음 백엔드         502, 504 (M6-15)
               → HTTP/1.0 요청 전송 (M6-10)         502, 504 (M6-16)
               → 응답 헤더 확인                     502, 504 (M6-12, M6-16)
               → 헤더 전송 → 본문을 받는 대로 전달  실패하면 닫기 또는 RST (M6-13)
               → 백엔드 소켓 닫기
  → 연결 유지 조건을 만족하면 다음 요청, 아니면 닫기
```

### 종료 흐름

```text
[시그널 스레드] sigwait → 첫 번째 신호
                종료 플래그 → 종료 파이프에 1바이트 → conn_queue_shutdown → 종료 시작 로그
                → 다시 sigwait
                   ├ 두 번째 신호            → _exit(1)
                   └ main이 깨움 (정리 완료) → 스레드 종료

[main]          accept 루프를 나옴 → 리스닝 소켓 닫기 → 작업 스레드 join
                → 정리 완료 플래그 → pthread_kill로 시그널 스레드를 깨워 join
                → 자원 해제 → 종료 완료 로그 → 종료 코드 0

[작업 스레드]   진행 중인 요청을 마침 → Connection: close → 연결 닫기
                쉬는 keep-alive 연결은 종료 파이프로 깨어나 바로 닫음
                큐에 남은 연결의 첫 요청까지 처리한 뒤 끝남
```

## 7. 확인 기준

백엔드는 받은 메서드, 경로, 헤더, 본문 길이와 자기 포트를 돌려주고, 늦은 응답, 길이 없는 응답, 중간에 끊긴 응답을 만들 수 있는 테스트용 서버로 준비합니다. `504`는 `--proxy-timeout`을 줄여 확인합니다.

### 단위 테스트

| 대상 | 확인할 것 |
| --- | --- |
| 규칙 해석 | 정상 규칙, 백엔드 여러 개, 형식 오류, 중복, 상한 초과, 자기 자신, `/api/`와 `/` |
| 라우팅 | `/` 경계, 가장 긴 접두사, 쿼리 무시, 규칙 없음 |
| Round-Robin | 순서, 여러 스레드에서 순번 사용 (`make tsan`) |
| 요청 헤더 만들기 | 홉 단위 헤더와 `Connection`에 적힌 이름 제거, `Expect` 제거, `X-Forwarded-For` 덮어쓰기, `Via` 추가, Host가 없는 요청, 모르는 헤더 유지 |
| 응답 헤더 해석 | 형식 오류, 8 KiB 초과, 길이 있음·없음·충돌, HEAD, `204`, `304`, `100`, `103`, `101`, `Transfer-Encoding` |
| 요청 검사 | 메서드 토큰, URI 시작 글자, 제어 문자, 헤더 이름 |

### M6 기능 테스트

| 요청이나 조건 | 기대 결과 |
| --- | --- |
| `GET /api/users` 반복 | 로그에 두 백엔드가 번갈아 찍힘 |
| `GET /api`, `GET /apiary` | 앞은 백엔드로 감, 뒤는 서버가 직접 처리 |
| `GET /home.html` | 백엔드를 거치지 않고 `200` |
| `POST /api/users` | 백엔드가 같은 본문 길이와 `Content-Type`을 받음 |
| `HEAD /api/users` | 본문을 기다리지 않고 끝남 |
| `Expect: 100-continue`를 붙인 POST | 서버가 `100`을 보내고 백엔드는 `Expect`를 받지 않음 |
| `X-Forwarded-For: 1.2.3.4`를 붙인 요청 | 백엔드는 실제 클라이언트 IP를 받음 |
| `curl --path-as-is`로 `/api/../x`, `/api//x`, `/api/./x` | `403` |
| `DELETE /api/users/3` | `501` |
| 백엔드 2대 중 1대를 끄고 반복 | 모두 살아 있는 백엔드가 응답 |
| 백엔드를 모두 끔 | `502` |
| 연결 시간 초과와 연결 거부가 섞이고 모두 실패 | `504` |
| 연결은 받지만 응답하지 않는 백엔드 | `--proxy-timeout` 뒤 `504` |
| 한 연결로 프록시 요청 두 번 (길이 있음) | 연결 재사용 |
| 길이 없는 응답 | 본문을 모두 받고 연결이 닫힘 |
| 길이 없는 응답이 오류로 중간에 끊김 | curl이 오류로 끝남 |

### M7 기능 테스트

| 요청이나 조건 | 기대 결과 |
| --- | --- |
| `G@T / HTTP/1.1`, `PUT / HTTP/1.1` | `400`, `501` |
| `GET ./secret HTTP/1.1`, NUL이 든 헤더, `Connection : close` | `400` |
| `POST /home.html` | `405`, `Allow: GET, HEAD` |
| `HEAD /cgi-bin/adder?1&2` | `405`, `Allow: GET, POST`, 본문 없음 |
| 긴 URI, 큰 `Content-Length` | `414`, `413` |
| 헤더를 1초마다 한 바이트씩 전송 | 첫 바이트 뒤 약 10초에 닫힘 |
| 본문을 1초마다 한 바이트씩 전송 | 본문 읽기 시작 뒤 약 30초에 닫힘 |
| 정적, CGI, 프록시를 섞은 동시 요청 50개 | 모두 정상 응답 |
| 큰 파일을 받는 중에 클라이언트를 끊음 | 서버가 다음 요청에 응답 |
| 큰 파일을 받는 중에 SIGTERM | 파일을 끝까지 받고 서버 종료, 새 연결은 거부 |
| CGI 실행 중 터미널에서 Ctrl+C | CGI 요청이 정상 응답을 받고 서버 종료 |
| keep-alive로 쉬는 연결이 있을 때 SIGTERM | 5초를 기다리지 않고 종료 |
| 종료 중 SIGINT나 SIGTERM을 한 번 더 보냄 | 즉시 종료 |
| 정상·오류 요청 뒤 SIGTERM 한 번 | 종료 코드 0, 누수 보고 없음 (Linux) |
| 큰 파일, POST 본문, CGI, 프록시 도중 강제 끊김 반복 | 전후의 열린 fd 수가 같고 좀비가 없음 (Linux) |
| 시그널 설정을 출력하는 CGI | SIGINT·SIGTERM이 막혀 있지 않고 SIGPIPE가 기본값 |
